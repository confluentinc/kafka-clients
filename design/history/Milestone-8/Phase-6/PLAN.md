# Phase 6: `NetworkClientDelegate` + `RequestManager` + `CoordinatorRequestManager`

## Goal

Translate the network-side scaffolding that all request managers (Phase
7–9) share:

- `NetworkClientDelegate` — wraps the existing `KafkaClient` trait, manages
  an `unsent_requests` queue with per-request timers, propagates metadata
  errors, and drives `client.poll(...)`.
- `RequestManager` trait — the common interface (`poll`, `pollOnClose`,
  `maximumTimeToWait`, `signalClose`) that every Phase 7–9 manager
  implements.
- `RequestState` + `TimedRequestState` — exponential-backoff bookkeeping
  + per-attempt deadline tracking shared across all managers.
- `CoordinatorRequestManager` — the first concrete `RequestManager`. It
  sends `FindCoordinator` requests when no coordinator is known, exposes
  the discovered coordinator `Node`, handles per-error retry semantics.
- `RequestManagers` — the container holding optional/concrete managers;
  Phase 10's bg task iterates over its `entries()` to poll each manager.
  In Phase 6 we ship a **skeleton container** with `Option<...>` slots
  for managers that don't exist yet (Phase 7–9 fill them in).

After this phase lands, Phase 7 (`Fetch*`) and Phase 8 (`Heartbeat` /
`Membership`) and Phase 9 (`Commit`) can implement `RequestManager` for
their concrete managers and feed `UnsentRequest`s through the delegate.

## Type-by-type spec

### `RequestManager` trait (`src/consumer/internals/request_manager.rs`)

`pub(crate)`. Java: `RequestManager.java:28-87`.

```rust
use crate::consumer::internals::network_client_delegate::PollResult;

pub(crate) trait RequestManager: Send + 'static {
    /// Java: `PollResult poll(long currentTimeMs)`. Non-blocking; produces
    /// `UnsentRequest`s the bg task will dispatch through `NetworkClientDelegate`.
    fn poll(&mut self, current_time_ms: i64) -> PollResult;

    /// Java: `default PollResult pollOnClose(long currentTimeMs) { return EMPTY; }`.
    fn poll_on_close(&mut self, _current_time_ms: i64) -> PollResult {
        PollResult::empty()
    }

    /// Java: `default long maximumTimeToWait(long currentTimeMs) { return Long.MAX_VALUE; }`.
    fn maximum_time_to_wait(&self, _current_time_ms: i64) -> i64 {
        i64::MAX
    }

    /// Java: `default void signalClose() {}`.
    fn signal_close(&mut self) {}
}
```

Notes:

- **No `#[async_trait]`** per DoD §11. `poll()` is per-iteration and
  Java itself documents it as non-blocking ("no network I/O occurs in
  this method"). Sync `fn` is correct.
- **`Send + 'static`** because the bg task owns `Box<dyn RequestManager>`
  via `RequestManagers::entries()`. No `Sync` — each manager is
  single-task-owned.
- **`&mut self`** on `poll` and `poll_on_close` — they mutate the
  manager's internal `RequestState` (backoff, attempt count, etc.).

#### `UnsentRequest` and `PollResult` (same file)

```rust
use tokio::sync::oneshot;

pub(crate) struct UnsentRequest {
    request_builder: Box<dyn AbstractRequest::Builder>, // or concrete dispatch
    handler: FutureCompletionHandler,
    node: Option<Node>,
    deadline_ms: i64,
    enqueue_time_ms: i64,
}

impl UnsentRequest {
    pub(crate) fn new(
        request_builder: Box<dyn AbstractRequest::Builder>,
        node: Option<Node>,
    ) -> Self;

    pub(crate) fn future(&self) -> &FutureHandle;
    pub(crate) fn when_complete(self, callback: impl FnOnce(Result<ClientResponse, KafkaError>) + Send + 'static) -> Self;
    pub(crate) fn request_builder(&self) -> &dyn AbstractRequest::Builder;
    pub(crate) fn node(&self) -> Option<&Node>;
}

pub(crate) struct FutureCompletionHandler {
    // Wraps a oneshot::Sender<Result<ClientResponse, KafkaError>> + a
    // Mutex<Option<Sender>> for idempotent completion (mirrors Phase 5's
    // CompletableEventHandle pattern).
    inner: Arc<FutureCompletionInner>,
}

pub(crate) struct PollResult {
    pub time_until_next_poll_ms: i64,
    pub unsent_requests: Vec<UnsentRequest>,
}

impl PollResult {
    pub(crate) const WAIT_FOREVER: i64 = i64::MAX;
    pub(crate) fn empty() -> Self;
    pub(crate) fn from_wait(wait_ms: i64) -> Self;
    pub(crate) fn with_requests(requests: Vec<UnsentRequest>) -> Self;
    pub(crate) fn single(request: UnsentRequest) -> Self;
}
```

**`AbstractRequest::Builder`** — the polymorphic request-builder trait
already exists in `src/common/requests/abstract_request.rs` (Phase-0
work for producer). Verify and reuse; if missing fields, extend.
Translation contract: Java's `AbstractRequest.Builder<?>` is a sealed
trait in Java; Rust uses `Box<dyn AbstractRequestBuilder>` (whatever
the existing surface is).

Notes:

- **`async fn poll`**: Java's `poll()` is sync because it calls
  `client.poll(timeout, now)` which is sync-blocking on a Java thread.
  In Rust, `KafkaClient::poll` is `async` (already established in
  `src/kafka_client.rs:118`). So `NetworkClientDelegate::poll` must
  also be `async`.
- **`unsent_requests: VecDeque<UnsentRequest>`** — Java uses
  `ArrayDeque`. `VecDeque` is the direct analog.
- **`metadata_error: Option<KafkaError>`** vs the `error queue` path:
  the `notify_metadata_errors_via_error_queue` flag (default `true` for
  AsyncKafkaConsumer per `RequestManagers` supplier line 156) sends
  errors to `BackgroundEventHandler`; legacy/sync path stores them
  locally. Translate both paths.
- **`maybeThrowAuthFailure`** returns `void` and throws in Java. Rust
  returns `Result<(), KafkaError>`.
- **`FutureCompletionHandler`** internals: mirror Phase 5's
  `CompletableEventHandle<T>` shape (Arc + Mutex<Option<Sender>>).
  Java `CompletableFuture` is closest to `oneshot::Receiver`-on-the-app-side.
  Don't reinvent — match the precedent.
- **`Closeable.close()`**: returns `Result<(), KafkaError>` (Java throws
  `IOException`).
- **Generic over `K: KafkaClient`**: lets tests use a mock client
  cheaply. The bg task uses a concrete `K = NetworkClient<...>`.
  Alternative considered: `Box<dyn KafkaClient>` — but the existing
  trait at `src/kafka_client.rs:33-118` uses `impl Future` in its
  signatures, making it non-object-safe. Generic dispatch is forced;
  document this.

```rust
use crate::consumer::internals::request_state::RequestState;
use crate::consumer::internals::network_client_delegate::{PollResult, UnsentRequest};

pub(crate) struct CoordinatorRequestManager {

impl CoordinatorRequestManager {

    pub(crate) fn coordinator(&self) -> Option<&Node>;
    pub(crate) fn fatal_error(&self) -> Option<&KafkaError>;

    /// Called by the bg task when a FindCoordinator response arrives.
    pub(crate) fn on_response(
        &mut self,
        current_time_ms: i64,
        response: FindCoordinatorResponse,
    );

    fn make_find_coordinator_request(&mut self, current_time_ms: i64) -> UnsentRequest;
    fn handle_successful_response(&mut self, current_time_ms: i64, data: FindCoordinatorResponseData);
    fn handle_failed_response(&mut self, current_time_ms: i64, error: KafkaError);
    fn mark_coordinator_unknown(&mut self, cause: &str, current_time_ms: i64);
}

impl RequestManager for CoordinatorRequestManager {
    fn poll(&mut self, current_time_ms: i64) -> PollResult;
    fn signal_close(&mut self) { self.closing = true; }
    // poll_on_close, maximum_time_to_wait use defaults
}
```

Notes:

- **`Option<Node>`** instead of Java's nullable `Node coordinator`.
- **`Option<KafkaError>` for `fatal_error`** instead of `Optional<Throwable>`.
- The Java `markCoordinatorUnknown(cause)` overloads (with/without
  `currentTimeMs`) — translate as one method taking explicit time.
- **Per-error handling**: Java's `onResponse` dispatches on
  `Errors` (the response error code) — `COORDINATOR_LOAD_IN_PROGRESS`,
  `COORDINATOR_NOT_AVAILABLE`, `NOT_COORDINATOR`, `GROUP_AUTHORIZATION_FAILED`,
  etc. Translate the same dispatch; ensure each variant exists on Rust's
  `Errors` enum.
- **`onResponse`** is called from the bg task after the network layer
  resolves the `oneshot::Receiver`. In Phase 6 the wiring is just "the
  manager owns the resolve" — the bg task (Phase 10) registers
  `whenComplete` on the `UnsentRequest` future to call `on_response`.

### `FindCoordinatorRequest` / `FindCoordinatorResponse` (`src/common/requests/`)

Mirror the `MetadataRequest` / `MetadataResponse` precedent
(`src/common/requests/metadata_request.rs:510 LOC`, `metadata_response.rs:643 LOC`).

`FindCoordinatorRequest`: wraps `FindCoordinatorRequestData`
(auto-generated), provides a `Builder` that picks the right version
based on the broker's `ApiVersions`. Public.

`FindCoordinatorResponse`: wraps `FindCoordinatorResponseData`, exposes
`coordinator()` (for v3-) / `coordinators()` (for v4+) helpers and
`errors()`. Public.

Keep both minimal — only the methods `CoordinatorRequestManager` calls.
Add additional methods on-demand in later phases.
