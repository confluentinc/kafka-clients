# Milestone 12 (producer-metrics) — Phase P1: Registry ownership + KafkaProducerMetrics + Producer::metrics()

Actor N=4. Branch `producer-metrics`.

## Goal

Establish the producer's metrics foundation, mirroring the consumer-metrics
Milestone-9-metrics work (Phase M1/M7 precedent):

1. `KafkaProducer` owns an `Arc<Metrics>` registry built from the producer
   config (`metrics.num.samples`, `metrics.sample.window.ms`,
   `metrics.recording.level`, `client-id` tag), mirroring the Java
   `KafkaProducer` constructor (`KafkaProducer.java:357-368`).
2. `KafkaProducerMetrics` (`producer-metrics` group, 8 latency sensors) is
   translated in full from `KafkaProducerMetrics.java`, with real record call
   sites for `flush-time-ns-total` (in `flush()`) and
   `metadata-wait-time-ns-total` (in `wait_on_metadata`). The 6 txn sensors are
   registered but have no call sites (no transactional API yet — awaiting a
   later milestone), exactly as Java registers all 8 and never records
   `txn-prepare`.
3. `Producer::metrics()` on the trait (sync `fn`, Java non-blocking) returning
   `HashMap<MetricName, Arc<KafkaMetric>>`, implemented on both
   `KafkaProducer` (snapshot of its registry) and `MockProducer` (its
   `mock_metrics` map). `MockProducer::set_mock_metrics` inherent test helper.

## Design decisions

- **ns time source**: use `crate::common::metrics::time::SystemTime` (monotonic
  `Instant`-backed `nanoseconds()`, the same source the consumer uses for
  `commit-sync-time-ns-total`). The producer currently holds only a millis
  `time_provider` closure; rather than replumb a `time` field through every
  constructor (bigger, riskier change out of P1 scope), the two per-call
  recording sites read `SystemTime.nanoseconds()` directly. Value-neutral:
  both are `System.nanoTime()` analogs. No producer test in scope drives these
  with a mock clock (the `KafkaProducerMetricsTest` exercises the metrics class
  directly).
- **metadata-wait placement**: recorded inside `wait_on_metadata` around the
  refresh loop, after the early cached-metadata return (Java records at
  `:1154`, after the `nowNanos = time.nanoseconds()` at `:1120`, which is
  itself after the early return). So the cached fast-path does NOT record, and
  a timeout (error return inside the loop) does NOT record — Java-faithful.
  All callers (doSend + partitions_for) record via the shared helper, matching
  Java.
- **metric tags**: `Metrics::metric_name` already merges `config.tags()`, so
  `KafkaProducerMetrics` passes an empty tag map (consumer `KafkaConsumerMetrics`
  precedent), yielding the same effective `client-id` tag Java attaches.
- **reporters / JMX**: N/A in Rust (consumer Phase M7 precedent — the registry
  is reporter-less but functional). `metric.reporters` config-class reflection
  and client-id auto-generation do not exist in the Rust producer surface.

### Skipped Java tests (with justification)

- `KafkaProducerTest.testMetricsReporterAutoGeneratedClientId` — depends on
  `metric.reporters` config-class instantiation (`MockMetricsReporter`) and
  client-id auto-generation, neither of which exists in the Rust
  `ProducerConfig` (no reporter reflection; `client.id` defaults to empty
  string, no auto-gen). Precondition absent → not translatable.
- `testSubscribingCustomMetrics...` (KIP-714 telemetry, ~2710-2789) — client
  telemetry / broker-push metrics subscription does not exist in Rust.

## Self-review notes

- **DoD #10 (hot-path allocation audit)**: the metric recording added in this
  phase is per-API-call — `flush()` and `wait_on_metadata` (once per send that
  needs a metadata refresh, and per `partitions_for`), NOT per-record on the
  send/batch-drain path. `metrics()` is a cold monitoring snapshot. No
  per-record allocation is introduced. The Sender/BufferPool/RecordAccumulator
  sensors (which WOULD touch the batch path) are explicitly deferred to later
  phases.
- **DoD #11**: N/A (producer, not consumer trait). `metrics()` stays sync on
  the trait (Java non-blocking).
