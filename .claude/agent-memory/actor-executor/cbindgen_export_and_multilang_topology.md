Two non-obvious facts nailed down while wiring `send_offsets_to_transaction`
through the multilanguage harness (PR #168 work item #2).

## cbindgen `[export].include` does NOT gate `#[no_mangle]` functions

`cbindgen.toml`'s `[export] include = [...]` lists ONLY opaque `_t` types and
`_callback_t`/`_destroy_t` typedefs — zero plain functions. Every one of the
~40 `#[unsafe(no_mangle)] pub extern "C"` FFI functions (the whole
`kafka_consumer_ConsumerGroupMetadata_*` accessor family included) exports into
`target/include/confluent_kafka.h` WITHOUT being in that list. Verified by a
clean regen (delete the header, `touch src/ffi/consumer.rs` to trip build.rs's
`rerun-if-changed=src/`, `cargo build --features ffi`): a brand-new
`#[no_mangle]` fn appears in the header with `cbindgen.toml` untouched.

So a task instruction to "add function X to the cbindgen include list" is
inert AND inconsistent — the list is for force-exporting opaque types, not
functions. Achieve the goal (fn in header, confirmed) and don't add the entry.
The header lives under `target/` (gitignored), regenerated by `build.rs` only
when the `ffi` feature is on. See [[ffi-verify-env-milestone11-cffi]].

## Multilanguage harness topology

- **Single source of truth proto:** `multilanguage-test-server/proto/*.proto`.
  `consumer_service.proto` `import`s `producer_service.proto` (so producer proto
  can't reference consumer types — a cycle). All three servers regenerate from
  the ONE copy: the Rust client via `multilanguage-test-server/build.rs`
  (tonic/prost, vendored protoc), and each Dockerfile
  (`bindings/{c,python}/Dockerfile.grpc*`) `COPY`s that proto + `target/include/
  confluent_kafka.h` into its build context. There is no second proto copy and
  the C++ CMake `PROTO_DIR` default is overwritten by the Dockerfile staging.
- **C++ gRPC server (`bindings/c/grpc_server/server.cc`) is Docker-only.** It
  needs protobuf + grpc++ + grpc_cpp_plugin, none present on this macOS host,
  and `make build-c` does NOT build it (that's `bindings/c/`, the unit tests;
  the server is `build-grpc-images-c`, Docker). So server.cc changes are
  correct-by-construction only — mirror the existing handlers exactly.
- **`producer_transactions_test.rs` compiles in the auto-discovered `integration`
  test target** (`tests/integration/main.rs`, NOT the `producer` `[[test]]`).
  Proof-of-compile: `cargo test --features multilanguage-tests --test
  integration --no-run` (client + `multilanguage_test!` expansion) and
  `--features integration-tests --test integration --no-run` (rust_only_fallback).
- **Producer txn RPCs on the wire:** the C gRPC server exposes init/begin/commit/
  abort + now send_offsets; the **Python** gRPC servers have NO txn handlers, so
  every transactional scenario's `__grpc_python*` target fails UNIMPLEMENTED —
  known-deferred to PR #175, not a regression. See [[multilanguage-suite-on-macos]],
  [[macos-verify-docker-multilang-blocked]].
