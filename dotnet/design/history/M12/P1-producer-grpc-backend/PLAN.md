## 1 · Objective & context

The multilanguage conformance harness already covers the producer for `rust`,
`python`, `python_async`, and `c`. The **one missing backend is .NET**: the
`.NET grpc-server` compiles `producer_service.proto` **messages-only** and
implements **`ConsumerService` only** (M8/P1 sync + M8/P2 async). This phase adds
the **`ProducerService` implementation** so the same producer conformance
scenarios also run against the .NET binding's **generic producer** —
`KafkaProducer<byte[],byte[]>` (sync) and `AsyncKafkaProducer<byte[],byte[]>`
(async), plus their `Mock*` twins for the empty-config smoke path.

Because the producer core is now **generic-only** (M11/P5 removed the non-generic
bytes types), the server bridges through `<byte[],byte[]>` + `Serdes.ByteArray` —
which **exercises the shipped generic serialize path end-to-end** over the wire.

Harness architecture: `design/history/MILESTONE-6/DESIGN-multilanguage-tests.md`.
Structural template: `design/history/M8/P1-sync-consumer-grpc-backend/PLAN.md` +
`M8/P2-async-consumer-grpc-backend/PLAN.md`.

## 3 · Design shape — ONE server per flavor hosts BOTH services (Python-parity)

**Recommendation: reuse the two existing dotnet images; each hosts BOTH
`ProducerService` and `ConsumerService`, flavor-selected by the existing
`CONSUMER_FLAVOR` env** — i.e. converge on the **Python** shape (`grpc_server.py`
registers both services in one server). Concretely:

| Image | `CONSUMER_FLAVOR` | Hosts |
|---|---|---|
| `dotnet-grpc-server:dev` | `sync` (baked, `Dockerfile.grpc:86`) | `ConsumerServiceImpl` **+ new `ProducerServiceImpl`** |
| `dotnet-async-grpc-server:dev` | `async` (`Dockerfile.grpc.async`) | `AsyncConsumerServiceImpl` **+ new `AsyncProducerServiceImpl`** |

The producer `__grpc_dotnet` arm → `BackendKind::Dotnet` (sync image → sync
producer); `__grpc_dotnet_async` → `BackendKind::DotnetAsync` (async image → async
producer). This mirrors the existing consumer arms exactly.

**Why reuse (not new producer-only images):**
1. **Python precedent / sibling consistency** (`bindings/CLAUDE.md §2` — mirror
   the siblings): Python has always served both services from one server per
   flavor. M8's consumer-*only* .NET split existed only because the .NET producer
   didn't exist yet; now that it does, converging on "one server, both services"
   is the natural, consistent shape — and it means **every `BackendKind` still
   maps to one image**.
2. **Near-zero new infrastructure:** no new image, no new `BackendKind`, no
   Dockerfile edit, no Makefile target, no `.semaphore/` change (§2.8). The M8
   consumer work already built all of it.

**Isolation trade-off (state it):** the M8/P2 maintainer chose two *consumer*
images for "true isolation." Reusing them means the proto flip + a Program.cs
registration now also affect the shipped consumer images (they gain a second
service on the same Kestrel host). The change is **purely additive** (ConsumerService
codegen + servicers are untouched), so the risk is low — but the **DoD mandates
re-running the consumer `__grpc_dotnet[_async]` arms to prove no regression**
(§8). *Alternative if the maintainer wants strict isolation:* build separate
`dotnet-producer-grpc-server[-async]` images with their own `BackendKind` +
Dockerfiles + Makefile targets (the M8 maximal-isolation path — much more
infra, diverges from the Python one-server shape). **Not recommended; flagged for
the record.** → **[FLAG — one-image-per-flavor vs separate producer images]**

**`Program.cs` registration (the one wiring edit):** keep the existing
`CONSUMER_FLAVOR` selector (§2.8); in each branch, **also** register the matching
producer servicer:
- `async` branch: `AddSingleton<AsyncConsumerServiceImpl>()` +
  `AddSingleton<AsyncProducerServiceImpl>()`, then `MapGrpcService<…>()` for both.
- else (sync): `ConsumerServiceImpl` + `ProducerServiceImpl`, both mapped.
Servicers **must** be singletons (they own the id→producer map, same rationale as
the consumer, `Program.cs:59-65`). Keep the env name `CONSUMER_FLAVOR` to avoid
Dockerfile churn (a rename to `SERVER_FLAVOR` is cosmetic and would touch both
Dockerfiles — not worth it; note only).

## 4 · Sync vs async servicer scope — one phase

**[FLAG — one phase or two].** The consumer split sync/async across M8/P1 + M8/P2
because each needed **its own new image + Docker + Make + CI** built from scratch.
For the producer, **all that infra already exists and is shared** (§2.8, §3), the
surface is small (6 RPCs), and the two servicers are near-identical (like the two
consumer servicers). **Recommendation: ONE phase (M12/P1) delivering both**
`ProducerServiceImpl` (sync) and `AsyncProducerServiceImpl` (async), each behind
the existing flavor selector, exercised by the two macro arms. Confirm.

**RPC → member mapping (both flavors):**

| RPC | Sync servicer (`IProducer`) | Async servicer (`IAsyncProducer`) |
|---|---|---|
| `CreateProducer` | empty/all-blank config → `MockProducer<byte[],byte[]>(Serdes.ByteArray, Serdes.ByteArray)`; else `KafkaProducer<byte[],byte[]>(config, Serdes.ByteArray, Serdes.ByteArray)` | `AsyncMockProducer<…>` / `AsyncKafkaProducer<…>` (same ctors) |
| `Send` | `RecordMetadata Send(record)` — **blocks on the handler thread** (Java `send().get()`; the sync-consumer-poll precedent) | `await Send(record)` |
| `Flush` | `Flush()` | `await Flush()` |
| `PartitionsFor` | `PartitionsFor(topic)` | `await PartitionsFor(topic)` |
| `Close` | `Close()`; idempotent on unknown id (Python parity) | `await Close()`; idempotent |
| `CloseTimeout` | **ignore `timeout_ms` → `Close()`** (§5 [FLAG]) | **ignore `timeout_ms` → `await Close()`** |

**No per-id gate (divergence from the consumer).** The consumer servicer takes a
per-id `lock`/`SemaphoreSlim` because the native consumer is single-owner / not
thread-safe. The **producer is thread-safe** — the core's internal `Mutex`
serializes concurrent `Send` (`ffi-marshalling.md §A1`: "concurrent `Send` is
safe — don't add your own lock"). So the producer servicer needs **only a
thread-safe `ConcurrentDictionary<ulong, …>` id→producer map** (+ `Interlocked`
id counter) for `CreateProducer`/`Close` races — **no per-op gate.** State this in
the self-review.

## 5 · [FLAG] `CloseTimeout` mapping

The proto declares `CloseTimeout(timeout_ms)` but the .NET producer has **no timed
close** at any layer (`Producer_close` takes no timeout; neither `IProducer` nor
`IAsyncProducer` has a `Close(TimeSpan)`/timed overload — §2.1). Verified
expectations of the two consumers of this RPC:
- **Python server** (`grpc_server.py:189-192`): ignores `timeout_ms`, delegates to
  `Close()` — a best-effort, faithful mapping.
- **Rust client** (`multilanguage_producer.rs:165-177`): sends
  `CloseTimeoutRequest{timeout_ms}` and only checks the returned error/ok. **No
  `multilanguage_test!` scenario calls `close_timeout`** (§2.9) — so the mapping
  is behaviorally invisible to the conformance suite.

**Recommendation: mirror Python — `CloseTimeout` ignores `timeout_ms` and delegates
to the plain `Close()`** (sync) / `await Close()` (async). This is (a) a faithful
port of the Python server, (b) consistent with M8/P2's async-consumer
`Close`-ignores-`timeout_ms` precedent, and (c) safe because no scenario exercises
it. Document it as a deliberate, behaviorally-invisible divergence. Confirm.
