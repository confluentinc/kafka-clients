# Cloud consumer benchmarks — 2026-06-16 (USW2, **Intel**)

Rust vs librdkafka vs Java (kafka-clients) consumer e2e-latency / CPU / RSS, against real
Confluent Cloud over SASL_SSL, in-region (us-west-2). Companion to the us-east-1 / **Graviton**
set in `../2026-06-15/`; this set is the **Intel (m8i)** environment.

## Graphs (latency over time, per-interval, 30-min window)
- **`workload1_tuned_latency_over_time.png`** — throughput-tuned config.
- **`workload2_default_latency_over_time.png`** — latency-tuned / default config.
- Each PNG = two stacked panels (p50 median, p99 tail), all three clients overlaid; x = minutes
  into the 30-min measurement window. Generated by `plot_latency_graphs.py` from the per-interval
  log lines.

## Start here for numbers
- **`summary.csv`** — one row per run, aggregate metrics, same columns as `../2026-06-15/summary.csv`.
  `throughput_msg_s` is the accurate throughput; derive MiB/s as `msg/s * msg_bytes / 1048576`
  (do **not** trust harness MiB/s — see caveats).

## Environment
- Cluster `pkc-devcg13mnr` (12 CKU Dedicated), **us-west-2**, single-zone `usw2-az4`.
- Topic `cmp-bench-200p` (200 partitions), RF3, 5-min retention.
- Consumer host: EC2 **m8i.4xlarge (Intel x86_64, 16 vCPU)**, AL2023, co-located in `usw2-az4` (same-az).
- Rust = release build **including the TLS-reset fix** (commit `d5b0e50`, branch `consumer-impl`) —
  required to complete the latency-tuned 30-min run without aborting (see caveats).
  librdkafka = source build (`librdkafka_e2e.c`). Java = `JavaE2E.java` on kafka-clients 4.0.0.

## Two workloads (same 200p / 2 KB / ~300 MB/s / 30 min / same-az, only fetch+poll config differs)
- **workload1 — throughput-tuned:** `fetch.min.bytes=4 MiB`, `max.partition.fetch.bytes=4 MiB`,
  batch/`max.poll.records` = 2000 (librdkafka consume-batch) / 2500 (Rust, Java).
- **workload2 — latency-tuned (default):** `fetch.min.bytes=1`, default `max.partition.fetch.bytes` (1 MiB),
  `max.poll.records=500` (Rust, Java), **librdkafka via single-message `rd_kafka_consumer_poll()`** (`--single-poll`).
- `check.crcs=false` on **all** clients in **both** workloads (aligned). NB: this differs from the
  `../2026-06-15/` default group, which used each client's *default* CRC setting.
- `group.protocol=consumer` (KIP-848), `auto.offset.reset=latest`. Producer = `kafka-producer-perf-test` (acks=1, 4 producers).

## Headline

**workload1 — throughput-tuned** (4 MiB fetch.min floors everyone near ~300 ms):

| client | p50 | p99 | p99.9 | RSS | CPU |
|---|---|---|---|---|---|
| librdkafka | 254 | 525 | 551 | 324 MB | 38% |
| Java | 283 | 568 | 595 | 2874 MB | 55% |
| Rust | 307 | 636 | 832 | **118 MB** | 42% |

**workload2 — latency-tuned (default)** (fetch.min=1 removes the floor):

| client | p50 | p99 | p99.9 | RSS | CPU |
|---|---|---|---|---|---|
| Java | 4 | 19 | 37 | 1885 MB | 118% |
| librdkafka (single-poll) | 4 | 21 | 88 | 144 MB | 132% |
| Rust | 5 | 40 | 111 | **32 MB** | **108%** |

- Throughput tied at ~150k msg/s (~293 MiB/s) in every run.
- **Latency:** throughput-tuned, the 4 MiB fetch wait dominates and the three sit in tight parallel
  bands (librdkafka lowest, Rust highest, ~80 ms spread at p50). Latency-tuned, medians collapse to
  ~4–5 ms for all; p99 ~20 ms for Java/librdkafka, ~40 ms aggregate for Rust.
- **Rust latency-tuned converges over time:** the p99 time-series (workload2 PNG) shows Rust elevated
  and noisy (~40–100 ms) for the first ~13 min, then a regime change to ~20–30 ms for the back half —
  landing on top of Java/librdkafka. The aggregate p99 of 40 ms is pulled up by the settling period;
  the **converged steady-state p99 is ~20–25 ms**. Even the 40M-record warmup did not fully exclude
  Rust's settle-to-live-edge ramp (near-zero throughput headroom under default config).
- **Memory:** Rust ≪ librdkafka ≪ Java in both workloads (e.g. latency-tuned 32 / 144 / 1885 MB).
- **CPU (latency-tuned):** Rust lowest (108%), < Java (118%) < librdkafka single-poll (132%).

## Caveats (important for honest reading)
- **MiB/s artifact:** Rust & librdkafka harnesses compute bytes from a 1 KB assumption, so they
  report ~146 MiB/s for these 2 KB runs; the true rate is ~293 MiB/s (Java reports it correctly).
  `summary.csv` records `msg/s` only.
- **CPU source asymmetry:** Rust & Java CPU = external `/proc` sampler (the in-harness sampler reads
  0% — visible as `cpu=0.0%` in those interval lines); librdkafka CPU = its own self-report. Comparable
  in magnitude, not identically sourced.
- **librdkafka `max` outliers** (31478 / 31937 ms in `summary.csv`) are a single ~31 s
  bootstrap-connect stall at run start; p99.9 (≤88 ms) is the real steady-state tail. These show as
  a clipped/annotated off-scale point on the p99 panels.
- **Rust required the TLS-reset fix to run clean:** before commit `d5b0e50`, a transient broker
  TLS-handshake reset (broker was mid-roll) was mis-classified as a fatal auth failure and aborted
  the consumer; 3 prior latency-tuned attempts died at connection setup. Root cause + fix:
  `design/current/consumer-tls-reset-fatal-rootcause.md`. The fix was unit-tested and the clean
  30-min run survived; it was not directly exercised by a live reset (broker had stabilized).
- **Rust latency-tuned aggregate includes the ~13-min settling ramp** — see "converges over time" above.
- Java RSS = JVM heap (no `-Xmx`); 1885 MB here, far below the throughput-tuned 2874 MB (smaller
  default 1 MB fetch buffers → less allocation pressure).

## 36-partition run group (`default-36p-2kb-300mbs`, added 2026-06-17)

Same latency-tuned/default config as workload2 (`fetch.min.bytes=1`, default `max.partition.fetch.bytes`,
`max.poll.records=500`, librdkafka `--single-poll`, `check.crcs=false` aligned, 2 KB, ~300 MB/s, 30 min,
same-az), but on a **36-partition topic** (`cmp-bench-36p`) instead of 200p, with a **~4-min warmup
(36M records)** for all three clients. Graph: **`workload3_36p_default_latency_over_time.png`**.
Raw data in `same-az-36p/`. Rust binary includes the TLS-reset fix (`d5b0e50`).

| client | p50 | p90 | p99 | p99.9 | max | avg | RSS | CPU |
|---|---|---|---|---|---|---|---|---|
| librdkafka (single-poll) | 4 | 6 | 19 | 43 | 222 | 4.39 | 63 MB | 110.7% |
| Java | 4 | 7 | 21 | 51 | 326 | 4.86 | 846 MB | 115.0% |
| Rust | 6 | 21 | **98** | **270** | 663 | 11.22 | **39 MB** | **89.8%** |

**Findings:**
- Throughput tied at 150k msg/s (~293 MiB/s); all three ran clean (0 aborts).
- **Rust tail is notably fatter at 36p than at 200p** (p99 98 vs 40, p99.9 270 vs 111), while
  **librdkafka and Java stay tight (~20 ms p99) at both partition counts**. So the regression is
  partition-count-sensitive and **Rust-specific** — not environmental. The p99 time-series shows
  Rust oscillating ~45–290 ms the whole run (no convergence), vs librdkafka/Java pinned at ~15–30 ms.
  Likely cause: with 36 partitions each carrying ~8 MB/s (vs ~1.5 at 200p), fetch responses are
  larger/burstier and a single partition's leader/fetch hiccup hits proportionally more messages →
  fatter tail. Worth investigating in the Rust fetch path (per-partition fetch fairness / how a
  large single-partition fetch interleaves with poll delivery).
- **Both Rust and librdkafka use less CPU/RSS at 36p than 200p** (fewer partitions → less fetch/poll
  bookkeeping): Rust 90% / 39 MB (vs 108% / 32 MB), librdkafka 111% / 63 MB (vs 132% / 144 MB).
  Rust remains the lowest CPU and lowest RSS of the three.
- **Fix validated against a live reset:** during Rust's join, the flaky broker `54.213.232.68` reset
  the TLS handshake **19 times**; the fixed client logged each as a retriable disconnect (WARN
  "terminated during authentication … transient network issue"), reconnected, and completed the full
  30 min — the exact scenario that aborted 3 pre-fix runs. Direct real-world confirmation of `d5b0e50`.

`same-az-36p/` files: `lr36d_rust.log` + `lr36d_rust_metrics.jsonl` + `lr36d_rust_cpu.csv` (Rust);
`lr36d_repo.log` + `lr36d_repo_metrics.jsonl` (librdkafka single-poll); `lr36d_java.log` +
`lr36d_java_intervals.csv` + `lr36d_java_cpu.csv` (Java); `longrun30_def36_drive.sh` (driver).
