# Confluent Kafka Rust

Rust Kafka client implementation translated from the Java Kafka client (client only) with AI assistance. Keeps the same architecture, namespace, and names, adapted to Rust naming conventions.

Any change to this prompt is to be avoided by automatic agents.
Suggestions for changes are possible through the process highlighted in [agent-roles.md](.claude/rules/agent-roles.md).

**The public API in Rust is stable since version 1.0.0, C FFI is experimental and may change**

## Translation Rules
1. **Classes outside the repository**: when you find classes outside of the Kafka repository:
    1. In case code with same behaviour and equal or better performance is found in Rust standard library use that one.
    2. In case code with same behaviour and equal or better performance is found in a very popular Rust crate ask if possible to include the new dependency and then use it.
    3. As last resort implement it from scratch by translating it from latest stable OpenJDK source code, ask before doing it and
       keep the same licence: GPL + Classpath Exception (important).
2. **Naming Conventions**:
   - Java package `org.apache.kafka.message` → Rust module `message`
   - Java package `org.apache.kafka.clients.consumer` → Rust module `consumer`. `clients` MUST NOT appear in folder name or Rust module.
   - Java class names (PascalCase) → Rust struct/enum names (PascalCase)
   - Java method names (camelCase) → Rust function names (snake_case)
   - Java const CommonClientConfigs.RETRY_BACKOFF_EXP_BASE → Rust `CommonClientConfigs::RETRY_BACKOFF_EXP_BASE`
   - Each Java class MUST be in its own file, with all its nested classes and enums, but imports for the struct MUST use the parent module re-export, not the file module path. For example, `ProducerRecord` is defined in `producer_record.rs` but imported ONLY as
   `use crate::producer::ProducerRecord;` not `use crate::producer::producer_record::ProducerRecord;`. Only when there are nested classes, or nested enums, they can be available through the submodule, for example: `use crate::producer::producer_record::NestedStaticClassInJava`.
   - Constant MUST be exported only by the struct defining them. E.g.:
     `GROUP_METADATA_TOPIC_NAME` is accessible through
     `::common::internals::Topic::GROUP_METADATA_TOPIC_NAME`
   - Static functions MUST be exported through only by the struct defining them. E.g:
     `to_byte_buffer_accessor` is accessible through `::common::protocol::MessageUtil::to_byte_buffer_accessor`
   - Classes whose package contains `internal` MUST NOT be public
   - Classes whose package contains the disclamer "This module is not a supported API" MUST NOT be public
   - Classes that ARE NOT annotated as `@InterfaceAudience.Public` since Apache Kafka 4.4 MUST NOT be public
   - Java `Exception` → Rust `Error` (e.g. `TopicAuthorizationException` → `TopicAuthorizationError`)
     - they're all enums of Error
     - each error has its own file
     - they implement `ErrorHierarchy`
     - errors in packages different from `common` should have a prefix corresponding to their package to avoid conflicts like `ConsumerOffsetOutOfRange` for the `OffsetOutOfRange` error in `consumer` module.
     Java errors should all have the `Local` prefix, independently of the subpackage.
     - the word "exception" MUST never appear in Rust code, except in comments about the Java client.
   - Java `throws` / `throw` → Rust `return Err(...)` (e.g. `maybeThrowAnyException` → `maybe_return_any_error`)
   - Preserve original architecture and logical structure
   - Java `long` fields used in comparison (e.g. `Uuid`, producer IDs, offsets) must use `i64` in Rust, not `u64` — signed vs unsigned comparison produces different ordering for values with the high bit set
   - Nullable `string`/`bytes` fields in the Kafka message specs without an explicit `"default": "null"` must default to empty (`Some(String::new())` / `Some(Vec::new())`), not `None`. Only use `None` when the spec explicitly sets `"default": "null"`
   - Java interfaces become traits in Rust, except those translated to std traits or to functions, default method implementation on an interface become a default trait function implementation in Rust
    If a Java class implements multiple interfaces and that have a function in common with same signature, implement the function on the struct and delegate to it in both implementations.
    Constants that should be associated to the trait are exported through the module containing the trait, also nested structs, enums or static methods. If there's an inner interface that is nested and it needs static methods, they are free functions of the outer class's module named `<module>::<Inner>_<fn>` (`<fn>` being `static_method`, `new` or `with_<parameters>`), e.g. `kafka_future::BaseFunction_new` for Java's `KafkaFuture.BaseFunction`
   - The configuration MUST NOT take classes as values or "class" in the property name. A class is Java terminology and we don't use reflection here, every time there's a property with a class the corresponding value needs to be set in the properties struct through a setter and the value must be a trait.
   - When generating wire protocol code, always use per-field `flexibleVersions` overrides via `field_flexible_versions(field, msg_flex)` in the generator — never the raw message-level value. Some fields (e.g. `ClientId` in `RequestHeader`) override to `"none"` and must always use length-prefixed encoding
   - Overloaded methods: make sure there's:
     - a method with same name (after translation) that has the intersection of parameters from all overloaded methods, if that method exists in Java.
     - additional methods with <base_name>_with_<param1_name>_<param2_name> (ALWAYS using the "with" keyword in between).
     - when parameters have the same name and different type,
     **in case if the final names would collide**, use the Rust parameter type name instead of the parameter name to discriminate, only for the parameters with same name while continue using the parameter name for rest of parameters.
     In case the difference is **only** Optional use Rust's `Option` and a single method name
     - constructor translation from Java always uses `new`, not `from`. If there are parameters use `.with_<a>_<b>_<c>(a,b,c)`, not `.new_with_<a>_<b>_<c>(a,b,c)`
     - a static factory method sharing its name with an instance method keeps the name on the instance one and becomes `new_with_<parameters>` if the corresponding `with_<parameters>` is also taken by an instance method: `CloseOptions.timeout(Duration)` beside the getter `timeout()` and `withTimeout()` -> `CloseOptions::new_with_timeout`
     - a static NON-factory method sharing its name with an instance method becomes `do_<method_name>(_with_<parameters>)?`
     - if there a static method `from_<something>` that is translated from Java and a corresponding constructor `with_<something>` with same final signature, keep only the method `with_<something>`
     - if there are more than three parameters in the method name, add a dedicated non-exhaustive `Options` struct that is the only parameter to the method name with `_with_options` suffix. Also in case Java API makes some parameters of the intersection set optional in a later version, add this method with only the `options` parameter
     The `Options` struct must have a `OptionsBuilder` with a `new` parameterless constructor. All optional parameters have fluent setters in the builder. Finally the user calls `build` before passing the `Options` struct, there the different sets of mandatory parameters are validated and a `IllegalArgumentError` error is returned in case they weren't passed. Semantic validation is left to the method where the `Options` is passed.
     - getters and setters with same name: use `<field_name>` for the getter and `set_<field_name>` for the setter. If a method is a setter,
       use `set_<field_name>` even if there's no corresponding getter
     - examples:
       - `fooBar(a, b)`, `fooBar(a, c)` -> `foo_bar_with_b(a, b)`, `foo_bar_with_c(a, c)`
       - `fooBaz(a)`, `fooBaz(a, c)` -> `foo_baz(a)`, `foo_baz_with_c(a, c)`
       - `fooBar(a, b)`, `fooBar(a, c)`, `fooBar(a, b, c, d)`  -> `foo_bar_with_b(a, b)`, `foo_bar_with_c(a, c)`, `foo_bar_with_b_c_d(a, b, c, d)`
        - later: `foo_bar_with_b(a, b, c, d, e)` -> `foo_bar_with_options(options)`, `FooBarOptionsBuilder::new().set_a(a).build()`
        - later: `fooBar(b)`, `fooBar(c)` -> `FooBarOptionsBuilder::new().build()`
3. **Forward compatibility**
  The Rust client need to stay always forward compatible with any change that is done to the Java public API. Each type of change that doesn't require a major version in Java MUST not require a major version in Rust, that should be possible by maintaining the same design an not adopting ad-hoc solutions for each adaptation. Here are some of the rules:
    - Rust public enums and struct MUST be "#[non_exhaustive]" in case new values are added to Java ones
    - There should be no public field in public structures: getter, setters or builders are used depending on what's also used in Java client
    - Traits must be dyn-compatible: in Java we can put objects of different types in collections with an interface as generic argument. Exception are made for performance oriented trait such as the `Producer` but they must have a corresponding dyn trait such as `DynProducer` so they pay the cost only when needed
    - a public FunctionalInterface in Java MUST be translated to a trait, as it can gain overloaded methods. The trait module should have a static `new` and one `with_<params>` per default-method overload, named by the overloaded method rules, each taking a function with that shape and returning an implementation of the given trait that calls that function (`cargo xtask lint-custom`, `check-functional-interface-trait`)
    - classes that are translated from Java MUST have the same name as Java, considering the translation rules, except when there are other rules changing their name
    - methods that are translated from Java methods must not be public if they're not public in Java implementation
    - package names must be compatible with Java: in case two classes with same name are added to the Java clients, they must not collide in the same Rust package
    - deprecated API MUST NOT be translated since the first major version of the client. Ensure this is not affecting the ability to implement later some large features that are not implemented at the moment such as the classic consumer group, because of changes to public traits
    - NEVER EVER accept or return a fixed size array from a public interface
    - Every Error should have the corresponding predicate. Users must use a predicate instead of enum matching to make sure that when we match an error we also match all future subclasses of it in Java client
    - A public enum variant carries data only as a single wrapped type this crate defines (a struct, an enum, a trait object, possibly behind `Box`/`Arc`/`Rc`), never as inline fields or a `std` / foreign type, so the wrapped type keeps its own forward compatibility (`cargo xtask lint-custom`, `check-no-data-carrying-enum-variants`)
    - A public enum translates a Java `enum` or a Java class hierarchy (one variant per subclass of an interface, an abstract class or an extended class), never a plain class: a class nothing extends becomes a struct with private fields (`check-enum-translation`)
    - No public method is a native `async fn`: it is declared `fn name(..) -> impl Future<Output = T> + Send`, so `Send` is part of the signature rather than inferred from the body; an `#[async_trait]` method is exempt, its boxed future already being `Send` (`check-send-future`). A trait with such methods has a sealed, dyn-compatible `Dyn<Name>` companion blanket-implemented for it (`check-dyn-compatible`)
    - A `Dyn<Name>` companion declares the same methods as its trait; its blanket impl forwards each to `Name::<method>` and `impl Name for dyn Dyn<Name>` forwards each, defaulted ones included, to `Dyn<Name>::<method>`, the parameters in order (`check-dyn-forwarding`)
    - A public Java `@FunctionalInterface` is a trait, never a closure type, enum or struct, and no public method takes a closure in its place (`check-functional-interface-trait`)
    - Super and auto traits (`cargo xtask lint-custom`, `check-derive-translation`,
      `check-thread-safety-probe`):
      - `Debug`: every public type; a client, result or metrics type hand-writes one printing
        its identifiers, a type holding a secret renders what `Display` renders
      - `Clone`: on a value type (Java overrides `equals()`, an enum, an exception,
        `KafkaFuture`, an `*Options`), since cloning is how Rust aliases what Java shares by
        reference; never on a client (an implementor of `Producer`, `Consumer` or `Admin`) or
        a `*Config` holder
      - `Copy`: never on a struct or a data-carrying enum, except `Uuid` (a 128-bit value by
        definition, as `std`'s `Ipv6Addr`); a fieldless enum translating a Java enum may keep it
      - `PartialEq + Eq` and `Hash`: together, iff Java overrides `equals()` / `hashCode()`,
        directly or in a superclass of the client tree (`AbstractConfig`, `SampledStat`); a
        Java enum or record counts; an `f64` field hand-writes them over `to_bits()`
      - `PartialOrd + Ord`: iff Java implements `Comparable` (`Uuid`) or is an enum
        (`Enum.compareTo` by ordinal, so variants stay in Java declaration order)
      - `Display`: iff Java overrides `toString()`, directly or in a client-tree superclass; a
        Java enum prints the constant's name unless Java overrides it; an exception always has
        it (`Throwable.toString()`); each `Display` has the C `_to_string` export
      - `Send` and `Sync`: every public type is `Send + Sync`, except a type whose Java class
        is not thread-safe and whose methods Rust exposes through `&mut self`: the consumers
        (`KafkaConsumer`, `MockConsumer`, `DynConsumer`, and the share consumers once
        translated). Those carry a `PhantomData<Cell<()>>` field so they are `Send + !Sync`
        whatever their fields are, and `ConsumerHandle` is their `Sync` cross-thread view. A
        lazily computed field uses an atomic or `OnceLock`, never `Cell`/`RefCell`.
        `rust/src/api_promises.rs` asserts the auto traits of every public type
4. **C FFI Conventions**:
    - Always define types ending with '_t' for opaque or public structures
    - The crate's base error type `common::Error` -> `kafka_common_Error_t`. Note this
      is NOT Java's `KafkaException`: the handle wraps the whole flat `Error` enum and it allows to map other exceptions that aren't subclasses of `KafkaException`.
      (§12.3). Java's `KafkaException` maps to the embedded `common::KafkaError`
      struct, which never crosses the boundary on its own.
    - Fallible functions return their value (or `void`) and take a trailing `kafka_common_Error_t **out_err`, never NULL, with `*out_err` NULL on entry; on failure they store an owned error there and return NULL / 0 / -1, so the caller tests `*out_err`, not the value. The caller owns the error and the returned value. Interface method pointers that can fail take the same shape.
    - Language bindings include only `confluent_kafka_bindings.h`: it declares the fallible and `_cb` functions under their own names and every other function only as its `_err` twin, which takes the same trailing `out_err` and stores a caught panic there.
    - the word "exception" MUST never appear in C API and ffi code, except in comments about the Java client.
    - Classes that aren't public in Rust crate MUST NOT have C bindings.
    - Predicates on `Error` keep their Rust name behind the type prefix:
      `is_retriable_error` -> `kafka_common_Error_is_retriable_error`, and likewise every
      hierarchy predicate from §12.4, e.g. `is_kafka_error` ->
      `kafka_common_Error_is_kafka_error`. A predicate added on the Rust side is
      expected on the C side too — C cannot see enum variants, so these are the
      only way a C caller can classify an error beyond its numeric code. The C
      exports are generated from the predicates on `impl Error` by
      `cargo xtask generate-error-predicates` (`check-generated` fails when they
      are stale), never written by hand.
    - Exceptions having additional fields in Java: expose the corresponding C opaque type that can be retrieved from the `kafka_common_Error_t` like `kafka_common_Error_resource_not_found`. In case that error is not that type it returns `NULL`, otherwise the returned pointer can be used to access the additional fields with accessor functions. An example of these types and accessors is `kafka_common_ResourceNotFoundError_t` and `kafka_common_ResourceNotFoundError_resource`.
    - preserve Java namespaces in first part of the function name, skipping `clients`:
      - `org.apache.kafka.clients.producer.KafkaProducer` -> `kafka_producer_KafkaProducer_t`
      - `org.apache.kafka.clients.producer.MockProducer` -> `kafka_producer_MockProducer_t`
    - Do panic on failing type preconditions, for example when passing NULL for a mandatory parameter, and propagate the panic in the fallible functions, always in the calls from the bindings. The returned error and message must match the Java one including `LocalNullPointerError`. Delegate rest of precondition validation to the Rust client. In C headers dedicated to C users instead, the panic aborts instead of always returning an error.
    Never cause a segmentation fault from the C call.
    - Overloaded C function names MUST correspond to the Rust methods plus the corresponding prefix, `Option` struct builder MUST also
      be available to C when it's present in Rust.
    - Enums: as with errors given `base_package_Foo` is the enum name, we MUST have for every value, let's say `a` or `b` the corresponding function:
      `base_package_Foo_a` and `base_package_Foo_b` that return the value or structure corresponding to that enum key. A value without data is returned as a `const base_package_Foo_t *` static singleton, never freed and comparable with `==`; a value carrying data is built by the Java static factory and returned owned, freed with `_destroy`.
      There's also a corresponding C enum `base_package_Foo_e`, with enumerators `base_package_Foo_A` and `base_package_Foo_A`, to use in a switch and `base_package_Foo__enum()` returns the enum value. The enumerator keys MUST always be added in constant case as in `base_package_Foo_A` and without `_e_`.
    - Traits: when returning a trait we create a C interface by having a type whose constructor takes a void* and a list of typed function pointers corresponding to the methods (`base_package_FooInterface_<method>_fn_t`), each function is then invoked with the given void* as first argument when we call the corresponding method on the interface.
    Example: `base_package_FooInterface_t`, `base_package_FooInterface_t *base_package_FooInterface_new(void *self, base_package_FooInterface_do_foo_fn_t do_foo)`, `base_package_FooInterface_do_foo()` -> calls `do_foo` with `self` as first argument. The caller owns `self` and keeps it alive until the registration is released (each registering function documents its release point); there is no destroy hook. A Java default method is a nullable pointer, `NULL` meaning the Java default. A released constructor's parameter list never changes, as with the Rust trait module's factories (§3): when Java adds methods to the interface, a new constructor `base_package_FooInterface_with_<parameters>`, named by the overloaded-method rules (§2), takes the pointers of every method as of that release, while the existing constructors keep the Java default for the added ones. A method whose Rust counterpart is `async fn` returns `void`, takes a trailing `int64_t callback_id` and reports its result through `base_package_Client__set_callback_result(client, callback_id, void *result)` (`NULL` = success or void, `kafka_common_Error_t *` = failure), from any thread, synchronously or later. A class can be converted into an interface with the suffix `__as_FooInterface`: the result is a borrowed view valid until the class handle is destroyed and is never passed to the interface's `_destroy`. The double underscore marks functions derived by convention (`__enum`, `__as_`) that have no Java counterpart.
    - Primitive types: always use fixed size values like int8_t, int16_t, int32_t, int64_t for byte or boolean, short, int, long in Java, `double` for double. Unsigned types never appear in a signature: byte buffers cross as `kafka_Bytes_t` (`const uint8_t *data`, `int32_t len`), the only place `uint8_t` is used.
    - Async variants of blocking methods: given a blocking function `f_a` a second non-blocking `f_a_cb` is created. It takes `f_a_cb_t` as last argument together with an opaque pointer; `f_a_cb_t` receives the return value (always a pointer, omitted for void functions), a `kafka_common_Error_t *` (`NULL` on success) and the opaque pointer. When the non blocking function completes it adds (callback, return value, error, opaque) to a vector. There's no Rust thread executing these callbacks but each client has its `__execute_callbacks` function that runs the pending ones serially on the calling thread and returns how many it executed, and a `__set_callbacks_notify(fn, opaque)` whose hook is fired from a Rust task once each time the vector goes from empty to non-empty; the hook may only schedule, never run callbacks. `_destroy` runs the still pending callbacks so each fires exactly once. A blocking function invokes interface methods directly on the calling thread, a `_cb` function queues them; callbacks fired by Rust background tasks (delivery callbacks) are always queued. Once a callback finishes it runs `__set_callback_result` on the client to set the return value. The Rust task corresponding to that callback is then completed with the returned value.
    - Generic types: every time there's a generic argument it'll be replaced by a void* when it's used. Key and value serializers and deserializers are interfaces; when `NULL` is passed the `void*` is a `kafka_Bytes_t *`. Helpers standing for `java.util` types carry no package segment: `kafka_List_t`, `kafka_Map_t`, `kafka_Bytes_t`.
    - Serde interfaces: a C serializer or deserializer is asynchronous only. It is registered through `kafka_common_serialization_Serializer_new_async(self_, serialize, serialize_with_headers, configure, close)` / `kafka_common_serialization_Deserializer_new_async(self_, deserialize, deserialize_with_headers, deserialize_with_headers_bytes, configure, close)`, the first pointer required and the others `NULL` for the Java default; there is no synchronous constructor. Each method returns `void`, takes a trailing `int64_t callback_id` and reports through the handle's own `kafka_common_serialization_<Serde>__set_callback_result(self, callback_id, result, error)` (`error` `NULL` on success, else owned and taken over), from any thread, during the call or later; its arguments stay valid until it reports. `<Serde>__is_async` answers 1 for a C implementation and 0 for a built-in class's view, which completes within the call. The headers a `*_with_headers*` method receives are the record's own, not a copy, valid until the report: a mutable `kafka_common_header_internals_RecordHeaders_t *`, for a serializer as for a deserializer, which may add or remove headers as Java's may, the record carrying what they hold when it reports.
    - Nested types: `ClassA.ClassB` -> `package_prefix_ClassA_ClassB_t`
    - Static methods: `ClassA::static_method_a(a,b,c)` -> `package_prefix_ClassA_static_method_a(a,b,c)`
    - Instance methods: `a.instance_method_a(a,b,c)` -> `package_prefix_ClassA_instance_method_a(package_prefix_ClassA_t *self,a,b,c)`

translate javadoc to rustdoc. Never change the contract of public API

  - contract must be clearly documented. Copy it from Java when applicable
  - any additional Rust consideration MUST be in a dedicated "Translation notes" section, after the original documentation

  - linter must enforce for public API documentation: parameters are documented, return value is documented, at least the javadoc errors are documented. Size should be validated following previous rule. It should fail it the agent annotated the docstring with a WARNING because of different contract

11. **Concurrency**: 
    1. If a method is blocking in Java it should async in Rust
    2. Translate callbacks you find in Java client to code that is executed 
       after awaiting the corresponding call in Rust.
    3. In case the original method isn't blocking to await the callback response (for example awaiting a CompletableFuture), use Tokio `task::spawn` to create a coroutine that is detached from current flow.
    4. When Java uses `thread.join()` or `Future.get()` to block until completion, the Rust translation must actually `.await` the corresponding handle — setting a flag or dropping a channel is not equivalent to joining.
    5. Translating a Java callback to async does not eliminate the callback obligation. If Java guarantees exactly-once callback invocation per record at a specific lifecycle point (e.g. `completeFutureAndFireCallbacks`), the Rust translation must invoke the equivalent at the same point — not defer it or silently drop it.
    6. **Tokio-specific pitfalls** (no Java equivalent — Java threads do not have cancellation semantics):
       - `tokio::select!` cancels the losing branch's future mid-execution. Never put operations with side effects (incrementing a counter, sending on a channel, writing to a buffer) inside a `select!` arm unless the future is cancellation-safe. Use `biased;` when ordering matters.
       - Holding a `MutexGuard` across an `.await` point deadlocks the async runtime — always drop locks before awaiting.
    7. About naming, whenever we're talking about a "thread" in Java let's use the term "task" in Rust. E.g. in log messages.
12. **Error handling**: follow [Rust guidelines](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html) for error handling.
    1. Avoid `panic` for public API, use it only if there's no way to recover from a particular error, such as an OOM or a
       `ArithmeticException` like division by zero.
    2. Return a `Result` when Java code throws an exception even if unchecked but recoverable.
    3. **The base error type is `Error`** (`common::Error`) — the single type every
       fallible API returns. It is a flat enum with no Java counterpart: Rust cannot
       express Java's exception hierarchy, so one enum holds both `KafkaException`'s
       subclasses and the generic `java.lang` / `java.util` runtime exceptions that
       sit beside it. Java's `KafkaException` base class maps to the `KafkaError`
       struct (error code + optional message), embedded in each specific error
       struct.
    4. Because the hierarchy is flattened, every class in
       Java's error hierarchy MUST be recoverable as a predicate on `Error`, named
       `is_` + the class name snake_cased with the Exception suffix replaced by
       `Error` (§2). The `_error` suffix is applied uniformly — no exceptions, so
       the name is derivable from the Java class without judgement:

       | Java class                  | predicate                      |
       |-----------------------------|--------------------------------|
       | `KafkaException`            | `is_kafka_error()`             |
       | `ApiException`              | `is_api_error()`               |
       | `RetriableException`        | `is_retriable_error()`         |
       | `RefreshRetriableException` | `is_refresh_retriable_error()` |
       | `InvalidMetadataException`  | `is_invalid_metadata_error()`  |
       | `AuthenticationException`   | `is_authentication_error()`    |
       | `AuthorizationException`    | `is_authorization_error()`     |

       These predicates encode Java's `extends` chain, so the family contains
       all Java subclasses. A Java *static* that classifies an exception is
       NOT a predicate on `Error` and MUST NOT be added to this trait — it is
       translated as a free function in the module matching its Java home, taking
       `&Error`. The one such case is fatality: `RequestUtils.isFatalException`
       becomes `common::requests::request_utils::is_fatal_error(&Error)`, whose
       body mirrors the Java `instanceof` chain (delegating to
       `is_authentication_error` / `is_authorization_error` for the two base
       classes, matching variants for the standalone ones). It is deliberately
       NOT `Error::is_fatal_error`: fatality is not a property of an exception's
       *type* — the same class is fatal in one context and recoverable in another
       (Streams' `RecordCollectorImpl.isFatalException` and
       `TransactionManager`'s `FATAL_ERROR` state use entirely different notions),
       so it does not belong in the `extends`-encoding trait. Java itself keeps it
       a static with a single caller (`AdminMetadataManager`); the translation
       mirrors that shape. Being in an API that is not public 
       `common::requests::request_utils::is_fatal_error` is not exposed in C FFI.

       Leaf classes get a predicate too (§3): every `Error` variant has its own
       *class predicate*, named the same way after its payload type
       (`TopicExistsError` -> `is_topic_exists_error`, `InvalidRegularExpression`
       -> `is_invalid_regular_expression_error`), meaning Java's `instanceof` —
       true for the class and for every class that extends it. Users classify
       with these, not by matching the variant or comparing the code: a subclass
       a later Java release adds becomes a new variant that a `matches!` misses,
       while its payload answers `true` to its parent's predicate. So every
       predicate, leaf or intermediate, is an `ErrorHierarchy` method the payloads
       override — never an inherent `matches!` — with a `Box<T>` forwarder and a
       UFCS forwarder on `Error`. `cargo xtask lint-custom`
       (`check-error-predicate`) enforces each piece, and
       `ffi_every_class_has_its_own_predicate` checks every class predicate
       against one instance of every class. The crate's own code may still match
       variants internally.

       Each predicate additionally MUST:
         - document the exact set of variants it covers and cite the Java class it
           translates, because a flattened enum gives the reader no other way to
           see the hierarchy;
         - be covered by a test asserting BOTH directions over every error code
           against the Java `extends` chain (the precedent is `errors.rs`'s
           `test_retriable_errors_match_java_hierarchy`) — a sampled test cannot
           catch a code wrongly added to, or missing from, the set;
         - state its polarity relative to its siblings. These predicates are NOT
           complements of one another: `Serialization` and `Wakeup` are
           `KafkaException`s that are not `ApiException`s, so they answer `true` to
           `is_kafka_error()` and `false` to `is_api_error()`.
    5. **Panics policy.** A Java throw that only checks a programming precondition the
       caller can avoid by reading the signature (a guarded getter on a closed consumer,
       `group_metadata()` without `group.id`, a violated argument precondition such as
       `MetricConfig.samples(0)`) stays a Rust panic with Java's message, documented
       under `# Panics`; its C export keeps its shape (a `void` stays `void`). A runtime
       failure the caller cannot rule out is a `Result` (12.2). At the C boundary
       `#[ffi_guard]` catches the panic and reports it as an `IllegalStateError` whose
       message begins `Rust panic caught at the FFI boundary in <function>`, stored in
       `out_err` by a fallible function or an `_err` twin and delivered by a `_cb` twin's
       completion (`rust/src/ffi/common.rs` `panic_error`). `consumer-threading.md` §1
       and DoD #11 apply this policy to the consumer's guarded getters.
13. **Language-related optimizations**: When the memory can be kept on the stack even if Java code creates a new object, keep it on the stack. On hot paths (send path, batch drain, wire framing, per-record processing), also account for costs Java's JIT/GC masks but Rust makes explicit:
    - Identifiers cloned on every message (topic names, client IDs): prefer `Arc<str>` over `String` to make clones cheap
    - A single numeric field shared across tasks: prefer `AtomicI64`/`AtomicU64` over `Mutex<i64>` to avoid lock contention
    - Hot-path async dispatch: avoid `Pin<Box<dyn Future>>` per call — prefer concrete `async fn` return types or generic dispatch
    - Per-message `tokio::spawn` on the send path: avoid — use a shared completion task with a channel instead

    **"Hot path" definition**: per-record / per-message dispatch (send-path record build, batch drain, deserialize/serialize, wire framing). This does **not** include per-RPC or per-batch top-level API surfaces (e.g. the `Producer` / `Consumer` dispatch trait used at `send()` / `poll()` granularity) — there, one `Pin<Box<dyn Future>>` per call is amortized over many records and is negligible. `#[async_trait]` is acceptable for those top-level surfaces.

    Outside hot paths, prefer the simpler type (`String`, `Mutex`) unless profiling shows otherwise.
14. **Parameters and return values of public API**: Accept the most general borrowed form for input parameters. Borrow immutably, and return immutable values.
    Return a borrowed reference in case the data is still owned by the original struct (getter for example).
    When ownership is transferred to the caller prefer returning the struct (making use of RVO) over Box or Rc or Arc.
    Don't copy byte arrays holding the key, value or headers passed to ProduceRecord or received in ConsumeRecord. This zero-copy requirement extends through the entire write path: serialized bytes must be written directly into the batch buffer (no intermediate buffer), batch finalization must not copy already-serialized bytes, and wire sends must use vectored I/O (`IoSlice` / `write_vectored`) so the framing header and payload are sent without assembling a single contiguous buffer. On the receive path, the symmetric rule applies: fetched bytes are owned by one buffer in `CompletedFetch`, every downstream type borrows slices from it, and the `Deserializer<T>` trait (`rust/src/common/serialization/deserializer.rs`) is async, its methods returning `impl Future + Send` (no `#[async_trait]`), with the sealed dyn-compatible `DynDeserializer<T>` companion, whose methods return an `InlineFuture` so a call through `dyn` boxes no future per record; it takes `data: &[u8]` (plus the KIP-863 `deserialize_with_headers_bytes` overload taking `&Bytes`), borrowed from the fetch buffer — see `consumer-threading.md` §27.
15. **Consumer-specific rules**: see [consumer-threading.md](.claude/rules/consumer-threading.md) for `AsyncKafkaConsumer` API shape, background-task design, `wakeup()` cancellation, `SubscriptionState` ownership, group-protocol scope, receive-path zero-copy, and `ConsumerRebalanceListener` invocation thread. These rules supplement #10/#11/#13/#14 inside the consumer module.

## Python Binding Conventions

The Python client, package `confluent_kafka` in `python/`, is built only on the C FFI of §4. Its surface and implementation are generated from this section, the Java source, the C FFI header and the previous release's interface; the same inputs give the same result on every run.

- **General rules**
  - Rule 1: Java decides the content — classes, methods, parameters, types, defaults and behaviour. Python decides only the form, through the idiom translations below. A deliberate content change is marked *(deviation)*; anything else needs a new rule. Nothing comes from confluent-kafka-python or readability, and Javadoc is read only for nullability.
  - Rule 2: Java's standard types map to Python's standard types by the fixed table in Types.
  - Rule 3: where Java has nothing, Python's standard convention applies.
- **Idiom translations (rule 1)**
  - Names are snake_case for methods and parameters, PascalCase for types, a nested Java type a nested class (`CloseOptions.GroupMembershipOperation`) (`offsetsForTimes(timestampsToSearch)` -> `offsets_for_times(*, timestamps_to_search)`); a class name's `Exception` suffix becomes `Error`, nothing else changes (`setPollException` -> `set_poll_exception`).
  - A leading `get` is dropped from a getter, a method whose name after `get` names what it returns (`Uuid.getMostSignificantBits()` -> `most_significant_bits()`); a `get` that is the whole name (`Config.get(name)`, `KafkaFuture.get()` -> `get`) or that is qualified rather than followed by what is returned (`KafkaFuture.getNow(valueIfAbsent)` -> `get_now(*, value_if_absent)`) stays; `is` and `has` stay (`hasRack()` -> `has_rack()`).
  - One Java overload set -> one method (Signatures).
  - `null` and `Optional` -> `None`; Java collections -> Python collections (Types).
  - A Java client interface -> a non-instantiable base class; an interface the client only hands out -> a `typing.Protocol`; a multi-method interface the user implements -> a class to subclass (`abc.ABC`), Java's abstract methods staying abstract (`@abstractmethod`, so a subclass missing one fails at construction, as Java's fails to compile) and `default` methods keeping their body; a single-method callback interface -> a `Protocol` of the interface's name whose `__call__` takes Java's parameters keyword-only plus `**kwargs` (`Callback`, `OffsetCommitCallback`, `AcknowledgementCommitCallback`); `Runnable` -> `Callable[[], None]`.
  - `AutoCloseable` / `Closeable` -> a context manager (`__enter__`/`__exit__`, async `__aenter__`/`__aexit__`) whose exit calls `close()`, the producer flushing first.
  - `iterator()` -> `__iter__`, `count()` -> `__len__`; `equals`/`hashCode` -> `__eq__`/`__hash__`, `toString()` -> `__str__`, a `double` printed as `Double.toString` specifies it since JDK 19 (older JDKs print extra digits for some values: `9.999999999999999E22` for `1.0E23`) *(deviation: `null`, `true` and `false` print as Python's `None`, `True` and `False`. Why: the user reads Python values, as everywhere else in the API; the strings the core parses keep Java's)*, `Comparable` -> ordering.
  - `Future<T>` and `KafkaFuture<T>` -> `confluent_kafka.common.KafkaFuture[T]` on a sync class, `AsyncKafkaFuture[T]` on an async one (Futures); a client class -> itself on a sync class, its async peer on an async one (`AsyncAdmin.create` returns an `AsyncAdmin`, built as an `AsyncKafkaAdminClient`), and a client class's nested types are repeated on its async peer with the same swap (`AsyncMockAdminClient.Builder.build()` returns an `AsyncMockAdminClient`); `Duration` -> `float | timedelta`; `java.util.UUID` -> `uuid.UUID`.
- **Scope**
  - In scope: the `Producer`, `Consumer`, `ShareConsumer` and `Admin` families and every public type reachable from what is generated (taken, returned, thrown, the superclass of a generated class other than a client class, or a public subclass of an abstract class a generated method takes: `AbstractOptions`, `UserScramCredentialUpsertion`, `UserScramCredentialDeletion`), recursively *(the last two edges are a specific fix. Why: no signature names `AbstractOptions` or the SCRAM subclasses. Goes when: every public class is generated)*, plus the `common` types the share consumer reaches (`TopicIdPartition`), and the public nested types of every generated class (`CreateTopicsResult.TopicMetadataAndConfig`, `OffsetSpec.EarliestSpec`). Only public classes annotated `@InterfaceAudience.Public` (§2), outside `internals` packages and packages marked "not a supported API", and only their public members (not the package-private `KafkaConsumer.clientId()`). Errors follow the Errors rule instead: a class for every exception the FFI enum names, Public or not, because the core can raise it.
  - The config classes (`ProducerConfig`, `ConsumerConfig`, `AdminClientConfig`) are translated for their `public static final` constants only *(deviation: their `ConfigDef` machinery is not translated. Why: a configuration is a `dict` of these keys, and the `ConfigDef` types are the types Configuration checks)*. `ShareConsumerConfig` is not translated while the share consumer is not. `CommonClientConfigs` is not translated: Kafka 4.4 leaves it out of its public API (not `@InterfaceAudience.Public`); its keys are on `ProducerConfig`, `ConsumerConfig` and `AdminClientConfig` or are plain strings. The key-name and config-value classes (`TopicConfig`, `SaslConfigs`, `SslConfigs`, `SecurityConfig`, `LogLevelConfig`, `SecurityProtocol`, `SslClientAuth`, `GroupProtocol`) are translated in full, except a method that takes a `ConfigDef` (`SaslConfigs.addClientSaslSupport`, `SslConfigs.addClientSslSupport`) *(deviation: the same `ConfigDef` machinery as above)*. Not translated *(deviation)*: assignors (the group coordinator assigns partitions under KIP-848, `consumer-threading.md` §20), interceptors (the core runs none; goes when interceptors are designed) and partitioner implementations (selected by `partitioner.type`, as config takes no classes, §2).
  - Nothing Java lacks is added except as a *(deviation)* or by rule 3: no `client_id()`, no producer `poll()`.
- **Modules**
  - An error lives in the module of its Java package, `clients` dropped (`BufferExhaustedError` -> `confluent_kafka.producer`, `InvalidRecordError` -> `confluent_kafka.common`, `CorrelationIdMismatchError` -> `confluent_kafka.common.requests`); a Java built-in exception class is at the root.
  - Every other type lives in the module of its Java package, `clients` dropped (`clients.consumer.KafkaConsumer` -> `confluent_kafka.consumer`, `common.record.TimestampType` -> `confluent_kafka.common.record`, `common.acl.AclBinding` -> `confluent_kafka.common.acl`, `common.security.auth.KafkaPrincipal` -> `confluent_kafka.common.security.auth`); `Duration` is at the root.
  - One snake_case file per Java class in its module package (`consumer/close_options.py`), re-exported by the package `__init__.py` as `from .close_options import CloseOptions as CloseOptions` and listed in `__all__`; users import from the module, never the file. Internals are `_`-prefixed. By rule 3 the root exports only `Duration` and the Java built-in exception classes. `_confluentkafka` (the C extension) is never a public import path.
  - A name Python gives by rule 3 (`Async*`, `*_nowait`, the serde factories, `Duration`) is kept once released. If Java later adds a public item of that name to the same module, the Java item is the one that gets a different name, chosen with the owner when it happens.
- **Class family**
  - A Java client interface -> a base class with all its methods; constructing it raises `TypeError("<Base> is a non-instantiable base; use <Kafka> or <Mock class>")`, `<Kafka>` being the `Kafka*` class when it has a public constructor, else the public static factory that returns it (`Admin.create`).
  - `Kafka*` subclasses add only Java's public constructors; `Mock*` subclasses add Java's public constructors and the Java mock's public methods beyond the interface.
  - By rule 3, each of the twelve client classes (four bases, four `Kafka*`, four `Mock*`) has an asyncio peer with the same constructors and methods, except overloads left out because their entry point is missing (Implementation over the FFI).
  - Every public asyncio class is named `Async` + the name of its sync class, and lives in the sync class's module: `AsyncKafkaConsumer` beside `KafkaConsumer` in `confluent_kafka.consumer`, `AsyncKafkaFuture` beside `KafkaFuture` in `confluent_kafka.common`. There is no separate async module.
  - By rule 3 each callback interface an async client class takes has a public asyncio form beside it, named and placed the same way, whose methods are `async def`: `AsyncCallback` (`confluent_kafka.producer`), `AsyncOffsetCommitCallback` and `AsyncConsumerRebalanceListener` (`confluent_kafka.consumer`), `AsyncConsumerRebalanceListener.on_partitions_lost` awaiting `on_partitions_revoked` as Java's default calls it. `AsyncKafkaFuture`'s `then_apply` functions and `when_complete` actions stay plain callables, as asyncio's own `add_done_callback` takes. The async client class's parameter takes the Java form or the asyncio form; `AsyncMockConsumer.schedule_poll_task` takes a `Runnable` or an `async def` task, which `poll()` awaits. A plain callback runs on the event loop and must not block it, as Java's callbacks must be fast on its I/O thread.
  - A class, method or overload Java deprecates (§3, in the releases of the Source Reference) is not generated: no consumer `close(Duration)`, no `ConsumerGroupMetadata` constructor, no `ConsumerRecords(records)`, no `OffsetResetStrategy` and so no `MockConsumer(OffsetResetStrategy)`. By rule 3, one Java deprecates after this client's first major release -> a `DeprecationWarning` when the method, or the deprecated overload, is called, plus Java's deprecation note in the docstring.
  - On the async peer a method is `async def` iff the entry point it calls has a `_cb` twin in the C FFI header (§4): both classes call the `_cb` twin, never the blocking form (except `KafkaProducer.send()` from inside a producer's callback, Behaviour with no other home, and a call from inside a consumer's listener, which waits on the `ConsumerHandle`'s blocking form, the conversions table); the async class awaits its completion on the event loop, the sync class waits for it in short slices while the client's callback queue is drained (by the waiting call itself on the consumer, by the client's completion thread on the producer and the admin client), so Ctrl+C is seen. Every other method is a plain `def` on both classes (`assignment()`, `paused()`, the admin RPCs, which return at once as Java's do); `current_lag()` has the `_cb` twin `kafka_consumer_Consumer_current_lag_cb`, so it is `async def` on the async classes. `begin_transaction`'s entry point first drains the records already sent (`producer-transactions.md` §13), so it has a `_cb` twin: it is `async def` on the async classes and waits on the sync ones *(deviation: Java's `beginTransaction` does not wait. Why: the FFI decides which methods wait)*. `AsyncMock*` mirrors `AsyncKafka*`, plus `rebalance` and `lose_partitions`, which run the listener. While `rebalance()` or `lose_partitions()` runs its listener, or the async `poll()` awaits an `async def` poll task, a call from another task or thread raises `ConcurrentModificationError` with `KafkaConsumer`'s message; the listener's or task's own calls back into the consumer and `wakeup()` pass *(deviation: Java's caller waits for the synchronized call, which a task on the listener's loop cannot do without stopping it)*.
  - *(deviation)* A Java `xSync` / `xAsync` pair -> `x()` / `x_nowait()`, `_nowait` meaning the call does not wait for the broker's answer: `commitSync` -> `commit()`, `commitAsync` -> `commit_nowait()`. Java's `xAsync` names are never reused. Why: on an asyncio class "async" means a coroutine, so Java's `xAsync` name would mark the one method that does not wait for the broker; `_nowait` is Python's suffix for that, as in `queue.put_nowait`.
  - Members keep Java's declaration order (the interface's order in the base, then the Java mock's own methods); a dunder replacing a Java method takes its place, `__enter__`/`__exit__` follow `close`; the async peer uses the sync order.
  - Java getters stay methods (`tp.topic()`), never `@property`. Java static methods -> `@staticmethod`.
  - `public static final` constants -> class attributes of the same name (`RecordMetadata.UNKNOWN_PARTITION`, `ConsumerRecords.EMPTY`, `ConsumerRecord.NO_TIMESTAMP`, `DisconnectError.INSTANCE`, `Uuid.ZERO_UUID`), a constant `Set` as a `frozenset` (`Uuid.RESERVED`), a constant `List` as a `tuple` (`SslClientAuth.VALUES`). Apart from nested types, enum members and constants there are no public attributes.
  - A public mutable field -> a setter `set_<field>(*, <field>)` and nothing else *(deviation. Why: the surface has no public attributes (Class family), and a setter is the method form of Java's field assignment)*: `MockProducer.sendException` -> `set_send_exception(*, send_exception)`.
  - Java type parameters -> `Generic` with Java's letters (`KafkaConsumer[K, V]`, `ConsumerRecord[K, V]`), except one that only stands for the class itself (`AbstractOptions<T extends AbstractOptions>`, returned as `this`), which is `typing.Self` (`typing_extensions.Self` on Python 3.10); other types are not generic. A class holding futures that both a sync and an async client return (the admin `*Result` classes) is generic over a private marker of the client kind, set by the client that returns it; each method returning a future has one stub per kind, its future being `KafkaFuture` for the sync kind and `AsyncKafkaFuture` for the async one (Futures). No code, test or doc writes the marker. The records (`ProducerRecord`, `ConsumerRecord`) are covariant in `K` and `V`.
  - A Java enum -> `enum.IntEnum` valued by the constant's integer field when its constructor sets exactly one, whatever Java names it (`id`: `TimestampType.CREATE_TIME = 0`; `code`: `AclOperation.READ = 3`; `value`: `ElectionType.PREFERRED = 0`), else `enum.Enum` valued by the constant's name (`LEAVE_GROUP = "LEAVE_GROUP"`); members in Java order. Its other public fields are reached through Java's own methods (`toString` -> `__str__`, `forName` -> `for_name`), not as attributes. The kind of an enum is chosen when it is first released and never changes. An integer field Java adds later becomes a method, as `name` is today, not a new value.
  - No public constructor (all private, package-private or protected) and not a class Java builds with setters (Signatures) -> `__init__` raises `TypeError` naming the public static factories that return the class, its own or another class's (`NewPartitions`; `KafkaAdminClient`: `Admin.create`), or, when there are none, the methods that return it (`CreateTopicsResult`: the admin client's `create_topics()`); all constructors deprecated -> `__init__` raises `TypeError` naming where instances come from (`ConsumerGroupMetadata`: the consumer's `group_metadata()`). Java's non-public constructor becomes the private class method `_new`, keyword-only with the Java constructor's parameters, which builds the object without `__init__` (`cls.__new__(cls)`) and runs the constructor's body; the client, the mock and the other translated classes build the object through it. A Java `abstract` class -> a base class whose construction raises `TypeError`, naming its public static factories when it has any (`TopicCollection`: `of_topic_ids`, `of_topic_names`), otherwise saying to use one of its subclasses (`AbstractOptions`, `UserScramCredentialAlteration`); its subclasses construct as Java's do, and it gets no keyword constructor. Value types and records change only where Java's do: a Java setter changes the object (and returns what Java returns); a class whose Java fields are all `final` has no setter. A constructor that stores an argument as Java's does stores a `None` too, a copy it makes of the input keeping `None` as `None`; the `TypeError` comes where Java uses the field (Types), or from the call that hands it to the FFI (Implementation over the FFI, exception 4). A `*Result` whose sync or async kind is read from its futures requires them (`ListOffsetsResult(futures=None)` raises), since it cannot tell its kind without them.
  - Dropped *(deviation)*: any method whose `AsyncKafkaConsumer` body only logs that it is unsupported (`enforceRebalance`), and any mock helper that only reads, sets or clears state that exists only for a dropped or not-generated method (`MockConsumer.should_rebalance()`, `reset_should_rebalance()`). Why: under KIP-848, the only protocol here, such a method does nothing, and such a helper can do nothing without its method.
- **Futures**
  - `Future<T>` and `KafkaFuture<T>` -> `confluent_kafka.common.KafkaFuture[T]` on a sync class, `AsyncKafkaFuture[T]` on an async one: one future type for every future the package hands out, `send()`'s included *(deviation: Java's `Future<RecordMetadata>` gains `then_apply`, `when_complete` and `all_of`. Why: the package hands out one future type)*; a `Future` implementation keeps its own `cancel()` answer, `send()`'s being `False`, as Java's `FutureRecordMetadata`. The async `send` is awaited twice: `md = await (await p.send(record=r)).get()`.
  - The class is Java's `KafkaFuture` by Signatures, its members in Java's declaration order: the static `completed_future(*, value)` and `all_of(*, futures)`, `to_completion_stage()`, `then_apply(*, function)`, `when_complete(*, action)`, `cancel(*, may_interrupt_if_running)`, `get()` and `get(*, timeout: Duration)`, one stub each (Java's `get()` and `get(long, TimeUnit)`; a `None` timeout is Java's null `TimeUnit` and raises `TypeError("timeout must not be None")` (Types); a negative or zero timeout is no error: `get` raises `TimeoutError` at once unless the future is done, as Java's `CompletableFuture.get(timeout, unit)` does, while the Timeouts rule's overflow, `NaN` and `timedelta` reading still applies), `get_now(*, value_if_absent)`, `is_cancelled()`, `is_completed_exceptionally()`, `is_done()`. `get` is `async def` on `AsyncKafkaFuture`; every other method is a plain `def` on both. Java's nested single-method interfaces `BaseFunction` and `BiConsumer` are `Callable` aliases of those names nested in the class: a `then_apply` function is called positionally with one argument, Java's `apply(A)`, and a `when_complete` action with two, Java's `accept(A, B)`, the value and the exception *(deviation from the keyword contract of single-method callbacks (Signatures). Why: Java names their parameters `a` and `b`, which carry no meaning as keywords, and Python's futures call their callbacks positionally, so `then_apply(function=lambda v: v + 1)` works as written)*. `to_completion_stage()` returns the inner `concurrent.futures.Future[T]` / `asyncio.Future[T]` the future waits on. Java's protected `complete` / `completeExceptionally` are not public: they are `complete` / `complete_with_error` on the private `_KafkaFutureImpl`.
  - Two value sources, one surface: a C `kafka_common_KafkaFuture_t` handle (the clients' futures; the handle is the value source, `get_cb` and `is_done`) or Python state (`_KafkaFutureImpl`, Java's `KafkaFutureImpl`: the mocks' futures, `completed_future`, the dependants, `all_of`).
  - The class is slots-only: the inner Python future (`concurrent.futures.Future` / `asyncio.Future`) and the C `get_cb` registration are created on the first operation that needs the completion delivered: the first wait, `when_complete`, `then_apply`, `to_completion_stage()` or `cancel`, or the future becoming a source of `all_of` (a Result's `all()` included), so a dependant completes without anyone waiting on its source; state reads go to the C handle, and no closure is made per record. The gate is an A/B run of the producer performance test (`python/test/performance/producer_performance_test.py`) against the base branch, for the sync and the async producer.
  - `get()`, `get(timeout=…)` and `get_now()` on a failed future raise the root `confluent_kafka.ExecutionError` (Java's `java.util.concurrent.ExecutionException`), raised `from` the stored exception, so `e.__cause__` is Java's `getCause()`; its message is the cause's `toString()` form (`<module>.<class>: <message>`), as Java's `ExecutionException(Throwable)`. A cancelled future raises its inner future's `CancelledError` (`concurrent.futures.CancelledError` from `KafkaFuture`, `asyncio.CancelledError` from `AsyncKafkaFuture`); a timed-out `get` raises `TimeoutError`. `when_complete` receives the raw stored exception; dependants and `all_of` carry the raw exception and box it only in their own `get`.
  - The cancel family is Python-side: `cancel`, `is_cancelled`, `is_completed_exceptionally`, `get_now` and `when_complete` are implemented in the class over the C future's `is_done` / `get` / `get_cb` and the inner Python future. `cancel()` cancels every dependant built in Python (`then_apply`, `when_complete`, `all_of`, a Result's `all()` and per-key refinements), never the source, the request or the core, as Java. A Result's `all()` is composed in Python only where Java's is `allOf`: so a Result whose Java `all()` is `KafkaFuture.allOf` over its per-key futures (`CreateTopicsResult`, `DescribeConsumerGroupsResult`, …) composes `all()` in Python over them, not through C's `all_of`; a Result whose Java `all()` is its own future (`DescribeUserScramCredentialsResult`, `AlterConsumerGroupOffsetsResult`, `RemoveMembersFromConsumerGroupResult`, `ListGroupsResult`, `DeleteConsumerGroupOffsetsResult`) takes the C future; a refinement whose value comes from a C future (`CreateTopicsResult.config(topic)`) is linked as a dependant of its key's future.
  - `then_apply` functions and `when_complete` actions run where the completion runs: on the producer's completion thread, on the sync admin client's pump thread (Threads and callbacks), on the event loop for an async client; on a mock, and on a future already done, inside the registering call. `KafkaFuture.get()` only waits, in short slices on its inner future, so Ctrl+C is seen; it never drains the client's callback queue and never calls the blocking C `get` on a pending future; a done future's value is read at once through it, which does not wait. The consumer keeps draining inside its waiting calls.
  - The admin RPC methods are plain `def` on both clients and return their Result at once, as Java's (Class family). A Result is one class per RPC, generic over the private `Sync` / `Async` marker (Class family), its accessors returning `KafkaFuture[...]` on the sync kind and `AsyncKafkaFuture[...]` on the async kind, with one stub pair per accessor. `CreateTopicsResult.config`, `topic_id`, `num_partitions` and `replication_factor` for a topic not in the request answer what the C accessor answers (a future failed with `IllegalArgumentError`, surfacing at `get()` as `ExecutionError`), with no Python-side check *(deviation: Java's accessor dereferences the missing key and throws `NullPointerException` at the call. Why: the C accessor answers a failed future, and the binding makes no check of its own. Goes when: the FFI answers as Java's accessor does)*.
- **Signatures**
  - *(deviation)* Every parameter of every method, constructor and module function is keyword-only (`*,`), dunders aside; a positional call is a `TypeError`. Exemptions: listener methods, the `Partitioner` and `Cluster` a mock is given, and the functions and actions given to a `KafkaFuture` (Futures), are called positionally. Serdes and single-method callbacks are called with keyword arguments named after Java's parameters and must accept `**kwargs`, so a parameter Java adds later reaches them without breaking existing ones; a callable without `**kwargs` is rejected with `IllegalArgumentError` where it is given. The binding may call a registered callable positionally when its Java-named parameters allow it, an implementation detail that leaves this contract unchanged. Why: Java's overloads become one method, and a call by keyword keeps working when Java adds a parameter or makes one optional.
  - A parameter whose Java type is a collection of `String` (`topics`, `topic_names`, `group_ids`, `transactional_ids`, `users`, `protocol_types`, an error's `unauthorized_topics` and `invalid_topics`, a mock builder's `broker_log_dirs`) refuses a `str`, `bytes` or `bytearray` with Python's `TypeError("<name> must be an iterable of str, not <type>")` (rule 3): Java cannot receive one there, and Python would otherwise iterate it by character, so `subscribe(topics="orders")` would subscribe to five one-letter topics. A collection of collections names its element (`broker_log_dirs` -> `"must be an iterable of lists of str"`) and checks each element the same way, after reading a one-shot iterable once. Like the positional-call `TypeError` and the `java_forms` check it comes before the body's own checks, the closed check included, so it wins over a closed client; `reject_str` in `confluent_kafka/_args.py` makes it, and a generator emits it for every such parameter it generates.
  - A parameter is named by the Java **interface** declaration when the method is declared on one (`Consumer.subscribe(topics, callback)` -> `callback`, although the implementations say `listener`), else by the class's own declaration; a type never renames it: `errorNext(RuntimeException e)` -> `error_next(*, e)`, `Uuid.fromString(String str)` -> `from_string(*, str)`.
  - One Java overload set -> one Python method (or `__init__`) taking the union of the overloads' parameters by Java name, never one method per overload: `seek(tp, long offset)`, `seek(tp, OffsetAndMetadata offsetAndMetadata)` -> `seek(*, partition, offset=MISSING, offset_and_metadata=MISSING)`, with one stub per overload.
  - Order: each overload keeps its own order; where that leaves a choice, the parameter of the earliest-declared overload goes first. `subscribe(topics)`, `(topics, callback)`, `(pattern, callback)`, `(pattern)` -> `topics, pattern, callback`; `TopicIdPartition(topicId, topicPartition)`, `(topicId, partition, topic)` -> `topic_id, topic_partition, partition, topic`.
  - Same position, Java types mapping to the same Python type -> one parameter named after the earliest-declared overload (`KafkaConsumer(Map configs)`, `(Properties properties)` -> `configs`); an error's message is never merged this way.
  - A parameter in every overload is required. Otherwise its **Java-given** value, which `java_forms` fills when it is left out (below), is what a shorter overload gives it — the argument it passes calling a longer public overload of the set, or the constant it assigns to that parameter's field — read in the declaring class or, for an interface method, in the `Kafka*` class following `delegate` forwards (`KafkaConsumer`'s delegate is `AsyncKafkaConsumer`, `KafkaShareConsumer`'s `ShareConsumerImpl`), or in the interface's own `default` body when the `Kafka*` class does not redeclare the method (`Admin.listConfigResources()` passes `Set.of()`): `null`, `Optional.empty()` -> `None`; a literal, enum constant or `static final` constant -> its value; an empty array, list or set (`new Node[0]`, `Collections.emptySet()`) -> `()`; an empty map -> `None`, read as empty (a filled `dict` would be one mutable object shared by every call). So `OffsetAndMetadata(offset)` -> `metadata=""`, `Node(id, host, port, rack)` -> `is_fenced=False`, `acknowledge(record)` -> `type=AcknowledgeType.ACCEPT`. A Java-given value records what Java's shorter overload passes; it never makes a parameter omittable on its own (`java_forms`, below).
  - Every parameter some overload omits, a header parameter included, has the marker `MISSING` as its implementation-signature default. `MISSING` is a private sentinel object defined in `confluent_kafka/_args.py`: Python's way of saying "no argument here", which Java does not need, since Java chooses the overload from the arguments written. It is internal only: never a valid value of any parameter, never `None`, never exported by a public module, and never named in a stub or a docstring as something to pass; `help()` and `inspect.signature` show it only because it is the real default. Passing it explicitly is the same as leaving the parameter out.
  - Leaving a parameter out is the only "not given", and selects the overload without it; what Java's shorter overload passes for it (`()` for headers, `Cluster.empty()` for `MockProducer`'s cluster) is filled by `java_forms` (below), never written as a default in a signature or a stub. An explicit `None` is Java's `null`: it counts as given, selects the overload that takes the parameter, and raises Java's error and message where Java throws on null. An `Optional<T>` parameter reads `None` as `Optional.empty()` (Types).
  - A serializer / deserializer parameter is the one exception to exact matching (`java_forms`, below): it may be left out on its own. Left out, or given as `None` (Java's null, which `KafkaProducer` and `KafkaConsumer` read as "use the config key"), the config key is used if set, else `bytes_serializer()` / `bytes_deserializer()` *(deviation: Java fails at construction when the key is missing too. Why: a client needs a serde, and the bytes serde passes the data through unchanged)*, and its type variable binds `bytes` (Binding).
  - One `@typing.overload` stub per Java overload, with exactly that overload's parameters and no defaults: `close()` and `close(Duration)` are `close(self) -> None` and `close(self, *, timeout: Duration) -> None`; `Node`'s three constructors are three stubs. A stub never shows a default: what Java's shorter overload passes is filled by `java_forms` and stated in the docstring. The implementation signature is the keyword-only union, each omittable parameter defaulting to `MISSING`.
  - Stubs exist for every method or constructor with more than one Java overload, for one whose single overload carries several types for one name (one stub per type), and for a constructor that binds a type variable (Binding); a method with one Java overload and nothing to bind has none. So `subscribe` has four stubs, `commit` four, `close` two and `poll` none. Stubs follow Java's declaration order, `@Deprecated` overloads last.
  - Binding, so that a construction needs no written type parameters under `mypy --strict`:
    - An omitted serde binds its type variable to `bytes`; a serde given only through the config route leaves the client typed as if it were omitted (`[bytes, bytes]`), so pass serdes as arguments when typing matters.
    - A record key or value that is omitted or `None` binds its type variable to `Never` (`typing_extensions.Never` on Python 3.10).
    - Each constructor gets one stub per combination of those parameters, annotating `self` with the bound types. In a stub a given serde, key or value has its plain type and no default; a `None` key or value is typed `None`, without a default, since the stub is one Java overload and that overload takes it.
    - Stub order: for each Java overload's stub in its order, the given sets from none, then each parameter alone in parameter order, then pairs, up to all. `KafkaConsumer` -> `(self: KafkaConsumer[bytes, bytes], *, configs)`, `(self: KafkaConsumer[K, bytes], *, configs, key_deserializer: Deserializer[K])`, `(self: KafkaConsumer[bytes, V], *, configs, value_deserializer: Deserializer[V])`, `(self, *, configs, key_deserializer: Deserializer[K], value_deserializer: Deserializer[V])`.
    - A class with nothing to bind from gets no binding stub, and the caller annotates it as Java writes the type arguments: `c: MockConsumer[str, str] = MockConsumer(offset_reset_strategy="earliest")`, like `new MockConsumer<String, String>("earliest")`. Otherwise no code, test or doc writes type parameters.
  - One Java name with several types -> one parameter typed as their union (in stub order), one stub per type, dispatched by `isinstance`: `f(String x)`, `f(Uuid x)` -> `f(*, x: str | Uuid)`.
  - A `None` for a parameter whose overloads differ only in its type matches no overload: `IllegalArgumentError` naming both, as Java's compiler rejects `f(null)` there; when one of those types is `Optional`, the `None` is that overload's `Optional.empty()` (Types) (`list_partition_reassignments(partitions=None, options=o)` lists every partition).
  - *(deviation)* Types `isinstance` cannot tell apart (a `str` is an `Iterable[str]`) -> one parameter per type, `<name>_<type>` (`topics_str`, `topics_iterable`), checked by `java_forms` like any other names; when the second type arrives in a later Java release, the existing parameter keeps its plain name and only the new one is suffixed. When one parameter's Java types map to the same Python type (`int`, `long`), generation stops with an error at that site. Why: there one parameter cannot be dispatched by `isinstance`.
  - `java_forms` works on Java's overloads, unfolded: each overload's parameter set, in Java declaration order. A set of given names matches an overload only when it is exactly that overload's parameter set; nothing is filled in to make a match (a serde excepted, above). Several overloads match only when they differ in a parameter's type alone, and `isinstance` then decides (Implementation over the FFI). `java_forms` then fills the matched overload's Java-given defaults — the values Java's shorter overloads pass to it (a `null`, a constant or an empty collection, as above; a default some other overload receives does not count) — before the body runs. So `acknowledge(topic=…, partition=…, offset=…)` without `type` is rejected, as Java has no such overload; and `ProducerRecord(topic=…, partition=…, value=…)` is rejected until `key=None` is written, which is Java's `(topic, partition, key, value)` with a null key.
  - "Given" means "not left at `MISSING`". A given value equal to what Java's shorter overload passes still counts as given (`acknowledge(type=AcknowledgeType.ACCEPT)` is Java's two-argument `acknowledge`), and so does an explicit `None` (`ProducerRecord(topic=…, partition=…, key=None, value=…)` is Java's four-argument constructor with a null key; `commit_nowait(offsets=…, callback=None)` is `commitAsync(offsets, null)`; `o.timeout_ms(timeout_ms=None)` sets `null` where `o.timeout_ms()` reads).
  - A method whose union accepts a set of given names matching no overload gets the one decorator `java_forms` from `confluent_kafka/_args.py`, listing its overloads and their Java-given defaults. It matches the given names against the overloads, raises `IllegalArgumentError(message="<m>() takes one of (<a>, <b>), (<c>); got (<given>)")` listing every overload when none matches (`<m>` the method name, or the class name for a constructor; names in parameter order; `commit_nowait` -> `"commit_nowait() takes one of (), (callback), (offsets, callback); got (offsets)"`), then fills the Java-given defaults and runs the body. It builds its check once, when the class is defined. A method whose every combination matches an overload has no decorator.
  - A getter and a setter sharing one name (`timeoutMs()`, `timeoutMs(Integer)`) -> one method, two stubs: no argument reads, one argument sets and returns what Java's setter returns. A static factory and an instance getter sharing one name (`CloseOptions.timeout(Duration)`, `timeout()`) -> one attribute: on the class the factory, on an instance the getter.
  - A class Java builds with setters (its only public constructor takes no arguments, or all its constructors are private and it is built by its own static factories and setters; setters being public one-argument methods that set a field: the `*Options`, `ListConsumerGroupOffsetsSpec`, `CloseOptions`, `MockAdminClient.Builder`) also takes one keyword per setter field in its Python constructor, named after the field *(deviation: Java builds it through the setters. Why: Python builds a configured object in one call; the setters stay, so Java's chain works too)*: `CreateTopicsOptions(timeout_ms=5000, validate_only=True)`, `CloseOptions(timeout=30.0, operation=GroupMembershipOperation.LEAVE_GROUP)`. Each keyword given, `None` included, calls its setter after construction; one left out leaves it uncalled (`MISSING`). The stubs show the field's Java starting value, mapped as Java-given values are, or `= ...` where it has no value of the setter's type (`DescribeFeaturesOptions.nodeId` starts `OptionalInt.empty()`, its setter takes an `int`): this keyword constructor is not a Java overload set, so it keeps its single stub showing those starting values, the one deliberate exception to the rule that a stub shows no default (stubs, above). The client builds the C options object with `<X>Options_new`, which carries the core's Java defaults, and calls its `set_<field>` only for the setters that ran. The parent class's fields come first, then the class's own, in Java's field order. The setters run in dependency order, read from their Java bodies and the calls they make inside the class: a setter that reads a field runs after the setters that write it (`MockAdminClient.Builder.controller(int index)` reads `MockAdminClient.Builder.brokers`, so it runs after `MockAdminClient.Builder.brokers(List<Node> brokers)`), and the setter of a field's own keyword runs after the setters that also write that field (`MockAdminClient.Builder.brokers(List<Node> brokers)` calls `MockAdminClient.Builder.numBrokers(int numBrokers)`, which rewrites `MockAdminClient.Builder.brokerLogDirs`, so `MockAdminClient.Builder.brokerLogDirs(List<List<String>> brokerLogDirs)` runs after it); otherwise in the keywords' order. A loop stops generation with an error. When several setters write one field, its keyword calls the one named like the field, else the one Java does not deprecate; if that leaves none or several, generation stops with an error at that class. The other setters stay as methods. After the client's first major release, a keyword keeps its name, its setter and its types, even when Java deprecates that setter (the keyword then warns as the setter does). A later Java change to the field's setters follows the setter's own parameter: a new type on the same parameter widens the keyword's type, split or stopping as for any parameter; a new setter adds a keyword named after the setter; a new overload of the setter with another parameter name adds a keyword named after that parameter. A name already taken stops generation with an error. A call may give at most one of a field's keywords, every keyword staying optional; `java_forms` reports two with its usual message (`CreateTopicsOptions() takes one of (timeout_ms, validate_only, retry_on_quota_violation), (timeout_ms, validate, retry_on_quota_violation); got (validate_only, validate)`), and the stubs show one signature per form, every keyword optional. Every other class keeps only Java's constructors (`NewTopic(name=…, num_partitions=…, replication_factor=…).configs(configs=…)`).
  - Timeouts: a `Duration` present in every overload is required (`poll(*, timeout: Duration)`); one some overload omits defaults to `MISSING` and has its own stub without it; `None` is a null `Duration` and raises `TypeError("timeout must not be None")`, as Java's `timeout.toMillis()` throws (Types). A negative duration raises `IllegalArgumentError`: with Java's message where Java's method checks the sign (`poll`, `commit` and `position` -> `"Invalid negative timeout <ms>"`, from Java's `Timer`; `close` -> `"The timeout cannot be negative."`), and with the core's `_with_timeout` message `"Timeout must not be negative"` where Java's method makes no check of its own (`committed`, `partitions_for`, `list_topics`, `beginning_offsets`, `end_offsets`, `offsets_for_times`) *(deviation: there Java's `CompletableEvent.calculateDeadlineMs` turns a negative timeout into no deadline at all, so Java waits without a time limit; goes when the core treats a negative timeout as Java does)*. A duration that does not fit `int64` milliseconds, `float("inf")` included, raises Python's `OverflowError`, and `NaN` Python's `ValueError` *(deviation: Java's `Duration.toMillis()` throws `ArithmeticException`. Why: Python raises them while converting the value, before the FFI; `OverflowError` is Python's `ArithmeticError` for it)*; neither reaches the FFI. A number is read with `float()` and rounded down to whole milliseconds; a `timedelta` exactly, from its days, seconds and microseconds, as Java's `toMillis()`; neither has a type check of its own. A Java `Integer timeoutMs` stays `timeout_ms: int | None` (milliseconds).
  - Java `void` -> `None`.
  - Nullability: a parameter is `T | None`, in the implementation signature and in every stub that lists it, when it is a record key or value (`K`, `V`), or when Java gives null a meaning for it: the method's own body (read as for defaults; not its callees, except a private overload of the same method that the body calls directly, which counts as the body) passes it to `Optional.ofNullable` or has a non-throwing null branch for it; it is stored in a field that holds `null` until this method sets it and that Java tests for null; or Java's own client code constructs the object with a value that can be null (`CompletedFetch` builds `RecordDeserializationException` from `record.key()` / `record.value()`, null for a null key or a tombstone, so `key_buffer` / `value_buffer` are nullable); or its Javadoc, or its getter's, allows null. A Javadoc "Non-null" wins. A parameter Java rejects as null is `T` (`subscribe`'s `callback`), so `mypy` flags a `None` before the runtime raises Java's error.
  - A return is `T | None` for `Optional<T>`, for a field that can hold null by the rule above, or when its Javadoc says it may be null. An argument handed to a user callback is `T | None` when the Java code invoking the callback can pass null for it (the commit callback's offsets on failure).
  - For an interface method the Javadoc read is the interface's, or, when that only points elsewhere (`@see`, `See {@link …}`), the one it points to.

Why: one name per role, the names of what `str(e)` and `__cause__` give, so `KafkaError`'s one `__reduce__` rebuilds every error by name)*:
    - In each constructor, the `String` passed unchanged to `super(...)` as the message, directly or through `this(...)`, is the keyword `message`, whatever Java calls it.
    - A `String` with the message's Java name in another constructor is the message too (`ConfigException(name, value, message)`); every other `String` keeps its Java name: `ResourceNotFoundException(message)`, `(message, cause)`, `(resource, message)`, `(resource, message, cause)` -> `ResourceNotFoundError(*, resource: str | None = MISSING, message: str | None, cause: BaseException | None = MISSING)`, one stub per Java constructor.
    - Every `Throwable` parameter, whatever Java calls it (`cause`, `t`, `throwable`), is the keyword `cause: BaseException | None`, stored as `__cause__`. It defaults to `MISSING` only where a Java constructor of the class omits it, an explicit `cause=None` then being a given null cause that selects the overload taking it; where every Java constructor takes it, it must be given, as `cause=None` for a null cause (`RecordDeserializationError`).
    - Java's `getCause()` is `__cause__`; for an error from the core it follows the FFI chain `kafka_common_Error_source`, a borrowed handle its owner frees, including a serde's or user callback's own exception; an error's payload is read through its view (the `kafka_common_Error_*` function returning the class's `kafka_common_<Class>Error_t`, `NULL` for another class, as `kafka_common_Error_resource_not_found`), then the view's accessors. An error an operation returns is owned and freed once converted (`from_ffi_error`); one borrowed (a source, a delivery callback's) is converted and left to its owner; a `_cb` completion owns the error it delivers.
    - `str(e)` is Java's `getMessage()`: the string the Java constructor passes to `super(...)` (`TopicAuthorizationError(unauthorized_topics={"t"})` -> `"Not authorized to access topics: [t]"`), `""` when that is `null`, and for Java's `Throwable(Throwable)` `cause.toString()`: `"<module>.<class>"`, plus `": <message>"` when the cause has one. A class that overrides `toString()` (`QuotaViolationException`) uses its override: `str(e)` is the override's text after the class name, and where Java uses `toString()` (a wrapping error's message, `ExecutionError`) it is the whole override with the Python class path.
    - A call giving none of the parameters is matched like any other: `KafkaError()` is Java's `KafkaException()`, while `TopicAuthorizationError()`, `ConfigError()` and `RetriableCommitFailedError()` are rejected by `java_forms`, since Java has no no-argument constructor for them.
    - `KafkaError` defines one `__reduce__` that rebuilds any error from its constructor arguments by name, with its cause, its notes and the attributes a caller added, so `copy` and `pickle` work. An error whose Java class has a field of a type that is not `Serializable` (`QuotaViolationException`'s `KafkaMetric`, `RecordDeserializationException`'s `ByteBuffer`s and `Headers`) does not pickle or deep-copy: its `__reduce__` raises `TypeError`, as Java's serialization throws `NotSerializableException`; `copy.copy` still works. The generator reads the field types from the Java sources.
  - Java's payload getters are methods (`RecordDeserializationError.topic_partition()`, `offset()`, `key_buffer()`, `value_buffer()`, `origin()`; `TopicAuthorizationError.unauthorized_topics()`). They return what the constructor was given, or the Java-given default `java_forms` filled for the matched overload (`TopicAuthorizationError(message="x").unauthorized_topics()` -> `set()`, since Java's `(String message)` passes `emptySet()`); an error from the core is constructed with the payload read from the FFI accessors of §4.
  - `CorrelationIdMismatchError`'s `request_correlation_id()` and `response_correlation_id()` read `-1` for an error from the core *(deviation: Java's class sits in `common.requests`, "not a supported API", so the Rust payload is crate-private and §4 gives it no C accessor; `-1` is a value Java's counter never assigns. Goes when the C FFI exposes them)*.
  - No `code()` and no `is_*` predicates: the type is the predicate (`except RetriableError`); a failure read through `KafkaFuture.get()` / `get_now()` arrives as `ExecutionError`, the type being `e.__cause__`'s, as Java's `ExecutionException.getCause()`. The FFI id is the private class attribute `_ffi_id` with one `id → class` table. Core -> Python: construct the class of the id, chained from its cause; an unknown id raises `KafkaError`. Python -> core: `type(error)._ffi_id`; the base `KafkaError` carries the core's id for a bare `KafkaException`, `UNKNOWN_SERVER_ERROR` (−1), which `UnknownServerError` owns in the table.
  - An error the user injects into a mock (`set_poll_exception`, `set_send_exception`, `error_next`, …) is raised again as the very same instance.
  - A Python exception that crosses the core (a listener's, a callback's, a serde's) comes back as the same object: the core carries it in a `LocalCallbackError` (`kafka_common_Error_local_callback`, the opaque pointer being the Python object) and the binding reads it back, so `except MyError as e: e is injected` holds, on the real clients as on the mocks.
  - A Rust panic caught at the C boundary is `IllegalStateError`, its message beginning `Rust panic caught at the FFI boundary in <function>`; through a `_cb` twin it arrives as that operation's failure.
- **Serialization**
  - *(deviation)* A serde is any callable accepting `**kwargs`. `Serializer(Protocol[T_contra])`: `__call__(*, topic: str, data: T_contra | None, headers: Headers | None = None, **kwargs: Any) -> bytes | None`, `data` being Java's name (`serialize(String topic, Headers headers, T data)`); `Deserializer(Protocol[T_co])`: `__call__(*, topic: str, data: memoryview | None, headers: Headers | None = None, **kwargs: Any) -> T_co | None`. Headers are always passed, as the `Headers` class. A parameter Java adds to `serialize` / `deserialize` later reaches the serde as one more keyword argument (Signatures). A serializer is called with the record's key or value as given, `None` included, and decides what null maps to, as Java's `KafkaProducer` calls it; a deserializer is not called for a null key or value, the record's field being `None`, as Java's `CompletedFetch` does. Why: Python's form of a single-method interface is a callable, so one shape replaces Java's `serialize` / `deserialize` overloads.
  - On every client a serde is a plain function: an `async def` one (or an object whose `__call__` is one) is rejected with `TypeError` where it is given *(why: no serde in the package does I/O, and an awaited serde would add a coroutine per record to `send()` and `poll()`. Goes when: a serde that does I/O, such as a Schema Registry serde, is translated; accepting one then is additive)*.
  - *(deviation)* Lifecycle is duck-typed: `configure(configs, is_key)` runs once after construction on the config route only; `close()` runs at client close, its exceptions logged, never raised; an absent method is a no-op. `Configurable` / `Closeable` are `@runtime_checkable` protocols for them, and `SerdeBase` is a no-op base with both. Why: a plain function has no lifecycle methods, so they are optional.
  - *(deviation)* Built-in factories in `confluent_kafka.common.serialization`, matching Java's serdes byte for byte: `bytes_serializer()`, `bytes_deserializer()` (an owned copy, made lazily), `memoryview_deserializer()` (views into the fetch batch), `string_serializer(*, encoding="utf_8")`, `string_deserializer(*, encoding="utf_8")`, `int_serializer(*, size=4)`, `int_deserializer(*, size=4)` (4 or 8: `Integer`, `Long`), `float_serializer(*, size=8)`, `float_deserializer(*, size=8)` (8 or 4: `Double` canonicalizing NaN like `doubleToLongBits`, `Float` keeping raw bits), `bool_serializer()`, `bool_deserializer()`, `uuid_serializer()`, `uuid_deserializer()` (`uuid.UUID` in Java's dashed form), `json_serializer()`, `json_deserializer()`. No others; another size raises `IllegalArgumentError`. Why: with serdes as callables, a ready-made one is a function that returns it, typed so that the client's type parameters are inferred.
  - Each factory is typed (`string_deserializer() -> Deserializer[str]`, `json_deserializer() -> Deserializer[Any]`) and returns a real Python callable, which the client calls like any other serde.
  - Supply by constructor argument (any callable or instance; a class raises `IllegalArgumentError(message="<key>: pass an instance, not the class — did you forget '()'?")`) or by config key `key.serializer`, `value.deserializer`, … (a dotted path or a class: resolved, no-arg constructed, then `configure(configs, is_key)`; an instance or an unresolvable name raises `ConfigError` at construction). A given argument wins and the config key is ignored.
  - Every record goes through a deserializer; there is no raw path. Serdes run eagerly on the caller's thread inside `send()` / `poll()` and raise from that call. A failing deserializer makes `poll()` raise `RecordDeserializationError` and leaves the position unmoved: `seek(partition=e.topic_partition(), offset=e.offset() + 1)` skips the record *(deviation: the core's poll moves the positions past the whole batch before Python deserializes; on a failure the binding seeks each partition back to its first record not returned, so the position ends where Java leaves it; until that seek lands, a timer-driven auto-commit can commit positions past records never returned. Goes when deserialization runs inside the core's fetch collection (`Deserializer_t`) or the core advances positions only past accepted records)*.
- **Configuration**
  - A client's configuration parameter, of a constructor or of a static factory, is `configs: dict[str, Any]` of Java's dotted keys, whatever Java names it *(deviation for `Admin.create`: Java names it `props` / `conf`. Why: one name for every client's configuration. Permanent)*; it is the one exception to Signatures' "one parameter named after the earliest-declared overload". A non-`str` key raises `ConfigError(name=…, value=…, message="Key must be a string.")`, as Java does. A value is checked against the key's `ConfigDef` type in the client's Java config class (`ProducerConfig`, `ConsumerConfig`, `ShareConsumerConfig`, `AdminClientConfig`, each with its SSL and SASL keys) as Java's `parseType` checks the object's type, and converted to the string the FFI takes; the core checks the value itself with Java's messages (Implementation over the FFI, exception 2). A `None` value for a key whose `ConfigDef` validator rejects `null` raises `ConfigError` with that validator's Java message, as Java's `ConfigDef.parseValue` runs the validator on an explicit `null` (`Range`: "Value must be non-null"; `ValidString`: "String must be one of: …"; `CaseInsensitiveValidString`: "String must be one of (case insensitive): …"; a `ValidList` that refuses nulls: "Configuration '<key>' values must not be null."); any other `None` reaches the core as not set, so the core's default applies *(deviation: for a key without a validator Java holds `null`. Why: the FFI takes every value as a string and has no null. Goes when: the FFI takes typed values)*.
  - The serializer keys of the client's own role never reach the core: a producer keeps `key.serializer`, `value.serializer`, `serializer.encoding`, `key.serializer.encoding` and `value.serializer.encoding`, a consumer or share consumer the deserializer equivalents. They keep Java's names and take a dotted path or a class (§2's no-class rule binds the core's keys). Every other key reaches the core under the core's name (`partitioner.type`), including keys the core does not implement.
  - Unknown keys are accepted and only the core reports them, in one INFO line listing the unused keys. `interceptor.classes` and `partitioner.class` are not core keys, so they are unknown keys. `partitioner.type` is passed verbatim: `ConsistentRandomPartitioner` (the default), `Murmur2RandomPartitioner` or `RoundRobinPartitioner`; the core rejects any other value with `ConfigError`. The share consumer rejects the keys Java's `ShareConsumerConfig` rejects.
  - `group.id` is optional; without it every method in which Java's `AsyncKafkaConsumer` runs `throwIfGroupIdNotDefined()` raises `InvalidGroupIdError` with Java's message: `subscribe`, `commit`, `commit_nowait`, `committed` and `group_metadata`.
  - No config value is a callback and no constructor takes an error callback or a logger: operation errors raise or fail their future; everything else is a record on the `confluent_kafka.*` Python loggers.
- **Threads and callbacks**
  - The `send()` callback runs on a background completion thread (`KafkaProducer`) or the event loop (`AsyncKafkaProducer`), never on the caller's thread; a producer's callbacks run one at a time in completion order; a raising callback is logged by the core once, with Java's message, not propagated; on `MockProducer` and `AsyncMockProducer` it runs inside the call that completes the record and propagates out of it, as Java's mock does. The record's future completes, and `flush()`, the transaction-ending calls and `close()` return, only after the callbacks of the records they cover have returned, as Java fires callbacks before completing the future. By rule 3 the asyncio producers also accept an `async def` callback, awaited on the loop; the sync producer rejects a coroutine callback with `TypeError`.
  - The sync `KafkaAdminClient` has one daemon pump thread, which runs the client's queued callbacks (`__execute_callbacks`) when its notify hook fires, as Java's admin thread completes futures: the `then_apply` functions and `when_complete` actions of its futures run there, and a blocking action blocks the client's callbacks, as in Java. At `close()` it stops after its current pump, then `_destroy` fires what is still pending. `AsyncKafkaAdminClient` runs them on the event loop.
  - `ConsumerRebalanceListener` methods, the `commit_nowait()` callback and the share consumer's acknowledgement-commit callback run on the caller's thread, inside the waiting call that delivers them (`poll`, `commit`, `unsubscribe`, `close`, …), and the rebalance does not advance until the listener returns (`consumer-threading.md` §31). By rule 3, on the async consumer a listener method may be `async def` and is awaited on the event loop. An exception a commit callback raises propagates out of the call that delivered it, as Java calls `onComplete` without a `try` (`poll()` wraps it in a `KafkaError` unless it is one); the callbacks queued behind it run inside a later call. `MockConsumer` runs it inside `commit_nowait()`, as Java's mock does. By rule 3 the `commit_nowait()` callback may also be `async def` on the async consumer, awaited on the loop inside the delivering call, callbacks still starting one at a time in commit order.
  - A listener may call back into its consumer through the core's `ConsumerHandle` (`consumer-threading.md` §31): `commit`, `commit_nowait`, `seek`, `seek_to_beginning`, `seek_to_end`, `pause`, `resume`, `position`, `committed`, `beginning_offsets`, `end_offsets`, `offsets_for_times`, `current_lag`, `partitions_for`, `list_topics`, `group_metadata`, `assignment` and `paused`, each with its `Duration` overloads (the handle's `_with_timeout` forms), and `metrics()` and `wakeup()`, which work there as in Java (`metrics()` takes no `acquire()`, `wakeup()` is callable from anywhere) although the handle has no form of `metrics()`; the call succeeds while the outer call waits, on the mocks too. The handle has no form of `assign`, `subscribe`, `subscription`, `unsubscribe`, `poll` or `close` (KIP-1306's `RebalanceConsumer` has none), so inside a listener they raise `ConcurrentModificationError` with `KafkaConsumer`'s message *(deviation: Java's listener may call them; goes when the handle has them)*; the mocks allow them, as Java's reentrant mock does.
  - An exception a listener or callback raises comes back from the delivering call as Java's `maybeWrapAsKafkaException` returns it: from `close()`, wrapped in `KafkaError("Failed to close kafka consumer")` with the original as `__cause__`, except a `KeyboardInterrupt`, which comes back as it is; elsewhere, a `KafkaError`, a `KeyboardInterrupt` or a commit callback's exception comes back as it is, and anything else wrapped as `KafkaError("User rebalance callback throws an error")` with the original as `__cause__`; `poll()`'s wrap of a commit callback's exception is a `KafkaError` whose message is that exception's `toString()` form.
  - `wakeup()` is a plain `def` on both classes, callable from any thread or signal handler: the in-flight or next waiting call raises `WakeupError`, and the call after proceeds normally (`consumer-threading.md` §11).
  - Ctrl+C during any client's waiting call re-raises `KeyboardInterrupt`, a consumer first waking itself and letting the call end; cancelling the task awaiting an async call does the same with `CancelledError`. An interrupted `poll()` seeks the consumer back to the records it did not hand out, so none is skipped.
  - `KafkaProducer` and `KafkaAdminClient` are thread-safe; `close()` frees the native handle only after every call using it has returned. `KafkaConsumer` and `KafkaShareConsumer` are not: a call while another thread is inside the instance raises `ConcurrentModificationError`, `wakeup()` and `metrics()` excepted, as Java leaves both outside `acquire()`. The async classes follow the same rule per event loop.
  - By rule 3 an asyncio client is bound to one event loop, the one running when it is constructed or else the loop of its first async call; its callbacks and its futures' completions run on that loop, and a call from another loop raises `RuntimeError`, as asyncio's own primitives do. `close()` alone may be called from another loop once the bound loop is closed, so a client whose loop ended can still be closed; Java has no loops and `close()` always works. For several threads each with its own loop, use one asyncio client per loop, or the sync client, which is thread-safe as Java's.
  - On an FFI-backed client `close()` releases every callback the client holds; a `Mock*` client does what Java's mock does (`MockConsumer.close()` only marks it closed).
- **Implementation over the FFI**
  - The client bases, the `Kafka*` classes and their async peers call the FFI. Every other class — value types, records, enums, errors, the Options and Result classes, `CloseOptions`, the serdes, and the `Mock*` classes with their async peers — is a direct Python translation of its Java source (the FFI's `Mock*` entry points serve the C binding); a mock does what Java's mock does for every method of its base, overriding it or supplying the private hooks the base's methods call; a base docstring note that holds only for the FFI-backed client says so. The `Mock*` classes translate the Java internals they use as private helpers (`SubscriptionState`; for `MockAdminClient` `CoordinatorKey`, `ConsumerProtocol`, `Time`; its futures are `_KafkaFutureImpl`s, Futures) *(temporary. Why: the FFI's mocks cannot keep Java's mock behaviour or hold the user's Python objects. Goes when: the FFI's mock entry points can; the `Mock*` classes then call the FFI like the `Kafka*` ones and the private translations go)*. In a `Mock*` class and those private translations, Java's `synchronized` is a re-entrant lock (`threading.RLock`) for each object whose lock Java takes: a `synchronized` method takes the instance's lock, `synchronized (x)` takes `x`'s own (`MockConsumer`: `_lock`, and `_poll_tasks_lock` for `synchronized (pollTasks)`), held for the method's body or the block; on an async peer it is released before every `await` and taken again after (`AsyncMockConsumer.rebalance`). A `static synchronized` method, `wait`, `notify`, or `synchronized` on an object passed in stops generation with an error until a rule is decided. `KafkaMetric` uses the `lock` it is given as Java's `synchronized (this.lock)` when it is a context manager (`threading.Lock`, `threading.RLock`), and locks nothing otherwise: Java takes the lock of the `Sensor` that writes the metric, which only the Rust core has.
  - Python adds no FFI entry points. Each Java overload of an FFI-backed class calls the entry point whose name §2 (Rust name) and §4 (C prefix) derive for it; a static factory derives from the Rust type that defines it (`Admin.create` -> `kafka_admin_AdminClient_create`); overloads §2 folds into one Rust method with `Option` parameters share one, and Python passes absent arguments as null.

    | `metrics()` | a list of `dict`s with `name`, `group`, `description`, `tags`, `value` | `Producer_metrics`, `Consumer_metrics` |

  - The binding reimplements no core logic and repeats no core check: a value the core computes is read from the core (`ConsumerRecords.next_offsets()` from `kafka_consumer_ConsumerRecords_next_offsets`). Python only converts values for the FFI, checks keywords and forms (`java_forms`), runs the serde route, constructs the value classes, and makes no check of its own, with these exceptions:
    1. A negative timeout raises `IllegalArgumentError`, with the message the Timeouts rule gives (Signatures). *Why:* the FFI's `timeout_ms` uses a negative value for Java's untimed overload, so a caller's negative timeout cannot cross it. *Goes when:* the FFI carries "no timeout" separately and the core checks the sign.
    2. A non-`str` config key raises `ConfigError(name=…, value=…, message="Key must be a string.")`; a value is checked against the key's `ConfigDef` type as Java's `parseType` checks the object's type (a wrong Python type raising `ConfigError` with Java's message), a `None` for a key whose validator rejects `null` refused with that validator's message (Configuration) and converted to the string the FFI takes (`True` -> "true", a list joined with commas, `None` left out); the core checks the value itself (ranges, enums, boolean text) with Java's messages (Configuration). *Why:* the FFI takes every config value as a C string, so only Python sees the object's type. *Goes when:* the FFI takes typed values.
    3. A call on a closed client raises `IllegalStateError` with the Java client's own closed message (`KafkaProducer`: "Cannot perform operation after producer has been closed"; `KafkaConsumer`: "This consumer has already been closed."; `KafkaAdminClient`: "Cannot accept new calls when AdminClient is closing.") (Behaviour with no other home). *Why:* `close()` frees the native handle, so nothing after it can reach the core. *Goes when:* the native object outlives `close()` and the core reports the closed state itself.
    4. A `None`, where Java's method — its body, an overload it forwards to, or a private helper it calls directly — checks it for null and throws, raises Java's error and message as Types spells them (a `NullPointerException` as `TypeError` naming the parameter, `null` as `None`): `partitions_for` -> `TypeError("topic must not be None")`, `assign` -> `IllegalArgumentError("Topic partitions collection to assign to cannot be None")`, `pause` -> `TypeError("partitions must not be None")`, `send_offsets_to_transaction` -> `IllegalArgumentError("Consumer group metadata could not be None")`, `subscribe(topics=…, callback=None)` -> `IllegalArgumentError("RebalanceListener cannot be None")`; where Java dereferences the null with no check of its own (`commit(offsets=None)` is `new HashMap<>(null)`, `close(option=None)` is `option.timeout()`), `TypeError("<param> must not be None")` too. The checks run in Java's order within the method. The mocks check where Java's mocks check, and a mock whose Java NPE comes later raises it there (`MockProducer(cluster=None)` fails at the first `send`). A null the FFI cannot carry that Java reads only later, on its own thread, failing the returned future (an admin RPC's group id, an election type, an options field), is reported by the call itself with the same `TypeError` *(deviation: Java's caller sees it at `get()`)*. *Why:* §4 lets an entry point assume its required pointers are not NULL, so a NULL would be undefined behaviour, not Java's error. *Goes when:* the FFI accepts NULL there and the core reports Java's error.
    5. `group_metadata()` without `group.id` raises `InvalidGroupIdError` (Configuration), and so does `committed(partitions=None)` before its null check, in Java's order (`throwIfGroupIdNotDefined()` precedes the dereference). *Why:* the core makes the `group_metadata()` check as a panic (§12.5), which reaches Python as the FFI guard's `IllegalStateError`, not Java's error, and its own group check of `committed` runs only when the call reaches it. *Goes when:* the FFI reports both as `InvalidGroupIdError`.

    **Order.** On an FFI-backed class Python checks the closed state first — after the keyword, form and `str` checks, which concern the call's shape, not the client's state — because the handle is gone after `close()`; the other checks follow where Java has them — in Python, the C binding, the FFI or the core. So on a closed client `partitions_for(topic=None)`, `send_offsets_to_transaction(…, group_metadata=None)` and `poll(timeout=-1)` report the closed client where Java reports the argument, and a negative timeout on a second `close()` returns silently where Java's checks the sign first *(deviation)*. The mocks keep Java's mocks' order. These deviations go only when the native object outlives `close()` and the core reports the closed state itself; moving an argument check into the FFI does not remove them. The Python null checks run before the core's own checks, so a consumer without `group.id` reports a null collection where Java reports `InvalidGroupIdException` (Java's group check sits at the top of `subscribeInternal`); accepted until the FFI reports Java's error itself.
  - An overload whose derived entry-point name is not in the header is not generated (a parameter, a method, or a whole class or family when all its overloads are missing), and `java_forms` and the stubs leave it out. Generation lists each overload it leaves out, with the entry-point name it looked for, in the module docstring. A mock does not generate what its base class does not. A value class the client builds from core data treats each FFI accessor as an entry point: a getter whose accessor is missing, and the Java constructor form that sets its field, are not generated, and are listed in the module docstring.
  - The Python method calls the entry point of the overload the given arguments select (by which are given, or `isinstance` for a union-typed parameter). A method whose entry point has a `_cb` twin calls that twin and waits for its completion on the sync class, awaits it as `async def` on the async peer (Class family); one whose entry point has no twin calls the plain form and is a plain `def` on both. Each `_cb` function's rustdoc states, self-contained, where its completion is queued.
  - Within what is generated, a mock implements every method and constructor argument Java's mock implements: `MockProducer(cluster=…, partitioner=…)` uses the cluster for `partitions_for()` and the partitioner to choose partitions, calling their Java methods by snake_case name. A mock method raises only where Java's mock throws.
  - A blocking call submits the `_cb` twin and waits for its completion in short slices, never in the blocking C form, so Ctrl+C is seen; the exceptions are `KafkaProducer.send()` from inside a producer's callback, which hands its record over through the blocking C send, because the completion it would wait for is queued on the thread it runs on (Behaviour with no other home), and a call from inside a consumer's listener, which waits on the `ConsumerHandle`'s blocking form, because the listener runs inside the consumer's own waiting call, which cannot drain a queued completion meanwhile (the conversions table). The completion is queued on the client, which signals it through `__set_callbacks_notify`, and runs when `__execute_callbacks` is called: by the waiting call itself on the consumer (its callbacks run on the caller's thread, as Java's), by the client's completion thread on the producer and the admin client (one thread per client, never a second one, as Java's I/O and admin threads). An async call registers the same `_cb` twin and awaits an `asyncio.Future`; the notify hook schedules `__execute_callbacks` on the event loop through `loop.call_soon_threadsafe`, so callbacks run on the loop.
- **Behaviour with no other home**
  - `Header` and `Headers` are the translated classes in `confluent_kafka.common.header`, with Java's methods: `Header(key=…, value=…)` *(deviation: Java's concrete class is the internal `RecordHeader`, so a user needs a public class to build one)*; `Headers(headers=…)` takes `RecordHeaders`' three constructors, `()`, `(Header[])` and `(Iterable<Header>)`, as one keyword with one stub each *(deviation: Java's concrete class is the internal `RecordHeaders`, whose public constructors are how Java users build headers)*; `Headers` is mutable until the record is sent and read-only after, as Java's `KafkaProducer` seals it ("RecordHeaders has been closed."), the producer sealing it once the serializers have run, before the core's metadata wait *(deviation: Java seals after that wait, so a send that times out on metadata leaves Java's headers writable; here the serializers run on the caller's thread before the core is entered)*; a fetched record's headers stay writable, as Java's `CompletedFetch` leaves them. Header values handed out are `memoryview`s (into the fetch batch for fetched records) or `None`; `headers()` is an empty `Headers` when there are none, never `None`. §14's no-copy rule covers header values too. `Header` and `Headers` pickle and deep-copy, a value as its bytes *(deviation: Java's `RecordHeader` and `RecordHeaders` are not `Serializable`. Why: a record carries its headers, and Python's default pickling of a record needs them to pickle)*; an error that holds a `Headers` (`RecordDeserializationError`) still refuses, as Errors says.
  - `ProducerRecord(value=None)` is sent as a null value (a tombstone), never as `b""`.
  - `close()` twice is harmless. On an FFI-backed client any other call after it raises `IllegalStateError`, the admin client's RPCs included *(deviation: Java's `KafkaAdminClient` returns the Result and fails its futures with that `IllegalStateException`. Why: the handle is freed, so the call cannot reach the core and has no Result to return. Goes when: the native object outlives `close()`, as for the other closed calls)*, except the consumer's `wakeup()`, which does nothing once closed, as Java's *(deviation for the producer's `flush()` and `partitions_for()` and for `metrics()` on the producer and the consumer: Java makes no closed check there, since its object outlives `close()`; here the native handle does not)*. A `Mock*` client answers after `close()` as its Java mock does.
  - Async sends that returned before a transaction-control call belong to it (`producer-transactions.md` §13).
  - Each `Kafka*` client and its async peer logs one WARNING on its `confluent_kafka.<module>` logger when constructed: "The Python client is in preview and not yet recommended for production use. The public API is not stable before the GA release and may change. We welcome your feedback while the design is still open"; the mocks log nothing *(deviation: Java logs no status warning. Why: the client is in preview. Goes when: the Python client is GA)*.
  - A call made from inside a `send()` callback, or from a `then_apply` function or `when_complete` action of a record future, runs on the producer's completion thread, as Java's runs on its I/O thread. There `send()` hands its record over on that thread through the blocking C send, waiting up to `max.block.ms` for metadata as Java's does; it raises what Java's `doSend` rethrows, and an `ApiException` (the metadata `TimeoutError`) goes to the record's callback and future. `flush()` raises Java's `KafkaError("KafkaProducer.flush() invocation inside a callback is not permitted because it may lead to deadlock.")`. `close()` and `close(timeout=…)` log Java's warning and close as `close(timeout=0)`, returning at once. `init_transactions`, `send_offsets_to_transaction`, `commit_transaction`, `abort_transaction`, `begin_transaction` and `partitions_for` raise `TimeoutError` after `max.block.ms`, the operation itself possibly still completing *(deviation: Java's raise at once when the producer's state is wrong, Java's `beginTransaction` never waits, and Java's `partitionsFor` answers at once from cached metadata; Java's other waits time out after `max.block.ms` as here. Why: these calls' completions are queued on the completion thread, which the callback blocks. Goes when: the FFI gives them a form that completes on the calling thread)*.
- **Tests and typing**

- **Stability**
  - The interface check compares the generated public signatures (names, parameters, defaults, types, stubs; member order aside) with the previous release's.
  - The client moves from development to preview releases to GA. During development, a new or changed rule may change existing interfaces from one PR to the next. In preview releases an interface may change even in a minor release, and the interface check only warns. After GA, a change to an existing interface fails the interface check in a minor release and warns in a major release.
  - A rule change that alters an existing interface says so; otherwise a new Java overload only adds optional keyword parameters or widens a union, and adds one stub, and nothing existing is renamed or removed silently. An overload left out for a missing FFI entry point is added when the entry point arrives, as new optional keyword parameters or a new method — an additive, non-breaking change.
  - After the client's first major release, when Java renames a parameter, or the field behind a constructor keyword (the same method or setter, at the same position, with the same type, under a new name), the keyword takes Java's new name and keeps the old one as a deprecated alias: `java_forms` accepts the old keyword as the same parameter with a `DeprecationWarning`, and the stubs gain one extra stub per overload under the old name, marked `@deprecated`, so type checkers and editors warn; giving both names is rejected as two forms are. The old names are read from the release baseline, never kept by hand. The alias stays until the next major version.
  - If Java's Javadoc starts to say that a method may return null, the Python return type gains `| None`. This is allowed in a minor release and only warns, because the call could already return `None` and the Python code does not change. A return type is never made narrower in a minor release.
  - A method or overload Java deprecates after this client's first major release is kept and deprecated as in Class family; a method Java removes is kept, deprecated, until the next major version.

## JavaScript Binding Conventions

The JavaScript client, npm package `@confluentinc/kafka-javascript` in `javascript/`, is built only on the C FFI of §4, through a Node-API addon. Its surface and implementation are generated from this section, the Java source, the C FFI header and the previous release's interface; the same inputs give the same result on every run. The source is TypeScript, and `tsc` emits the published `.js` and `.d.ts` files. "As in Python (Group)" means that the named group of the Python Binding Conventions applies in its JavaScript form. A number such as (Q15) names the question of the new-binding kickstart questions (Confluence page 6335693600) whose JavaScript answer (page 6339855190) decided the rule. An item under "Not decided yet" stops the work: the agent asks, and invents nothing for it.

- **General rules**
  - Rule 1: Java decides the content, and JavaScript decides only the form, through the rules below, as in Python's rule 1. A change to content is marked *(deviation)*, with its Why, and with a Goes when if it is temporary, and every deviation is agreed in review. A useful JavaScript language feature from 1.x may be kept, marked *(js-only)* (Q1, Q65).
  - Rule 2: Java's standard types map to JavaScript types by the fixed table in Types.
  - Rule 3: where Java has nothing, the standard JavaScript convention applies, marked *(js-only)*.
  - TypeScript first: the types are erased at run time, and a plain JavaScript caller never sees them, so the run-time checks stay: the JavaScript rows of the binding's own checks (Implementation over the FFI), the form check (Q15) and the number checks (Q22). The one exception is a constructor that Java doesn't make public, which only the published types guard (Class family) (Q4, Q16).
  - Every rule that shapes what a caller writes or gets back is checked against TypeScript first, when it's added or changed and again before code is generated from it. Its JavaScript form is written as TypeScript, and it says what `tsc` catches for a TypeScript caller and what a run-time check must still catch for a plain JavaScript caller. An agent that finds such a rule that doesn't say both stops and asks, as for an item under Not decided yet.
  - The Java source is the Apache Kafka release in `kafka/`, the one the Rust core is built from (Q2).
  - Code is generated wherever it can be, and anything that has to differ is marked *(deviation)*. Generated and hand-written code alike is TypeScript source, and the hand-written helpers live in `src/internal/` (Q4, Q13).
- **Scope**
  - In scope are the client families and types of Python's Scope, limited to what the C FFI exposes: the producer, consumer and admin families, every public type reachable from them, their nested types, the config constants and the key-name classes. The share consumer is out, because the FFI has none. As in Python, the assignors, interceptors, partitioner implementations, the `ConfigDef` machinery and `CommonClientConfigs` aren't translated (Q5).
  - Nothing is added except by a JavaScript standard convention (rule 3) or as a deviation. The additions Java lacks are all *(js-only)*, and each one is on the list of invented names (Layout and modules): `[Symbol.asyncDispose]` on the clients, `[Symbol.iterator]` where Java has `Iterable`, the built-in serde factories such as `stringSerializer()`, `TopicPartitionMap`, the `*Args` option types, and `toJSON()` on value classes, whose output is frozen once released (Q6).
  - Left out, as in Python, are a producer `poll()`, `clientId()`, an event emitter, and `connect()` and `disconnect()`: a client is ready once it's constructed, as in Java, and `close()` replaces `disconnect()`. KafkaJS-style `run()` helpers, an async iterator over `poll()` and `AbortSignal` options are GA candidates, not in the preview, and an `AbortSignal` would only ever come alongside `wakeup()`, never in its place (Q6).
  - The preview offers one API, shaped like Java's. Whether the client also gets a KafkaJS-style API, as 1.x has beside its callback API, is decided later by the team, so an agent builds none of it (Q1, Q6).
  - A Java form whose only extra parameter has a type that isn't translated is left out *(deviation. Why: a placeholder typed `unknown` checks nothing)*. Where a signature can't be dropped, the type is a placeholder, as in `export type Partitioner = unknown`, and so are `Cluster` and `MetricConfig`. A type that Java doesn't make public, such as `Time`, is `unknown` *(deviation, as in Python)* (Q30).
  - Nothing that Java has deprecated by this client's first major release is generated, as in Python (Class family) (Q71).
- **Layout and modules**
  - In `javascript/`, `src/` holds the TypeScript source, with one folder per Java package and `clients` dropped (`src/consumer/`, `src/common/acl/`), and `src/internal/` holds the hand-written helpers and the addon's generated types (Q4). `native/` holds the addon and its build file, node-gyp's `binding.gyp`, and the build runs only there, so npm never compiles on install. `dist/` holds `tsc`'s output, is git-ignored and is the only code published. `npm/` holds one folder per platform package, and `test/`, `examples/` and `bench/` sit beside them (Q13, Q73).
  - Each Java class is one generated snake_case file in its package's folder, which also holds its nested classes (`src/common/topic_partition.ts`). Each package has an index that re-exports its classes, and users import from the package, never from a file: a deep import fails with Node's `ERR_PACKAGE_PATH_NOT_EXPORTED` (Q13).
  - Each Java package has one import path, such as `@confluentinc/kafka-javascript/consumer` and `@confluentinc/kafka-javascript/common/acl`. The root exports only Java's built-in errors and `Duration`. The `exports` field of `package.json` lists only the package paths, so internal files need no `_` prefix, and the folders behind the import paths also exist in the package, for TypeScript setups that don't read `exports` (Q7, Q72).
  - The package is CommonJS only, as 1.x is. `tsc` emits CommonJS with `module: nodenext`, `package.json` has no `"type": "module"`, and each `exports` entry has the `types` and `default` conditions. ESM apps still use named imports, such as `import { KafkaProducer } from '@confluentinc/kafka-javascript/producer'`, because Node finds the names in `tsc`'s CommonJS output, through `export { }` and `export *` alike. One build means one copy of each class, so `instanceof` works across `import` and `require` (Q15), and a CommonJS Jest test can load the client and `jest.mock()` it on Node 22, which an ESM-only package breaks. The indexes re-export only with `tsc`'s own `export { }` and `export *` forms, because Node finds names only in the patterns it knows. For a TypeScript caller, `tsc` checks the imports under `node16`, `nodenext` and from an ESM file. A plain JavaScript caller that imports a name the package lacks gets Node's `SyntaxError: Named export '…' not found` at load, so no run-time check is needed (Q13).
  - A name that JavaScript invents is kept once released. If Java later adds an item of that name, Java's item gets another JavaScript name, chosen with the owner when it happens, as in Python (Modules). The list of invented names also holds `NODE_DEBUG=confluent_kafka`, the `diagnostics_channel` name once it exists, the deprecation warning codes and the platform package names, such as `@confluentinc/kafka-javascript-linux-x64-gnu`. An invented options type ends in `Args` (Q14, Q72).
- **Names**
  - Types are PascalCase. A class name's `Exception` suffix becomes `Error`, and nothing else changes, so `InvalidRegularExpression` keeps its name, and so does `Headers`, although JavaScript has a global of that name (Q8, Q33).
  - Methods keep Java's camelCase names, a leading `get` included, as in `offsetsForTimes()` and `getMostSignificantBits()`. Option keys are Java's parameter names, taken from the interface's declaration, as in Python (Signatures) (Q9).
  - A static member sits on the class that defines it, as in `Topic.GROUP_METADATA_TOPIC_NAME` and `Uuid.randomUuid()`. A constant `List` is a frozen array, and a constant `Set` is a read-only set whose `add` and `delete` throw. `Admin.create()` is on a runtime object named after the interface, beside the TypeScript type of the same name (Q10).
  - A nested Java type is a static member of its class, as in `CloseOptions.GroupMembershipOperation.LEAVE_GROUP`, and a TypeScript namespace with the class's name holds its types (Q11).
  - A static method and an instance method with the same Java name both keep it, as in `CloseOptions.timeout({ timeout })` and `options.timeout()` (Q17).
- **Class family**
  - A data object has public `readonly` fields, set once when it's built. The data classes are the records, `TopicPartition`, `OffsetAndMetadata`, `RecordMetadata`, `Node` and the admin description classes. The generator keeps their list, which is frozen at GA. In a data class, a Java method that takes no arguments and returns a value becomes a field, as in `tp.topic`. Client objects, option classes with read and write pairs, classes that change (such as `Headers`) and names that start with `get` keep methods. The test in one line: if reading it twice can give different answers, cost real work or fail, it's a method *(deviation. Why: the JavaScript guides read data through plain fields, 1.x and KafkaJS already write `tp.topic`, and a field can't fail silently through a forgotten `()`. Permanent)* (Q9). Each data class calls `Object.freeze(this)` at the end of its constructor, so a write such as `tp.topic = 'x'` throws `TypeError` in strict-mode code, which includes ES modules and classes, and does nothing in sloppy-mode code. The spike measures the cost for `ConsumerRecord` (Q9).
  - A `TopicPartition` is frozen when it's created, so a key can't change after it goes into a map (Q25).
  - A Java constructor that isn't public becomes a `private` TypeScript constructor, or a `protected` one where Java's is protected. The binding builds the object through one `@internal` static factory per class, such as `CreateTopicsResult.internalCreate(futures)`, which `stripInternal` removes from the `.d.ts` files. Unlike Python, nothing checks this at run time; CI compiles a test against the published `.d.ts` files instead (Q16).
  - A Java abstract class, such as `AbstractOptions`, becomes a TypeScript `abstract class`, so `tsc` refuses `new`, and Java's abstract methods stay `abstract`. For plain JavaScript, its constructor throws `TypeError` when `new.target` is the abstract class itself, as Python raises `TypeError`. An abstract error class is only for catching and has no FFI id (Q16, Q32).
  - Where Java takes a value class, JavaScript takes only an instance of it, and a plain object throws an error with a hint. Java's `Map` and `Properties` constructors become one form with the key `configs`, which also takes the bare map (Signatures). Records are built through their public constructors (Q16).
  - The option classes take one keyed object in their constructor, with one key per setter field, named after the Java field, as in `new CreateTopicsOptions({ timeoutMs: 5000, validateOnly: true })`. They are the `*Options` classes, `CloseOptions`, `ListConsumerGroupOffsetsSpec` and `MockAdminClient.Builder`, and such a class gets this constructor even without a public Java constructor, as `CloseOptions` does *(deviation: Java builds them only through their setters. Why: one call builds a configured object, and the setters stay, so Java's chain works too)*. After construction, each given key, `null` included, calls its setter in a fixed order, not the order the user wrote: the parent's fields first, then Java's field order, and a setter that reads a field runs after the one that sets it. A missing key leaves Java's starting value, and the FFI gets a `set_<field>` call only for the setters that ran. The starting values are documented with `@defaultValue`. Which classes qualify, the key names and the rule for a field with several setters follow Python's rules. Other classes keep only Java's constructors, as in `new NewTopic({ name, numPartitions, replicationFactor }).configs({ 'cleanup.policy': 'compact' })` (Q19).
  - A Java getter and setter pair with one name is one method. Called with no argument, it reads, as in `opts.timeoutMs()`; called with one argument, it sets and returns what Java's setter returns. The setter takes the value on its own or the options object, as in `opts.timeoutMs(1000)` or `opts.timeoutMs({ timeoutMs: 1000 })`, and the setter of a config map also takes the bare map. A reader with its own Java name keeps it, as in `shouldValidateOnly()`. `null` sets Java's null. `timeoutMs(undefined)` and `timeoutMs({})` throw `TypeError`, and a method that only reads throws `TypeError` when it's given any argument. There are no accessor properties (Q17).
  - An enum is a class with frozen instances, carrying Java's methods and fields plus `name()`, `ordinal()`, `values()` and `valueOf()`. `toString()` and `toJSON()` return the name, and values compare with `===`. There's no TypeScript `enum`, no string values and no closed string union in a returned type (Q12, Q69).
  - Generic classes keep Java's letters. A method's own type parameter stays generic, a self type becomes `this`, and the records are covariant through `out`. An omitted or `null` key or value binds `never`. Unlike Python, a `*Result` class has no marker for the kind of client, because there's no synchronous family (Q26).
  - TypeScript infers the type arguments from the serdes, and no code, test or doc writes them, except for a mock built without serdes. An omitted serde binds `KafkaProducer<Uint8Array, Uint8Array>` and `KafkaConsumer<Buffer, Buffer>` (Q27). In plain JavaScript, a string key or value given to a client without a serializer throws `TypeError`, with a message that points to `stringSerializer()`, because a string can't reach the FFI as bytes (Q24, Q27).
  - Each method of an interface that the user implements takes one object with Java's parameter names, as in `onPartitionsRevoked({ partitions })`, and a callback is a function such as `({ metadata, exception }) => void`. Java's abstract methods are required, and its `default` methods are optional: when one is missing, the binding passes NULL and the FFI's adapter applies Java's default, so a missing `onPartitionsLost` calls `onPartitionsRevoked`. There's no JavaScript helper class. The binding writes a JavaScript default only where the FFI can't take NULL, and for serdes, which it runs itself, so a missing serde `close()` does nothing (Q28).
  - A client interface, `Producer`, `Consumer` or `Admin`, becomes a TypeScript `interface`, and a runtime object of the same name holds its statics, such as `Admin.create` (Q10). An interface the client hands out, such as `Metric`, and a multi-method interface the user implements, such as `ConsumerRebalanceListener`, become TypeScript `interface`s too, and `Runnable` becomes `() => void`. The binding doesn't check at run time that a user's object has the required methods. The addon passes NULL for a missing one to the FFI's `_err` twin, such as `kafka_consumer_ConsumerRebalanceListener_new_err`, never to the plain entry point, which has no error slot and aborts the process on a NULL, and it turns the FFI's `LocalNullPointerError` ("on_partitions_revoked must not be null") into a `TypeError` (Q28, Q36).
  - Java's JDK interfaces follow a fixed table, as in Python, and an interface missing from it stops generation until it gets a row (Q29). `AutoCloseable` and `Closeable` become `close(): Promise<void>` plus `[Symbol.asyncDispose]`, so `await using` works, and there's no `[Symbol.dispose]`, because a synchronous dispose can't wait for `close()`. `Iterable<T>` becomes `[Symbol.iterator]()`, without Java's `forEach` and `spliterator`. `Comparable<T>` keeps `compareTo()`, and `equals` and `hashCode` stay methods. `toString()` keeps Java's format, with JavaScript's spelling of values (Q37). `Future` becomes `KafkaFuture` (Q44), and `Serializable` and `Principal` aren't translated. The docs say that when an `await using` block throws and `close()` throws too, JavaScript raises a `SuppressedError`.
  - A client has `close()` and `[Symbol.asyncDispose]`, so `await using` closes it (Q21).
  - A map keyed by `TopicPartition` is a `TopicPartitionMap` *(js-only. Why: JavaScript has no value equality for map keys)*. It wraps a `Map` keyed by a string such as `'orders:3'`, whose separator can't occur in a topic name, and keeps each original `TopicPartition`, so `keys()` and `entries()` return `TopicPartition` objects. It doesn't extend `Map`, so `instanceof Map` is false, and it has a `toJSON()` (Q25).
  - Where Java takes a `Collection`, `List` or `Set`, JavaScript takes any iterable, such as an array, a `Set` or a generator, and a bare string where Java takes `Collection<String>` throws `TypeError('topics must be an iterable of strings, not string')`, as Python's guard does. Where Java takes a map keyed by `TopicPartition`, as `commitSync({ offsets })` and `sendOffsetsToTransaction` do, only a `TopicPartitionMap` is taken, and a plain `Map` throws `TypeError` with a hint. A map keyed by strings may be a `Map` or a plain object. A `Set<TopicPartition>` that the client returns, as from `assignment()`, is a `TopicPartitionSet`, the set form of `TopicPartitionMap`, which matches by value *(js-only, as `TopicPartitionMap`)*. A returned collection is a new object that the caller may change, and constants are frozen (Q10, Q25).
- **Futures and waiting**
  - A method returns a Promise if and only if the entry point it calls has a `_cb` twin in the C FFI header (§4), so the split matches Python's. From JavaScript, the binding calls only `_cb` forms, accessors and constructors, never a blocking C function. An admin call returns its `*Result` at once, holding a future per key. Constructors are synchronous, as in Java. There's no synchronous family and no `Async*` name. A custom check fails the build when a public method returns a Promise but its entry point has no `_cb` twin, or the other way round (Q41, Q74).
  - Java's names stay, `commitSync()` and `commitAsync()`, and the same rule covers any other `xSync` and `xAsync` pair. Both return Promises. `commitSync()` settles when the broker answers, and as in Java it retries until it succeeds, fails with an error that can't be retried, or runs out of time. `commitAsync()` settles once the core has taken the commit, and the broker's answer goes to its optional `callback`, which runs inside the next waiting call, such as `poll()`, `commitSync()` or `close()`. Without a callback, a failed commit isn't reported, as in Java. Both must be awaited, because a commit that isn't awaited keeps the consumer busy. The docs say that both return Promises and that only `commitSync()` waits for the broker (Q43).
  - Java's `Future<T>` and `KafkaFuture<T>` are one `KafkaFuture<T>` class, `send()`'s included, with Java's `KafkaFuture` members in Java's order *(deviation, as in Python (Futures): Java's `send()` returns a plain `Future`)*. `get()` and its timed form return Promises, while `getNow({ valueIfAbsent })`, `isDone()`, `isCancelled()` and `isCompletedExceptionally()` are synchronous. The rest are `thenApply()`, `whenComplete()`, `toCompletionStage()`, which returns a native Promise, and the statics `allOf()` and `completedFuture()`. `allOf` and the cancel methods are built in JavaScript, as in Python, and `cancel()` on a `send()` future returns `false` (Q44). On a future over a native handle, `get()` calls `kafka_common_KafkaFuture_get_cb` and `get({ timeout })` calls `kafka_common_KafkaFuture_get_with_timeout_cb`, so the core enforces the deadline and no JavaScript timer runs (Q22). On a future with no native handle, such as `allOf()`'s, `get({ timeout })` races the future against a `setTimeout`, as Python's `asyncio.wait` does. The timer is cleared as soon as either side wins, and when the timer wins, the call rejects with `TimeoutError` and no message, as Java's `CompletableFuture` throws it. A zero or negative timeout rejects at once unless the future is done (Q22, Q44).
  - The Promise behind `get()` is created only when something first waits on the future, because Node ends the process on an unhandled rejection by default, so a failed send that nobody awaits must not create a rejected Promise. This mirrors Python's lazy inner future and gets the same A/B performance check. There's no `then` method, so `await` doesn't wait for delivery, and a send takes two steps: `const future = await producer.send(record)` means the record was accepted, and `await future.get()` means it was delivered (Q44).
  - A failed `get()` rejects with `ExecutionError`, whose `cause` is the failure (Q34).
  - Transactions keep Java's names, on the producer: `initTransactions()`, `beginTransaction()`, `sendOffsetsToTransaction()`, `commitTransaction()` and `abortTransaction()`. A send counts in a transaction once its `send()` Promise has resolved, and the docs state that guarantee instead of telling apps to await: "A send is part of the transaction once its `send()` Promise has resolved. `commitTransaction()` waits for its delivery, so there's no need to await `future.get()` first. A send whose Promise hasn't resolved yet may be left out." Their example awaits the sends with `Promise.all`, for an app that needs every send in the transaction. `beginTransaction()` waits too, so it returns a Promise *(deviation, as in Python: Java's returns at once)*. The binding adds nothing to `commitTransaction()`, `abortTransaction()` or `flush()`, because the core includes every send that returned a `KafkaFuture` and completes it before the call ends (Q51).
  - A new method that waits is one more Promise method when it's on a client. On a class that no client owns, it's an ask for the core (Q42).
- **Signatures**
  - A Java overload set is one method. Where it has several forms, the method takes one options object whose keys are Java's parameter names, and the given keys must match one Java form exactly; otherwise the call throws `IllegalArgumentError` naming every form. Unknown keys throw, and nothing is filled in, so a record with headers or a timestamp needs `partition: null`. Each Java form has one TypeScript overload signature (Q15, Q18, Q58).
  - A call with one parameter takes the value on its own, as in `poll(100)` and `send(record)`. A plain object is always the options object, except for config maps. Any other single value picks its form by `typeof`, `Array.isArray` or `instanceof`, and a value that fits no form throws `IllegalArgumentError` in Python's format, as in `commitSync() takes one of (), (timeout), (offsets), (offsets, timeout); got a string`. There's no bare form where two forms' values can't be told apart. Once released, a bare value keeps its form, and an overload that Java adds later and that would collide is reached only through its options object (Q15).
  - A config map may be passed bare, as in `new KafkaConsumer({ 'bootstrap.servers': 'localhost:9092', 'group.id': 'g' })` and `newTopic.configs({ 'cleanup.policy': 'compact' })`, and `{ configs }` stays as a second shape. A plain object is the options object when one of its keys is a parameter name of that method, and a config map otherwise. Other maps with string keys follow the one-parameter rule. This matches Java and departs from Python (Q15).
  - Forms with the same keys are told apart with plain `instanceof`, as in `deleteTopics({ topics: TopicCollection.ofTopicIds(ids) })`, and there's no `Symbol.for` brand. The docs say: "The client supports one copy of the package in an app. If `node_modules` holds two versions, calls that take the client's classes can fail." (Q15)
  - A pattern is only a `SubscriptionPattern`, and a `RegExp` throws an error that points to it (Q15).
  - `null` is Java's null, and it's accepted only where Java accepts null. `undefined` means "not given" only where a key is optional, which is in config maps and in the constructor keys of option classes. Anywhere else, `undefined` throws a `TypeError` that names the parameter and says to leave the key out or pass `null`, inside a list or headers too, and a required key that's missing gets the form error. Results use `null`, never `undefined`, and `Optional<T>` becomes `T | null` (Q18, Q20).
  - A timeout is a `number` of milliseconds or a `Temporal.Duration`. The root exports `type Duration = number | <the Temporal type>`, whose TSDoc says that a number is milliseconds, and every parameter or option key that takes a Java `Duration` is typed `Duration`. Java's `get(long, TimeUnit)` becomes `get({ timeout })`. A timeout key that's left out selects the overload without a timeout: it's sent as `-1`, and the core applies Java's default. A timeout that every overload has, as in `poll`, is required (Q22).
  - A `null` timeout throws `TypeError('timeout must not be null')`, except for `CloseOptions.timeout` and the admin `timeoutMs`, where `null` means the default. The binding doesn't check a negative timeout. The FFI rejects it with `IllegalArgumentError` and the core's message, "Timeout must not be negative", from every method *(deviation: Java says "Invalid negative timeout -1" from `poll`, `commitSync` and `position` and "The timeout cannot be negative." from `close`, and in `committed`, `partitionsFor`, `listTopics`, `beginningOffsets`, `endOffsets` and `offsetsForTimes` Java makes no check and waits forever, because its deadline calculation overflows. Why: the binding repeats no precondition (Q35). Goes when: the FFI returns Java's messages)* (Q22, Q35).
  - `NaN`, and a finite value above `Number.MAX_SAFE_INTEGER`, throw `RangeError`, and fractions are rounded down. `Infinity` is sent as `Long.MAX_VALUE` *(js-only)*. A `Temporal.Duration` is converted with `total({ unit: 'millisecond' })` and rounded down, one with years, months or weeks throws `RangeError`, and a negative one throws the same `IllegalArgumentError` as a negative number. Polyfills are accepted, and the `.d.ts` files declare their own small Temporal type (Q22).
  - The admin `timeoutMs` is a Java `Integer`: a value outside 32 bits, or `Infinity`, throws `RangeError`, a negative value is sent as `0`, and `null` means `default.api.timeout.ms` (Q22).
  - A timeout getter returns a `number`, or `null` when it's unset, and `Infinity` for `Long.MAX_VALUE`. The core enforces deadlines, never a JavaScript timer (Q22).

A lint bans `Buffer.from(string)` everywhere else, and the binding never cuts a string inside a surrogate pair (Q24).
- **Errors**
  - `KafkaError extends Error` heads the error tree, with one generated class per id in `kafka_common_Error_e`, following Java's class chain. `generate-error-codes` has a TypeScript emitter, and `check-generated` fails on stale output. The class is the check: there's no `is*()` method and no `code` property, and `name` is the fallback. The FFI id is kept in the private `_ffiId`, for the binding and the test harness (Q32).
  - Every class sets `name` to its class name, which is frozen once released. The root exports Java's built-in errors, such as `IllegalStateError`, `IllegalArgumentError`, `UnsupportedOperationError`, `ConcurrentModificationError` and `TimeoutError`. As in Python, `IllegalArgumentError` and `IndexOutOfBoundsError` extend `RangeError`, and the others extend `Error`. There are two `TimeoutError` classes, the root's and Kafka's in `common/errors`. Neither is the `DOMException` that `AbortSignal.timeout()` throws, and the docs say which call throws which (Q33).
  - A synchronous method throws. A method that returns a Promise never throws: it rejects, argument errors included. The binding copies a native error into JavaScript and frees it before the Promise settles, and an error with nowhere to go goes to `process.emitWarning` (Q34).
  - The binding repeats none of Java's preconditions. The FFI checks the mandatory parameters and the core checks the rest, and their error reaches the user as it comes, with Java's message where the core has it. The one exception is `group.id`: `groupMetadata()` and `committed(null)` without `group.id` throw `InvalidGroupIdError` with Java's message from the binding *(temporary. Why: the core checks `groupMetadata()` with a panic, which the FFI turns into `IllegalStateError` with `InvalidGroupIdError`'s message. Goes when: the FFI returns `InvalidGroupIdError`)*. A panic that the core catches reaches the user unchanged, and the docs say to close that client and create a new one (Q35).
  - A null where Java forbids one throws `TypeError`, and there's no `NullPointerError` *(deviation: Java throws `NullPointerException`. Why: `TypeError` is JavaScript's error for a null where an object is needed)*. The FFI's `LocalNullPointerError` becomes a `TypeError` that keeps Java's text, such as "topic cannot be null". The binding's own null checks are listed in Implementation over the FFI, and all checks run in Java's order (Q36).
  - Messages pass through unchanged: `err.message` is Java's `getMessage()`, or `''` when that is null. The binding writes messages only for its own errors, and those name JavaScript types. An error built from a cause alone takes the cause's `toString()` as its message, as Java's does. No message is reworded, the busy message included (Q37, Q48).
  - `cause` is read from `kafka_common_Error_source`. A value that the user's callback throws, or rejects with, crosses the FFI as `LocalCallbackError` and comes back as the same value, held through a Node-API reference. It's wrapped where Java wraps it, as in `KafkaError('User rebalance callback throws an error')` with the user's value as its `cause`, and a `KafkaError` passes unwrapped. An error injected into a mock is thrown again as the same instance (Q38, Q47).
  - An error's constructor takes one options object with `message` and `cause`, and Java's other parameters keep their names, as in `new TopicAuthorizationError({ message, unauthorizedTopics })` *(deviation: Java's names differ from class to class. Why: one shape for every error, so the generator and the mocks build any error the same way)*. A single value is read by its type: a plain object is the options object, a string is the message, and an `Error` is the cause, as in `new TimeoutError('Timed out')`. A second argument throws `IllegalArgumentError` in the form check's format (Q15), listing that class's forms, as in `KafkaError() takes one of (), (message), (cause), ({ message, cause }); got 2 arguments`, because a second argument is a call that fits no form. Payload getters stay methods, over private fields (Q39).
- **Serialization**
  - The core gets NULL serdes, and the binding runs the serdes in JavaScript, as in Python: serializers inside `send()`, before the record reaches the core, and deserializers inside `poll()`, after the core returns records. A serializer is called for `null` too, and a deserializer isn't, as in Python. A missing serde means bytes *(deviation, as in Python: Java fails)* (Q50).
  - A serde is an object with Java's methods, such as `{ serialize({ topic, headers, data }), close?() }`, with `deserialize` in place of `serialize` for a deserializer *(deviation: one method for Java's two `serialize` methods. Why: JavaScript can't have two methods with one name, and with positions a serde written like Java's two-argument form would get the headers as its data)*. `close()` runs when the client closes, and a failure there goes to `process.emitWarning`, never thrown. There's no `configure()`: a constructor argument comes ready, and Java doesn't call `configure()` for those either, while a function in a serde config key gets the config as its argument (Q50, Q53).
  - `serialize` and `deserialize` may return a Promise, which the binding awaits *(js-only, as 1.x's serdes do. Why: Schema Registry serdes fetch schemas over the network, and JavaScript can't block)*. A serde that returns a plain value adds no microtask. Sends that aren't awaited may then reach the core out of call order, like Java threads, and `await send()` keeps the order (Q50).
  - The built-in factories, such as `stringSerializer()` and `bytesDeserializer()`, match Java's serdes byte for byte, tested with Java's vectors. As a constructor argument, passing a factory instead of its result, as in `stringSerializer` for `stringSerializer()`, throws with Python's hint, "did you forget `()`?" (Q50). In a serde config key the factory itself is allowed (Q53).
  - When a deserializer fails, `poll()` rejects with `RecordDeserializationError`, and the binding seeks back, so the next poll returns the failed record again *(deviation, as in Python)* (Q50).
  - A serde comes as a constructor argument, `keySerializer`, `valueSerializer`, `keyDeserializer` or `valueDeserializer`, or through the config keys `key.serializer`, `value.serializer`, `key.deserializer` and `value.deserializer`, as in Java and Python. A config key takes a synchronous function, `({ configs, isKey }) => serde`, which the client calls once with the whole config, in place of Java's class and its `configure(configs, isKey)` call *(deviation: Java and Python take a class or a class name. Why: JavaScript can't load a class by name synchronously)*. A class name, a serde object, or a function that returns a Promise throws `ConfigError`. A built-in factory can go in the key without `()`, as in `{ 'key.serializer': stringSerializer }`, because it's itself such a function, so each built-in factory takes an optional `{ configs, isKey }`. A constructor argument wins, and its config key is then ignored, as in Java and Python. The client's own serde keys never reach the core, as in Python, while the other role's keys do, and the core lists them as unused. The function gets a config object that records the keys it reads, and the binding leaves those keys out of the config it sends to the core, as Java's `originals()` marks them as used, so a key such as `schema.registry.url` isn't listed as unused (Q53).
  - The binding doesn't copy a key or value that the app hands over as a `Buffer` or `Uint8Array`, one that a serializer returns included *(deviation: Java copies the bytes inside `send()`. Why: it saves a memory copy of each Buffer, as the Python binding does)*. The core reads the app's own bytes until it registers the record, and the binding holds a reference to the Buffer until the send settles and drops it on the JavaScript thread. Header values are always copied, because the C API has no borrowed form for them. `send()`'s docs and the README say: "The client reads a `Buffer` or `Uint8Array` key or value after `send()` returns. Don't write to it, transfer it or resize it until the Promise from `send()` settles; awaiting `send()` is enough. A serializer must return a new Buffer for each record." A `Buffer` over a `SharedArrayBuffer` is borrowed the same way, not copied, and the docs add: "If other workers share the Buffer's memory, they mustn't write to it until then either." This rule covers produce only (Q21).
  - The binding doesn't copy a consumed key or value either. Each is a `Buffer` over the record's own bytes in the core's fetch buffer, made with `napi_create_external_arraybuffer`, as the Python binding hands out memoryviews into the core's batch. The binding keeps the native record alive until every `Buffer` over it has been garbage collected, and then destroys it. Where the runtime refuses external buffers with `napi_no_external_buffers_allowed`, as Electron does, the binding copies the bytes instead. A header value on consume is a `Buffer` over the record's bytes in the same way (Q31). The consumer's docs and the README say: "A key or value from `poll()` points into the memory the client fetched, and a value you keep holds that whole fetch in memory. To keep a value for long, copy it with `Buffer.from(value)`." They also list Electron as a known limitation: "Electron doesn't allow external buffers, so on Electron the client copies each consumed key, value and header value." (Q24, Q31)
  - `Headers` wraps the FFI's `RecordHeaders`: it's a TypeScript class over a native handle, translated from Java's `Headers` interface, and its `add`, `remove`, `lastHeader`, `headers` and `toArray` call the addon, so the core holds the headers and enforces the read-only state *(js-only: Python and .NET keep plain headers and build the native ones at the send boundary)*. A `Headers` the app makes owns its handle, made with `kafka_common_header_internals_RecordHeaders_new`, and the Node-API finalizer destroys it. The FFI copies the headers into the native record on send, so the binding itself marks the app's `Headers` read-only with `kafka_common_header_internals_RecordHeaders_set_read_only` once the serializers have run, as Java's `send()` does. A consumed record's `Headers` wraps the view that `kafka_consumer_ConsumerRecord_headers` lends out, which is valid only while the native record lives, so it keeps the record alive, as Q24's Buffers do (Q31).
  - `Header` wraps the C `RecordHeader` too *(js-only, as for `Headers`)*. `lastHeader()` and `headers()` hand out a `Header` over the FFI's borrowed `kafka_common_header_internals_RecordHeader_t` view, which reads its key with `kafka_common_header_Header_key` and its value with `kafka_common_header_Header_value`, and it keeps its `Headers` alive. A `RecordHeader` the app makes owns its handle, made with `kafka_common_header_internals_RecordHeader_new_err`, the form with an error slot (Q28), and the Node-API finalizer destroys it. `add(header)` stores a copy, so the app's handle stays its own. A header's value is a `Buffer` over the native bytes, as Q24's values are, or `null`, and the `Buffer` keeps its `Header` alive. Where the runtime refuses external buffers, the binding copies the value. The FFI's view is valid only until its `Headers` next changes, so how a `Header` from a `Headers` that can still change stays valid is open (Q31).
- **Configuration**
  - `configs` is a plain object with Java's dotted keys, as the PRFAQ says, and a `Map` throws `TypeError`, because its entries aren't object keys. The binding has no `ConfigDef` table and checks no value. It converts each value to the string that the FFI takes, where `true` becomes `'true'`, arrays are joined with commas, and numbers are written in decimal, and it passes every key to the core except the four serde keys (Q53). `null` and `undefined` leave the key unset. The core checks types, ranges, enums, unknown keys and cross-key rules, with Java's messages that name the key, so `{ 'linger.ms': true }` fails with the core's "Not a number of type LONG" rather than Java's text. Any other value becomes text too, so an object becomes `[object Object]` (Q52).
  - librdkafka's keys and a 1.x `kafkaJS` block reach the core as unknown keys, which the core lists in one INFO log line. The binding adds no check or warning of its own, so the migration guide says that such keys are now ignored (Q54). Every consumer needs `group.protocol: 'consumer'` until the core changes its default, and every example sets it. `interceptor.classes` and `partitioner.class` are unknown keys that the core reports, as in Python, and `partitioner.type` selects a built-in partitioner and passes through (Q52, Q53).
  - The default partitioner is the core's, which hashes keys with CRC-32 (`ConsistentRandomPartitioner`, librdkafka's `consistent_random`), and the binding doesn't change it. 1.x's KafkaJS-style API and Java hash keys with murmur2, so the same key can land on another partition. The migration guide says so, and names `partitioner.type: 'Murmur2RandomPartitioner'` for an app that must keep murmur2's placement (Q53).
  - No config value is a callback, and no constructor takes an error callback or a logger; errors throw or reject. The core logs to stderr through `env_logger` under `RUST_LOG`, and once the core has a log hook, its logs go to a `node:diagnostics_channel` channel. The binding's own warnings, such as the preview warning and deprecations, use `process.emitWarning`, and its debug lines use `util.debuglog('confluent_kafka')`, shown with `NODE_DEBUG=confluent_kafka`. 1.x's `rebalance_cb` becomes a listener passed to `subscribe()`, and its `offset_commit_cb` the commit call's callback. A custom OAuth token callback has no replacement until the core has a token hook (Q56).
  - As in Python, `ProducerConfig`, `ConsumerConfig` and `AdminClientConfig` are translated for their constants only, such as `ProducerConfig.BOOTSTRAP_SERVERS_CONFIG` *(deviation: their `ConfigDef` machinery isn't translated. Why: the binding has no `ConfigDef` table (Q52))*. Key-name and value classes, such as `TopicConfig` and `SaslConfigs`, are translated in full, without their `ConfigDef` methods, and `CommonClientConfigs` isn't translated. The TypeScript type of `configs` lists the known keys for autocompletion and still takes any string, through `(string & {})`, because unknown keys go to the core *(js-only, types only)* (Q54, Q55).
- **Threads and callbacks**
  - Every callback runs on the JavaScript thread that owns the client, the main thread or the worker that created it, and never on a Rust thread. Each client has one thread-safe function: the FFI's notify hook only signals it, and the binding then drains `<Client>__execute_callbacks()` on the JavaScript thread. The binding adds no thread (Q45).
  - Listeners and commit callbacks run while the call that delivers them (`poll`, `commit`, `close`) is pending, and that call settles only after they report. Send callbacks run in a later turn of the event loop, or inside a later `send()`. So that a tight `await send()` loop can't starve deliveries, every 64th send that is accepted at once, and the first send after one that had to wait, runs the producer's queued callbacks before sending, and every 1000th send yields to the event loop with `setImmediate`. This is Python's fix, and its numbers are measured again in Node (Q45).
  - The rebalance listener's methods, the commit callback and the send callback may return a Promise *(deviation: Java's callback methods return `void`. Why: JavaScript can't block, so a Promise is the only way a callback can wait for async work, such as a commit in `onPartitionsRevoked`)*. The binding wraps the result with `Promise.resolve(result)` and calls `__set_callback_result` only when it settles. A rejection, or a throw before the callback returns, is the callback's error, handled as in Java: it crosses the core as `LocalCallbackError`, the consumer call that ran the callback (`poll`, `commit*`, `close`) fails with it, the producer logs a send callback's error, and no rejection is left unhandled. The core waits for send callbacks too, so a slow send callback delays its record's future and `flush()` (Q47).
  - While a listener's or commit callback's report is pending, the `ConsumerHandle` methods work, through their `_cb` forms, and the binding keeps draining callbacks; the consumer's `poll`, `subscribe`, `assign` and `close` fail with `ConcurrentModificationError` *(deviation, as in Python)*. Inside a send callback, `flush()`, `close()`, the transaction calls and awaiting a later record's future would wait for that same callback, so they're documented as anti-patterns: the core refuses them only before the callback's first `await`, and after it they can hang (Q46).
  - A callback that never settles has no timeout, as in Java: it blocks the call that ran it, such as `poll()` or `close()`, `wakeup()` doesn't end it, and the docs say so. The binding doesn't destroy a consumer while a report is pending, and never reports once destroy has returned (Q49).
  - `wakeup()` is a plain synchronous method that goes straight to the FFI and works at any time from any code on the client's thread, such as a timer or a signal handler. JavaScript has no asynchronous exceptions, so there's no Ctrl+C rule like Python's: the app wires `SIGINT` and `SIGTERM` to `wakeup()` and closes once its loop ends (Q48). There's no seek-back after a wakeup, because the core's `poll` either returns records or fails *(not checked)*. The preview has no per-call cancellation, and an `AbortSignal` may be added later, but never in place of `wakeup()` (Q49).
  - The producer and the admin client take any number of calls at once. The consumer takes one call at a time: the binding passes the core's error through, with no tracking and no async locks of its own, and `wakeup()`, `metrics()` and the callback window are exempt. The busy message is the FFI's, unchanged: "KafkaConsumer is not safe for multi-threaded access." for an overlapping consumer call, and, for a `ConsumerHandle` call outside a callback, the core's longer message, which starts with the same sentence. `close()` during a pending `poll()` fails, as in Java, so the app calls `wakeup()`, lets its loop exit, and then awaits `close()` (Q48).
  - A client stays in the thread that created it. The preview doesn't support clients in worker threads, because a worker that ends with its client still open, through `worker.terminate()`, `process.exit()` or an uncaught error, may crash the whole process until the cleanup hook under Future improvements exists. The binding doesn't refuse a client in a worker and keeps no check for it, so the rules above still say how one behaves. The docs say: "The preview doesn't support clients in worker threads. Create clients in the main thread, and send plain data to and from workers." They also show how to turn `Buffer` and `Headers` values into plain data (Q16, Q21).
- **Lifetime**
  - There's no finalizer. A client that's never closed runs until the process exits, with a warning *(js-only: Java logs nothing)*. Apps use `await client.close()` or `await using`, and registrations are released on the JavaScript thread (Q21).
  - A client keeps Node running from the moment it's created until `close()` closes it, as KafkaJS and 1.x do from `connect()` to `disconnect()`. The binding leaves the client's thread-safe function referenced, as Node-API creates it, and calls `napi_unref_threadsafe_function` once `close()` has closed the client, so nothing is counted. In a worker, it keeps the worker running the same way. A script that forgets `close()` never exits on its own *(deviation: Java's client threads are daemon threads, so a program can exit with a client still open. Why: Node exits in the middle of an `await` when nothing holds it, so this way no pending send or poll is cut off, as with KafkaJS and 1.x)* (Q21).

- **Future improvements** (not in the preview: an agent builds none of these until a rule takes the entry's place)
  - A cleanup hook for clients in worker threads (Q21). A worker can end while its client is still open only when `worker.terminate()`, `process.exit()` or an uncaught error stops it before its `close()` has finished, because an open client otherwise keeps the worker running. Node then frees the worker's memory while the core keeps running the client, so the core may signal a thread-safe function that Node has freed, or read a Buffer that a pending send still borrows, and either may crash the whole process. The addon would register the hook with `napi_add_env_cleanup_hook` when it creates a client and remove it with `napi_remove_env_cleanup_hook` once the client's `close()` succeeds, so Node runs it only for a client that's still open. The lean is that the hook clears the client's notify hook, closes the client with a zero timeout and then calls `_destroy`. The zero timeout fails the pending sends at once with Java's "Producer is closed forcefully.", so no send still borrows a Buffer, while a consumer skips its final auto-commit and may not leave its group. The other way only clears the notify hook and leaves the client to leak, with the warning. Either way the FFI changes first, for the producer, the consumer and the admin client: `__set_callbacks_notify` must accept `NULL` to clear the hook, which it rejects today, and clearing must wait until a call of the hook in flight has returned, which it doesn't do today. A test ends a worker with `worker.terminate()` while sends are pending and checks that the process keeps running.
  - `[util.inspect.custom]` on data objects, so `console.log(tp)` prints Java's `toString()` format, such as `orders-3` (Q29). Until then `console.log(tp)` prints the fields, as `TopicPartition { topic: 'orders', partition: 3 }`, and `` `${tp}` `` gives Java's format.
  - A debug check that a Buffer borrowed by a pending send didn't change before the send settled (Q21). It would hash each Buffer at `send()` and again when the send settles, so it costs time on every send, and no other client has one. The lean is to turn it on with `NODE_DEBUG=confluent_kafka`, which already shows the binding's debug log.
  - A closed client that's garbage collected while one of its calls still has an answer queued (Q49). The core's `_destroy` handles a pending report cleanly: it wakes a call still waiting, which fails with the wakeup error, waits for every `_cb` call, and runs each queued report exactly once before it frees the client (`kafka_consumer_KafkaConsumer_destroy`). But it runs those reports on the thread that calls it. So when Q61's finalizer calls `_destroy` for a closed client that still has an answer queued, such as the core's error for a call made after `close()`, the binding's JavaScript runs during garbage collection, and `_destroy` may hold the thread for up to 5 seconds while the client's runtime stops. Only an app that drops a closed client without awaiting such a call meets this. The lean is that the binding keeps a client reachable while one of its calls is pending, so the finalizer only ever finds an empty queue. Keeping Node running counts nothing (Q21), so this needs a count of its own, or a reference that each pending call holds. The other way is to run `_destroy` after the garbage collection, through `node_api_post_finalizer`, if the Node-API version that the addon targets has it.
  - Refusing a call made inside a callback after the callback's first `await`, when the call waits for that same callback, such as `await producer.flush()` inside a send callback (Q46). The core refuses such a call only during the callback's synchronous part, so after an `await` the call hangs, and the docs list these calls as anti-patterns. Node's `AsyncLocalStorage` could carry an "inside this callback" mark across `await`s, so that the binding throws instead. Python tracks the same thing with a `ContextVar`, for the producer's async send callbacks (`python/confluent_kafka/producer/async_producer.py:137`) and the consumer's callbacks (`python/confluent_kafka/consumer/_base.py:211`). The mark adds work to every callback, and send callbacks run once per record, so a spike measures the cost first. It's also a check that the binding keeps itself, not the FFI or the core.

## Development Workflow
The Rust code lives in `rust/`, the bindings in `python/` and `c/`. Run the `cargo` commands below from `rust/`; run `make` targets from the repository root.
- **Build**: `cargo build`
- **Test**: `cargo test`, run the timeout tool with timeout 10s by default when checking if single tests are timing out.
- **Format**: `cargo xtask format`
- **Format Check**: `cargo xtask format-check` (CI-friendly)
- **Lint**: `cargo xtask lint` (runs clippy with warnings as errors)
- **Lint Fix**: `cargo xtask lint-fix` (automatically fix clippy warnings)
- **Check Generated**: `cargo xtask check-generated` (validates generated code formatting only)
- **Coverage (unit)**: `cargo xtask coverage` (report at rust/coverage/html/index.html)
- **Coverage (lcov)**: `cargo xtask coverage-lcov` (writes rust/coverage/lcov.info)
- **Coverage (all tests)**: `cargo xtask coverage-all` (requires Docker)
