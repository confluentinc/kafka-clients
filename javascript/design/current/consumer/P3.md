What the forms and types follow:
- `offsets` and `timestampsToSearch` are `TopicPartitionMap`s only, and a `Map` is refused with the hint
  `payload.ts` already gives (line 62). A `long` taken is a `bigint` or a whole `number`, and one returned a
  `bigint` (line 93). `committed()` and `offsetsForTimes()` map a partition with no answer to `null`, as Java's
  Javadoc says, and `currentLag()` answers `null` for Java's empty `OptionalLong`, as the rules branch's line 97 says
  (P2.md, choice 8(a)).
- A bare `null` is refused with the form error where two one-parameter forms would both take it (line 73):
  `commitSync(null)` gives "commitSync() takes one of (), (timeout), (offsets), (offsets, timeout); got null".
- A timeout follows line 79: `null` is a `TypeError`, and a negative one goes to the FFI, which rejects it with the
  core's "Timeout must not be negative" (line 80). Each timed form's docs carry the timeout's `@throws` rows, as
  `poll`'s do (P2's issue 151-5). The six methods whose Java form makes no check and waits forever (`committed`,
  `partitionsFor`, `listTopics`, `beginningOffsets`, `endOffsets`, `offsetsForTimes`) say so in their `@remarks`,
  as line 80's deviation.
- `commitAsync()`'s docs say what line 65 says: both commits return Promises, only `commitSync()` waits for the
  broker, without a callback a failed commit isn't reported, and a commit not awaited keeps the consumer busy.
- `enforceRebalance()` resolves after the core logs "Operation not supported in new consumer group protocol", as
  Java's `AsyncKafkaConsumer` does (decision 9).
- The temporary `group.id` check (line 119): `groupMetadata()` and `committed(null)` without `group.id` throw, or
  reject with, `InvalidGroupIdError` and Java's message. The class records at construction whether `group.id` was
  given (choice 3). Every other check is the FFI's or the core's.
- P2's documented order of the null checks (`NOTES.md`, issue 151-3) covers P3's methods too: a null partition,
  collection or map is refused at the FFI's boundary, before the core's closed, busy and group checks, and a
  `TopicPartition` with a null topic gets the FFI's `TypeError`. So `position(null)` rejects with `TypeError` where
  Java says "You can only check the position for partitions assigned to this consumer.". In the same way, the FFI's
  busy check comes before `seek`'s negative-offset check, which Java makes first. Each method's `@remarks` says so
  where the doc-size limit leaves room, and `NOTES.md` lists them all, with a test that pins the order.
- A `null` timestamp in `offsetsForTimes` is a `TypeError`, as Java's unboxing throws `NullPointerException`: the
  binding's run-time type check, since a `null` has no `int64` to cross as. (The FFI would read a NULL value as 0.)
