### The built-in serdes (decision 1(a))

1. `common/serialization/deserializer.ts`: the `Deserializer` interface, `{ deserialize({ topic, headers, data }),
   close?() }` (line 126). It mirrors `Serializer`: one method for Java's three `deserialize` forms *(deviation, as
   the serializer's)*, whose result may be a Promise (line 127). `data` is a `Buffer` over the fetched bytes (line
   133).
2. Java's ten serializer and ten deserializer classes, for String, ByteArray, Short, Integer, Long, Float, Double,
   Boolean, UUID and Void, one file each in `common/serialization/`, translated from Java's source and built with
   `new` (line 128):
   - Their types follow the Types table: Short and Integer take a `number`, range-checked; Long takes a `bigint` or
     a whole `number` and returns a `bigint`; Float and Double are numbers; `ByteArrayDeserializer` returns the
     `Buffer` it's given.
   - Void is `null`, and a UUID is a canonical string that `UUIDSerializer` writes in lowercase. A string or bytes
     that hold no UUID are `SerializationError('Error parsing data into UUID')` *(deviation, line 128)*.
   - String and UUID are UTF-8 only, with no `configure()` *(deviation, line 128)*.
   - A built-in serializer given a value of another type throws `SerializationError`, naming the JavaScript types
     (line 129).
   - A serializer is called for `null`, and a deserializer isn't (line 124).
   - In plain JavaScript, any function given as a serde constructor argument throws `TypeError` "did you forget
     `new`?" (line 129). There are no factories (line 128).
3. `stringSerializer()` and its six charsets go. `string_serializer.ts` holds the `StringSerializer` class instead,
   and `encodeLikeJava` keeps only its UTF-8 form. The producer's README, MIGRATION.md, example, tests, docs and API
   report move to `new StringSerializer()`. The charset keys (`serializer.encoding` and the two others) are then
   unknown keys, which the core lists.
4. `tools/java-vectors/JavaVectors.java` gains the vectors of the twenty classes: Java's bytes for each value and
   Java's messages for each failure. `test/java_vectors.json` is regenerated from kafka-clients 4.4.0, built from
   `kafka/` in a scratch clone with Homebrew's JDK 17 (§5). The `stringSerializer` charset vectors go.

### The consumer's deserializers (PLAN §4.5)

5. The constructor takes Java's `(Map, Deserializer, Deserializer)` form as `{ configs, keyDeserializer,
   valueDeserializer }` (Java's `Properties` form is the same `configs`). TypeScript infers `K` and `V` from the
   deserializers (line 27). A `null` one means the config key's, and with neither there are Buffers.
6. The config keys `key.deserializer` and `value.deserializer` take `({ configs, isKey }) => deserializer`, as the
   producer's take serializers (line 131). A class name, a serde object, a class or a function returning a Promise
   is a `ConfigError` with PR #312's hints, such as "did you mean `() => new StringDeserializer()`?". PR #312's
   `serde.ts` helpers serve both roles (DoD #6). The configs follow choices 3 and 4.
7. `await KafkaConsumer.create(...)` (line 156) uses PR #312's `create()` code. It awaits each config function in
   turn, the key's first. A failure rejects with `KafkaError('Failed to construct kafka consumer')`, whose `cause` is
   the failure, after the deserializers already made are closed (line 157). The serde keys' own `ConfigError`s
   aren't wrapped.
8. `poll()` runs the deserializers over the records the core returns (line 124), as Java's `CompletedFetch.parseRecord`
   does: the key, then the value, each only when it isn't null. A deserializer gets the record's own `Headers` (line
   135). A plain result adds no microtask; a thenable is awaited, record by record (line 127).
9. A failing deserializer ends the batch where Java's `FetchCollector` ends it, as Python's binding does:
   - The records deserialized before it are returned. `poll()` rejects with `RecordDeserializationError` only when
     there are none.
   - The error carries Java's message ("Error deserializing KEY for partition t-0 at offset 5. If needed, please seek
     past the record to continue consumption."), its fields (origin, partition, offset, timestamp, the key and value
     Buffers, the headers), and the thrown value as its `cause`.
   - The core has already moved past the whole batch, so the binding seeks each partition back to its first record
     not returned (the consumer's `seek_with_offset_cb`, awaited before `poll()` settles). So
     `seek({ partition: e.topicPartition(), offset: e.offset() + 1n })` skips the record, and otherwise the next poll
     fails on it again (line 130, *deviation, as in Python*).
10. The deserializers' `close()` runs once the core reports the consumer closed. What it throws goes to
    `process.emitWarning` (line 126), a thrown `null` or `undefined` included.
11. Decision 13's interim refusal goes, with its tests and its `NOTES.md` lines.
12. `MockConsumer` takes no deserializers, as Java's typed mock doesn't, and has no `create()` (line 156).
