## 1. Deliverables

### The new forms

On `Consumer`, `KafkaConsumer` and `MockConsumer`, through the shared bodies of `internal/consumer_calls.ts`. Option
keys are the interface's parameter names (line 41): `callback` for both. Both methods keep returning Promises, their
entry points having `_cb` twins (line 64). Every entry point is in the header today (PLAN §3).

| Method | New forms | Entry points (`kafka_consumer_` dropped) |
|---|---|---|
| `subscribe` | `{ topics, callback }`, `{ pattern, callback }` | `Consumer_subscribe_with_topics_listener_cb`, `Consumer_subscribe_with_pattern_listener_cb`; `ConsumerRebalanceListener_new_err`, `_destroy_err` |
| `commitAsync` | `{ callback }` or bare, `{ offsets, callback }` | `Consumer_commit_async_with_callback_cb`, `Consumer_commit_async_with_offsets_callback_cb`; `OffsetCommitCallback_new_err`, `_destroy_err` |
| every method | — | `Consumer__set_callback_result_err` (the reports); `Consumer_handle_err` and `ConsumerHandle_destroy_err`; the `ConsumerHandle_*` forms of the window, below |

The forms follow Java:
- **A listener** is a `ConsumerRebalanceListener` and never `null`: Java throws "RebalanceListener cannot be null",
  and so does the FFI for a NULL listener, in Java's order (before the topics' check). Each of its methods takes one
  object, `{ partitions }`, a `TopicPartitionSet` (line 56). A missing required method (`onPartitionsRevoked`,
  `onPartitionsAssigned`) goes to `ConsumerRebalanceListener_new_err` as NULL, whose `LocalNullPointerError` becomes a
  `TypeError` (line 57). A missing `onPartitionsLost` runs `ConsumerRebalanceListenerDefaults`, which calls
  `onPartitionsRevoked`, checked at each call (line 56). A listener that isn't an object is a `TypeError` (line
  183's run-time checks).
- **A commit callback** is `OffsetCommitCallback | null`, since Java's `commitAsync()` is `commitAsync(null)`, and
  is called as `callback({ offsets, exception })` (P1's type). A callback that isn't a function or `null` is a
  `TypeError`. Under choice 2(a), `commitAsync({ callback: null })` and `commitAsync(null)` call `commit_async_cb`,
  which is Java's `commitAsync()`: the core logs a failed commit, as Java's null branch does.
  `commitAsync({ offsets, callback: null })` has no such entry point, so the NULL goes to the FFI, which refuses it
  with `TypeError` ("callback must not be null"), ask 14. Under choice 3(a), `offsets` is `null` where Java's is:
  for a failed commit, and for an empty map committed (Java's `completedFuture(null)`), where the FFI hands over an
  empty map *(temporary. Why: the FFI passes an empty map where Java passes null. Goes when: the FFI passes NULL,
  ask 15)*. On the mock, `offsets` is the map committed, as Java's mock passes it.
- **A listener method or callback may return a Promise** (line 148). Any result but `undefined` is wrapped with
  `Promise.resolve`, and the report waits for it. A throw, or a rejection, is the callback's error: it crosses the
  core as a `LocalCallbackError` that carries the value, through the carrier P4 shared (`native/mock_values.c`), so
  the value comes back as the same object (line 122). No rejection is left unhandled.
- **Each callback's error comes back where Java's would, wrapped as Java wraps it** (line 122):

  | The error of | comes back from | as |
  |---|---|---|
  | a listener method | `poll()`, `unsubscribe()` | a `KafkaError` as itself, and anything else as the `cause` of `KafkaError('User rebalance callback throws an error')` |
  | a listener method | `close()` | the `cause` of `KafkaError('Failed to close kafka consumer')`: a `KafkaError` as itself, and anything else inside a `KafkaError` built from it, whose message is the value's `toString()` |
  | a commit callback | `commitSync()`, `commitAsync()` | as itself |
  | a commit callback | `poll()` | a `KafkaError` as itself, and anything else inside a `KafkaError` built from it |
  | a commit callback | `close()` | as itself, the `cause` of `KafkaError('Failed to close kafka consumer')` |
  | the mock's listener or commit callback | `rebalance()`, `losePartitions()`, `commitAsync()` | as itself |

  These are Java's `AsyncKafkaConsumer`: `invokeRebalanceCallbacks` and `poll` wrap through
  `ConsumerUtils.maybeWrapAsKafkaException`, which leaves a `KafkaException` alone; `close` always wraps, the
  listener's error having gone through `maybeWrapAsKafkaException` in `runRebalanceCallbacksOnClose` and the commit
  callback's not; the commit paths call `onComplete` without a `try`; Java's mock calls the listener directly. Python
  gives `close()` the value as the direct `cause`, without Java's middle `KafkaError`; the binding keeps Java's.

  The core's error already has Java's layers, with a `LocalCallbackError` where Java has the value, and its own
  wrapping where Java's would leave a `KafkaException` alone, since a `LocalCallbackError` sits beside
  `KafkaException` (`rust/src/common/local_callback_error.rs`). So the binding puts the value back in its place,
  drops a layer that only `maybeWrapAsKafkaException` around a non-`KafkaException` makes when the value is a
  `KafkaError`, keeps `close()`'s own layer, and gives a layer built from its cause alone the value's `toString()` as
  its message (line 121). It finds the value by the `LocalCallbackError` that `error.c` reads, and a layer built
  from its cause alone by its message being the core's text of that cause, as Python's binding does. All of it is
  in one place (DoD #6).
- **The window** (line 149, PLAN §4.4 and decision 8). While a listener method's or commit callback's report is
  pending, the addon sends each call the `ConsumerHandle` has to the handle, which the core admits while it runs a
  callback; every other call goes to the consumer as usual. The addon counts the pending reports itself.

  | While a report is pending | Methods |
  |---|---|
  | through the handle's `_cb` forms | `commitSync` (4 forms), `commitAsync` (3), `seek` (2), `seekToBeginning`, `seekToEnd`, `pause`, `resume`, `position` (2), `committed` (2), `partitionsFor` (2), `listTopics` (2), `offsetsForTimes` (2), `beginningOffsets` (2), `endOffsets` (2), `currentLag` |
  | through the handle's sync forms | `assignment()`, `paused()`, `groupMetadata()`, `wakeup()` |
  | to the consumer, which answers | `metrics()` |
  | to the consumer, which refuses with `ConcurrentModificationError` "KafkaConsumer is not safe for multi-threaded access." | `poll`, `subscribe`, `assign`, `unsubscribe`, `close`, `subscription()` *(deviation, as in Python: Java's listener may call them. Why: the handle has no form of them, KIP-1306. Goes when: it has)* |

  The handle's longer message (line 152) shows only in a race: the core checks a handle call when the call runs, not
  when it's made, so a call that a callback makes without awaiting it may run after the callback has reported, and
  then gets the longer message. A test can't pin that timing, so the docs describe it. Any call made while a report
  is pending goes to the handle, a timer's included, as JavaScript can't tell which code made it.

  On a mock the handle isn't gated, as Java's mock has no `acquire()`, but it does less (ask 16): of its async
  operations only the commits and `currentLag` work, and the others fail with the core's `UnsupportedOperationError`
  ("ConsumerHandle async operations are not supported on a MockConsumer handle; drive the MockConsumer directly.").
  The calls the handle doesn't have meet the mock's single-owner flag, which `rebalance()`, `losePartitions()` and
  `commitAsync()` hold while the callback runs. Java's synchronized mock takes all of them.
- **Lifetimes, as the FFI's docs give them** (`rust/src/ffi/consumer/mod.rs`, the subscribe docs):
  - The addon keeps a listener until a later successful `subscribe` replaces it, a listener-less one included.
    `assign` and `unsubscribe` keep it.
  - A failed `subscribe` keeps the earlier listener. On a `KafkaConsumer` an empty topic list is `unsubscribe()`: it
    keeps the earlier listener and registers none.
  - A `KafkaConsumer` drops its listener once `close()` returns. A `MockConsumer` keeps it until the destroy, as its
    `rebalance()` and `losePartitions()` still call it after `close()`, as Java's mock does.
  - A commit callback is kept until it reported, or until the destroy.
  - The binding doesn't destroy a consumer while a report is pending, and never reports once the destroy has returned
    (line 150). So a pending report holds the consumer's object, and the finalizer can't run until it's made. A
    callback that the destroy itself runs (line 212's case) may report until the destroy returns, and a later report
    is dropped; the addon's memory for the consumer stays until then.
  - A callback that never settles has no timeout, and `wakeup()` doesn't end it (line 150). The docs say so.
- **Where the FFI differs from Java**, a test pins what the binding does, and `NOTES.md`, the package docs and PLAN
  §6 record it, as new asks:
  - 14: the FFI refuses a NULL commit callback, which Java takes (choice 2).
  - 15: a commit callback gets an empty map where Java's gets `null` (choice 3).
  - 16: inside a mock's callback, the handle does less than Java's reentrant mock, as above.

## 4. Your choices (decided 2026-11-27)

The user approved P5 as written ("approve 2a, 3a start P5"), with choice 2 the recommended (a) and choice 3 the
recommended (a).

1. **Approve P5** as written, or say what to change.

2. **`commitAsync` with a `null` callback.** Java takes a null commit callback, and its `commitAsync()` is
   `commitAsync(null)`. The FFI refuses a NULL callback (`require_ref` in `commit_callback_registration`,
   `rust/src/ffi/consumer/offset_commit_callback.rs`).
   - (a) *Recommended.* `{ callback: null }` calls the no-callback entry point, `commit_async_cb`, which is Java's
     `commitAsync()`, its failure log included. `{ offsets, callback: null }` has no such entry point, so it gets the
     FFI's `TypeError`, a deviation and ask 14, until the FFI takes a NULL callback.
   - (b) Both send the NULL to the FFI and get its `TypeError`. It's simpler, but `commitAsync({ callback: null })`
     then fails where Java's works.
   - (c) The binding passes a do-nothing callback for `null`. It works, but a failed commit is then silent, where
     Java logs it.

3. **A commit callback's `offsets` where Java passes `null`.** Java's callback gets `null` offsets for a failed
   commit, and for an empty map committed. The FFI hands it an empty map in both cases (`register_async_commit` in
   `rust/src/consumer/internals/async_kafka_consumer.rs`).
   - (a) *Recommended.* The binding passes `null` there, as Java does and as Python's binding does: when the
     callback's error is set, and when the app committed an empty map. P1's type already allows `null`. It's marked
     temporary, with ask 15, and goes when the FFI passes NULL.
   - (b) The binding passes the FFI's empty map, a deviation pinned by a test, with ask 15. It adds no logic to the
     binding, but an app that tests `offsets === null`, as Java's code tests for null, never sees it.

These stay with the user, unchanged: the merge style for 152-7, 151-3, and decision 14.
