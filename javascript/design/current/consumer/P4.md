## 1. Deliverables

### The mock's members

`MockConsumer<K, V> implements Consumer<K, V>`. Its `Consumer` members are `KafkaConsumer`'s, every form P2 and P3
built, through the same code (item 1) and the same native functions, over the mock's `__as_Consumer` view. They
come in the interface's order with no docs of their own, only a `@remarks` where the mock differs
(`check-implementation-docs`; Java's mock has no Javadoc on them, so no size limit applies). The mock's own members
follow, in Java's declaration order, with TSDoc translated from Java's Javadoc and kept within 150% of it
(`check-doc-size`, §6). Option keys are Java's parameter names (line 41). A member returns a Promise exactly when its
entry point has a `_cb` twin (line 64). Every entry point is in the header today (PLAN §3).

What the forms and types follow:
- Java's type parameters, with no defaults, as Java's have none: a test writes them, as
  `new MockConsumer<string, string>('earliest')`, the one case line 55 allows (a mock built without serdes). The mock
  takes no deserializers and runs none.
- `maxPollRecords` and the offsets are Java `long`s, a `bigint` or a whole `number` (line 93). `newOffsets` is a
  `TopicPartitionMap` only, a `Map` refused with `payload.ts`'s hint (line 62); `newAssignment`, `partitionsLost`
  and `partitions` take any iterable. `exception` is a `KafkaError` or `null`, Java's `KafkaException`, by a run-time
  type check (line 183), and `record` a `ConsumerRecord`.
- **The records are the app's own.** `addRecord(record)` keeps `record` through one reference until the mock is
  destroyed, as `add_record`'s doc requires, and its key and value cross as the addresses of that holder's two tags,
  as the producer mock's do. `poll()` hands back the very objects, as Java's mock returns the records it was given:
  `testSimpleMock` checks it with `assertEquals`, which for a `ConsumerRecord` (no `equals()`) is identity. The C
  record carries only what the FFI's mock reads (topic, partition, offset and leader epoch); the headers stay on the
  app's record. This refines PLAN §4.6, which had a reference to each key and value (§5).
- An error given to `setPollException` or `setOffsetsException` comes back as the very same object (line 122),
  through the producer mock's carrier, now shared (item 7): `poll()` rejects with it once, and `beginningOffsets()`
  or `endOffsets()` with the offsets error once, as Java's mock throws and clears them.
- Every check is the FFI's or the core's, with Java's message where the core has it (line 119): an unassigned
  partition's record, a lost partition that isn't assigned, `setMaxPollRecords(0)`, an invalid or null strategy, and
  `offsetsForTimes()`, which Java's mock doesn't support ("Not implemented yet."). The temporary `group.id` check
  stays `KafkaConsumer`'s: Java's mock answers a dummy `ConsumerGroupMetadata` and has no such check.
- The mock is the same native handle as a `KafkaConsumer`'s, as `MockProducer` is a producer's (line 185): its
  waiting methods settle from the drain; it takes one call at a time (line 152), so a call made while another is
  pending, a mock method included, fails with `ConcurrentModificationError`, except as the next point says; it keeps
  Node running from its creation until `close()` (line 158), so every test closes its mock; its finalizer destroys
  it only once closed (line 155), the close completion deciding, as for a `KafkaConsumer` (Java's mock always
  closes); and it emits no preview warning (line 186).
- Where the FFI's mock differs from Java's, the binding passes it through (lines 119 and 184), a test pins it, and
  `NOTES.md` and the package docs list it; PLAN §6 gains asks 8 to 10 (§9):
  - the setters with no error to report (the three `update*Offsets`, `setPollException`, `setOffsetsException`,
    `scheduleNopPollTask`), called while another call on the mock is pending, are logged and ignored by the FFI,
    where Java's synchronized mock waits and applies them (ask 8);
  - a `null` offset in `newOffsets` is a `TypeError`, the binding's run-time type check, as P3's `null` timestamp
    is: the FFI reads a NULL value as 0, where Java's mock keeps the null and later reports the partition as having
    no offset (ask 9);
  - a `null` topic or list given to `updatePartitions`, and a `null` option given to `close`, get the FFI's
    `TypeError`, where Java's mock stores or ignores them (ask 10), as the producer mock's `partitionsFor(null)`
    does;
  - `metrics()` on a closed mock fails with the FFI's panic error, ask 5's prefix, where Java's mock throws "This
    consumer has already been closed." (ask 5 gains it);
  - the check orders of 151-3 and 152-2 hold for the mock too: `addRecord(null)` on a closed mock is a
    `TypeError`, not "This consumer has already been closed.".
- Left out: Java's `subscribe(Pattern…)` forms, as on `KafkaConsumer` (line 112's row); the listener and
  commit-callback forms until P5; the deprecated `MockConsumer(OffsetResetStrategy)` and `close(Duration)`. For want
  of an FFI entry point (PLAN §6, items 1–3): `clientInstanceId`, `setClientInstanceId`, `disableTelemetry`,
  `injectTimeoutException`, `schedulePollTask`, `registerMetricForSubscription`,
  `unregisterMetricFromSubscription` and `addedMetrics`. By the user's decision of 2026-11-26, as Python drops them:
  `enforceRebalance()`, `enforceRebalance(reason)`, `shouldRebalance()` and `resetShouldRebalance()`, each with a
  permanent baseline line under a comment naming that decision (item 11), as `P3-followup.md` item 3 said. The
  rules branch's new line (`1d95fd94b`) names the mock's two helpers too.
