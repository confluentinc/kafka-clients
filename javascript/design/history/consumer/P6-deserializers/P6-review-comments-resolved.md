## Issue 155-1: a value config function's failure closes the caller's own key deserializer, which Java's consumer leaves open
- **Commit**: `3f43689f7` javascript: the consumer's deserializers, Java's built-in serdes, and KafkaConsumer.create()
- **File**: `javascript/src/internal/client_construction.ts:136` (`construct`), `javascript/src/internal/serde.ts:385` (`awaitedSerdes`), `javascript/test/unit/consumer/kafka_consumer.test.js:799-815`
- **Severity**: Behavior Mismatch
- **Reference**: `org.apache.kafka.clients.consumer.internals.AsyncKafkaConsumer#AsyncKafkaConsumer(ConsumerConfig,Deserializer,Deserializer,Time,...)` and `org.apache.kafka.clients.consumer.internals.Deserializers#Deserializers(ConsumerConfig,Deserializer,Deserializer,Metrics)`; P6.md item 7 ("after the deserializers already made are closed"); conventions line 157 ("closes the serdes that those functions returned")
- **Description**: When the value's serde config function throws or rejects, the shared construction code closes the key's serde "given or made": `given[0] ?? keyMade` in `construct`, and `given[0] ?? made[0]` in `awaitedSerdes`. That is Java's producer: `KafkaProducer` assigns `keySerializerPlugin` before it builds the value serializer, so the catch's `close(Duration.ofMillis(0), true)` closes the key serializer, given or made. Java's consumer differs. It builds both deserializers in one `new Deserializers<>(config, keyDeserializer, valueDeserializer, metrics)`, and assigns `this.deserializers` only once both are configured. When the value's `getConfiguredInstance` or `configure` throws, that field stays null, and the catch's `close(Duration.ZERO, ..., true)` reaches `closeQuietly(deserializers, ...)` with null. So Java closes no deserializer, and the caller's own `keyDeserializer` stays open. `AsyncKafkaConsumer.close` closes deserializers through that field only. A probe of the built package, with no broker:
  ```
  const shared = { deserialize: () => null, close: () => { closed++; } };
  new KafkaConsumer({ configs: { 'bootstrap.servers': '127.0.0.1:1', 'group.id': 'g', 'group.protocol': 'consumer',
    'value.deserializer': () => { throw new Error('no schema'); } }, keyDeserializer: shared, valueDeserializer: null })
  -> KafkaError Failed to construct kafka consumer | given key deserializer closed 1 time(s)
  KafkaConsumer.create({ configs: { ...same, 'value.deserializer': async () => { throw new Error('no schema'); } },
    keyDeserializer: shared, valueDeserializer: null })
  -> KafkaError Failed to construct kafka consumer | given key deserializer closed 1 time(s)
  ```
  The unit test pins this as Java's behaviour: "A deserializer given is closed too, as Java's catch closes what it has taken." (kafka_consumer.test.js:799). The comment above `taken` in `construct` ("Java's constructor assigns the key's, then the value's, and its catch closes only those") is true of Java's producer only. P6.md item 7 and line 157 ask only that the deserializers the functions made be closed, and `create()`'s TSDoc says the same: "a deserializer already made is then closed". As it stands, a caller who shares one deserializer instance across consumers, or retries the build with it, finds it closed by the failed build. The core's own construction failure ("Failed to construct kafka consumer" after the functions ran) is not affected. There Java has assigned `this.deserializers`, so closing both, given ones included, is Java's behaviour.
- **Expected**: On the consumer, a failure of the value's config function closes the key deserializer that the key's function made (line 157) and leaves a given one open, as Java's consumer closes no deserializer it was given there. The constructor and `create()` behave the same. The producer keeps PR #312's close of the given key serializer, which is Java's. The test asserts the given deserializer is closed 0 times on both paths, and the comment in `construct` says which client it describes.
- **Actual**: Both paths close the caller's key deserializer once, and the test asserts it.
- **Fixed in**: `d8e13025f` (fixup! of `3f43689f7`). `SerdeRole.keyTakenFirst` (true for the producer, false for the consumer) decides whether a failure of the value's function closes a given key serde: the consumer closes only what its config functions made, in `construct` and `awaitedSerdes`, and closes the serdes given only on the core's construction failure once both are taken. The producer keeps PR #312's behaviour, Java's. The test now asserts the given deserializer is closed 0 times, on the constructor and on `create()`.

## Issue 155-2: the deserializer window is real, but no test pins it and the consumer's class remarks still promise one call at a time
- **Commit**: `3f43689f7` javascript: the consumer's deserializers, Java's built-in serdes, and KafkaConsumer.create()
- **File**: `javascript/design/current/consumer/NOTES.md:49-52`, `javascript/src/consumer/kafka_consumer.ts:89-92`, `javascript/test/` (no test)
- **Severity**: Test Gap
- **Reference**: P6.md §7 ("Any other FFI or core difference the build finds is recorded the same way: a pinned test, a NOTES.md line, an ask"); conventions line 152 (the consumer takes one call at a time); the `KafkaConsumer` class remarks
- **Description**: NOTES.md records a new deviation, which the user is asked to accept: while a deserializer's Promise, or a seek back, is awaited, the core's poll has already answered, so the core takes other calls on the consumer. A broker probe (a scratch `apache/kafka:4.3.1`, now removed) confirms it. With an async value deserializer held pending and `poll(5000)` still pending, `position(tp)` resolved to `3`, a position past the whole batch the app hasn't received yet. `assignment()` answered, `pause()`/`resume()` resolved, and even a second `poll(0)` resolved. The same calls made while a plain core poll was pending rejected with `ConcurrentModificationError` "KafkaConsumer is not safe for multi-threaded access.". No test makes a call while a deserializer's Promise or a seek back is pending. The only busy test ("one call at a time: the core busy error, wakeup() ending the waiting poll, close() refused meanwhile") pins the opposite, for a plain poll. The NaN deviation, by contrast, is pinned by `floatSerdeShouldPreserveNaNValues`. The published class remarks still say "the consumer takes one call at a time, as Java's does: a call made while another is pending rejects with `ConcurrentModificationError` (...), `wakeup()` and `metrics()` excepted". That is false for a poll awaiting a deserializer's Promise or a seek back, and no user-facing text states the exception: not the class remarks, not `poll()`'s docs, not the consumer package docs. One more point, for the user's decision: "as in Python" holds only for the seek back. Python's deserializers can't wait: an `async def` serde is refused (root CLAUDE.md, Python conventions, Serialization). So Python has no window while a deserializer is awaited, and here that window can last as long as a Schema Registry fetch.
- **Expected**: A test that pins the window. For example, a broker test that holds an async deserializer pending and shows `position()` resolving and `assignment()` answering while `poll()` is still pending, so that a change to the window is noticed. The class remarks, or `poll()`'s, name the exception. The NOTES line scopes "as in Python" to the seek back.
- **Actual**: The deviation is recorded only in NOTES.md. No test pins it, and the published remarks state the opposite.
- **Fixed in**: `d8e13025f` (fixup! of `3f43689f7`): a broker test in `test/integration/consumer.test.js` holds an async deserializer pending and shows `position()` answering 3n, past the batch, and `assignment()`, `pause()` and `resume()` going through while `poll()` is pending; NOTES.md and the consumer package docs describe the window as the deviation the user accepted on 2026-11-27, with "as in Python" scoped to the gap between the seeks back. `e4e0b0d04` (new commit: the lines are P2's): `KafkaConsumer`'s class remarks name the exception.

## Issue 155-6: NOTES.md's Python comparison is wrong for Python's sync consumer, which releases its guard before its deserializers run
- **Commit**: `d8e13025f` fixup! javascript: the consumer's deserializers, Java's built-in serdes, and KafkaConsumer.create()
- **File**: `javascript/design/current/consumer/NOTES.md:54-56`
- **Severity**: Behavior Mismatch
- **Reference**: `python/confluent_kafka/consumer/_base.py`, `_ConsumerState._run_sync` (and `_poll_spec`, whose `convert` runs `deserialize_batch`); the user's decision on deviation 1b, relayed for round 2
- **Description**: The new text says: "Only the gap between the seeks back is shared with Python, whose seeks back are separate guarded calls; Python refuses an `async def` deserializer and holds its own guard while its deserializers run". The user asked for this wording, but the part about the guard is false for Python's sync `KafkaConsumer`. `_run_sync` takes its use of the handle in `with self._use() as h:` and returns `resolve(payload)` after that block has closed. For `poll()`, `resolve` is `_resolve_value(convert)`, and `convert` runs `deserialize_batch`. So Python runs its deserializers after releasing its own guard, and the FFI's guard is free too, since the core's poll has answered. A probe of the built Python package against a scratch broker (`apache/kafka:4.3.1`, now removed) shows it. The probe used `python3.12 -I`, three records and a value deserializer that blocks on an `Event`:
  ```
  control: assignment -> ConcurrentModificationError KafkaConsumer is not safe for multi-threaded access.
  while the deserializer runs: {'assignment': ['critic155-py-window-0'], 'position': 3}
  ```
  In the first line, a second thread called `assignment()` while the poll waited in the core. In the second, the second thread called while the poll thread was inside the deserializer: `position()` answered 3, past the batch not yet returned. That is the very effect NOTES.md describes for this binding. So Python's sync consumer has the same window from another thread while its deserializers run, and the gaps between its seeks back. Only its asyncio consumer has no deserializer gap: it runs its deserializers on the event loop, where no other task runs meanwhile. This corrects my own round-1 remark that "as in Python" held only for the seek back, which was too narrow.
- **Expected**: The comparison says what Python does. For example: "Python's sync `KafkaConsumer` runs its deserializers after releasing its guard (`_ConsumerState._run_sync` resolves after `with self._use()`), so another thread's call goes through while they run, as it does between its seeks back, which are separate guarded calls. Its asyncio consumer runs them on its event loop, where no other task runs meanwhile, so its only gaps are between its seeks back. Python refuses an `async def` deserializer, so only the wait for a deserializer's Promise is this binding's own." The user dictated the current wording, so the change needs the user's word.
- **Actual**: NOTES.md says Python holds its guard while its deserializers run, and that only the seek-back gap is shared with Python.
- **Fixed in**: `8ca405ef4` (fixup! of `d8e13025f`): NOTES.md's comparison replaced with the wording the user approved on 2026-11-27, word for word. The package docs and `KafkaConsumer`'s remarks make no such Python claim (their "as in Python" is the seek back's).
